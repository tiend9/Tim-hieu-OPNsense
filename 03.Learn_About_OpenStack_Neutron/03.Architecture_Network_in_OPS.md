# KIẾN TRÚC MẠNG TRONG OPENSTACK

> Tài liệu cập nhật theo OpenStack 2026.1 Gazpacho, là bản stable mới nhất tại thời điểm viết. Neutron trong nhánh này thuộc dòng 28.x.

## I. Mục tiêu của kiến trúc mạng OpenStack

Mạng trong OpenStack cần giải quyết 4 việc chính:

- Cấp kết nối mạng cho VM.
- Cô lập network giữa các project/tenant.
- Cho VM đi ra mạng ngoài hoặc Internet.
- Áp chính sách bảo mật, NAT, DHCP, metadata và QoS.

Trong OpenStack, **Neutron** là service chịu trách nhiệm chính cho networking. Nova không tự xử lý network nữa mà gọi Neutron để tạo/gắn port cho VM.

```text
User / Horizon / CLI
        |
        v
Nova boot VM
        |
        v
Neutron tạo port, cấp MAC/IP, security group
        |
        v
Backend network cấu hình datapath trên compute node
        |
        v
VM có network
```

## II. Các loại mạng trong một cụm OpenStack

Một môi trường OpenStack thường có nhiều lớp mạng khác nhau. Không nên gom tất cả vào một mạng duy nhất.

| Loại mạng | Mục đích |
| --- | --- |
| Management/API network | Cho API, database, RabbitMQ, SSH, service nội bộ |
| Provider/External network | Nối OpenStack ra mạng vật lý, cấp floating IP hoặc public IP |
| Overlay/Tunnel network | Dùng cho VXLAN/Geneve giữa các compute/network node |
| Storage network | Dùng cho Ceph, iSCSI, NFS hoặc traffic storage |
| Tenant/Self-service network | Mạng private do project tự tạo |

Mô hình cơ bản:

```text
                Physical Network / Internet
                          |
                          v
                  Provider / External Net
                          |
                          v
                   Neutron Router
                          |
                          v
                Self-service Tenant Net
                          |
                          v
                         VM
```

## III. Các node tham gia vào network

### 1. Controller node

Controller node chạy control plane:

- `neutron-server`
- ML2 plugin
- Keystone, Nova API, Glance API
- Database
- Message queue

Controller chủ yếu xử lý API và lưu trạng thái. Trong mô hình OVS truyền thống, controller thường không trực tiếp đi qua datapath của VM.

### 2. Compute node

Compute node chạy VM và datapath local:

- Hypervisor như KVM/QEMU.
- Nova compute.
- Open vSwitch hoặc OVN/OVS.
- Tap interface của VM.
- Security group enforcement.
- Tunnel endpoint nếu dùng VXLAN/Geneve.

Traffic của VM luôn bắt đầu từ compute node.

### 3. Network node

Network node thường có trong mô hình OVS truyền thống dùng self-service network:

- L3 agent.
- DHCP agent.
- Metadata agent.
- Router namespace `qrouter-*`.
- DHCP namespace `qdhcp-*`.
- Gateway ra provider/external network.

Network node là điểm quan trọng vì nếu không có HA/DVR, nhiều traffic North/South sẽ đi qua node này.

### 4. OVN database/gateway node

Trong mô hình OVN hiện đại:

- OVN Northbound DB lưu logical switch/router.
- OVN Southbound DB lưu binding và logical flow.
- `ovn-northd` chuyển state từ NB DB sang SB DB.
- `ovn-controller` chạy trên từng compute/gateway node.
- Gateway chassis xử lý kết nối ra provider/external network.

OVN giảm phụ thuộc vào L3 agent/DHCP agent truyền thống vì nhiều chức năng được xử lý native và phân tán.

## IV. Hai kiểu network chính

### 1. Provider network

**Provider network** là mạng được admin tạo và map trực tiếp xuống mạng vật lý.

![Neutron](./images/Neutron_12.png)

Đặc điểm:

- Thường dùng flat hoặc VLAN.
- VM có thể nằm trực tiếp trên mạng vật lý.
- Phù hợp public network, external network, lab đơn giản.
- Ít overhead hơn overlay.
- Phụ thuộc vào switch vật lý, VLAN trunk, bridge mapping.

Ví dụ logic:

```text
VM
 |
 v
tap port
 |
 v
br-int
 |
 v
br-provider / br-ex
 |
 v
NIC vật lý / bond
 |
 v
Physical switch
```

Provider network không bắt buộc phải có Neutron router. Nếu subnet trên provider network đã có gateway vật lý, VM có thể đi ra ngoài qua gateway vật lý.

### 2. Self-service network

**Self-service network** là mạng private do project tự tạo. Đây cũng thường được gọi là tenant network hoặc project network.

![Neutron](./images/Neutron_13.png)

Đặc điểm:

- User/project tự tạo được trong phạm vi quota.
- Thường dùng overlay như VXLAN hoặc Geneve.
- Các project có thể dùng CIDR trùng nhau vì network được cô lập.
- Muốn ra ngoài thường phải đi qua Neutron router.
- Phù hợp cloud multi-tenant.

Ví dụ logic:

```text
VM
 |
 v
br-int
 |
 v
br-tun hoặc OVN Geneve/VXLAN datapath
 |
 v
Overlay network
 |
 v
Network/Gateway node
 |
 v
Router/NAT
 |
 v
Provider network
```

## V. Provider network vs Self-service network

| Tiêu chí | Provider network | Self-service network |
| --- | --- | --- |
| Người tạo | Admin/operator | User/project |
| Kết nối mạng vật lý | Trực tiếp | Gián tiếp qua router/gateway |
| Công nghệ thường dùng | Flat, VLAN | VXLAN, Geneve |
| Cô lập tenant | VLAN/physical segment | Overlay network ID |
| NAT/Floating IP | Không bắt buộc | Thường cần |
| Độ phức tạp | Thấp hơn | Cao hơn |
| Use case | Public, external, direct VLAN | Private tenant network |

## VI. Kiến trúc OVS truyền thống

Open vSwitch là backend rất phổ biến trong OpenStack. Với ML2/OVS, các node chạy OVS agent để cấu hình bridge và flow.

Các bridge hay gặp:

| Bridge | Vai trò |
| --- | --- |
| `br-int` | Integration bridge, nơi nối port VM vào OVS |
| `br-tun` | Tunnel bridge cho VXLAN/GRE |
| `br-ex` hoặc `br-provider` | Bridge nối ra provider/external network |

### 1. Port của VM trên compute node

VM không nối trực tiếp vào card vật lý. Luồng cơ bản:

```text
VM eth0
  |
  v
tap interface trên host
  |
  v
OVS/Linux bridge/security group layer
  |
  v
br-int
```

Trong mô hình OVS cũ dùng `iptables_hybrid`, thường có thêm Linux bridge:

```text
VM tap
  |
  v
qbr bridge
  |
  v
qvb <-> qvo
  |
  v
br-int
```

Ý nghĩa:

- `tap...`: interface của VM trên host.
- `qbr...`: Linux bridge dùng cho iptables security group.
- `qvb...` và `qvo...`: veth pair nối Linux bridge với OVS.
- `br-int`: OVS integration bridge.

Trong triển khai mới hơn có thể dùng **native Open vSwitch firewall driver**, khi đó không cần lớp `qbr/qvb/qvo` cho security group. Tuy vậy, nhiều tài liệu và môi trường thực tế vẫn dùng `iptables_hybrid`, nên khi debug cần kiểm tra cấu hình thực tế.

### 2. Provider network với OVS

Đường đi gói tin:

```text
VM
 |
 v
tap/qbr hoặc tap trực tiếp
 |
 v
br-int
 |
 v
patch port
 |
 v
br-provider hoặc br-ex
 |
 v
physical NIC/bond
 |
 v
physical switch
```

Ví dụ bridge mapping:

```ini
[ovs]
bridge_mappings = provider:br-provider
```

Nếu tạo provider network với `--provider-physical-network provider`, tên `provider` phải khớp với mapping trên node.

### 3. Self-service network với OVS

Self-service network dùng tunnel để nối các compute node.

```text
VM
 |
 v
br-int
 |
 v
br-tun
 |
 v
VXLAN tunnel qua overlay network
 |
 v
br-tun trên node đích
 |
 v
br-int
 |
 v
VM hoặc router namespace
```

Cấu hình thường gặp:

```ini
[ml2]
type_drivers = flat,vlan,vxlan
tenant_network_types = vxlan
mechanism_drivers = openvswitch,l2population

[ml2_type_vxlan]
vni_ranges = 1:1000

[ovs]
local_ip = <IP_OVERLAY>

[agent]
tunnel_types = vxlan
l2_population = True
```

### 4. DHCP và Router namespace

Trong OVS truyền thống:

- DHCP chạy trong namespace `qdhcp-<network-id>`.
- Router chạy trong namespace `qrouter-<router-id>`.
- Metadata thường đi qua metadata agent hoặc route tới `169.254.169.254`.

Kiểm tra:

```bash
ip netns list
ip netns exec qdhcp-<id> ip a
ip netns exec qrouter-<id> ip route
ip netns exec qrouter-<id> iptables -t nat -S
```

Ví dụ router namespace:

```text
qrouter
  |
  |-- qr-* : interface nối vào tenant subnet
  |
  |-- qg-* : gateway interface nối ra external/provider network
```

## VII. Kiến trúc OVN hiện đại

OVN là backend hiện đại được dùng nhiều trong triển khai OpenStack mới. OVN vẫn dùng Open vSwitch làm datapath, nhưng control plane khác OVS agent truyền thống.

Mô hình:

```text
Neutron API
    |
    v
ML2/OVN mechanism driver
    |
    v
OVN Northbound DB
    |
    v
ovn-northd
    |
    v
OVN Southbound DB
    |
    v
ovn-controller trên từng node
    |
    v
Open vSwitch datapath
```

### 1. Thành phần OVN

| Thành phần | Vai trò |
| --- | --- |
| OVN Northbound DB | Lưu logical switch, logical router, ACL, NAT |
| `ovn-northd` | Chuyển logical topology sang logical flow |
| OVN Southbound DB | Lưu port binding, chassis, tunnel, logical flow |
| `ovn-controller` | Chạy trên node, lập trình flow vào OVS |
| Gateway chassis | Node xử lý kết nối ra provider/external network |

### 2. OVN thay thế gì?

OVN có thể thay thế nhiều agent truyền thống:

| Chức năng | OVS truyền thống | OVN |
| --- | --- | --- |
| L2 switching | OVS agent | OVN logical switch |
| L3 routing | L3 agent | OVN logical router |
| DHCP | DHCP agent/dnsmasq | OVN native DHCP hoặc tùy cấu hình |
| Security group | iptables/OVS firewall | OVN ACL |
| Distributed routing | DVR | Native OVN distributed routing |

### 3. Provider network trong OVN

Provider network được map qua localnet port và bridge mapping.

```text
Logical Switch
      |
      v
localnet port
      |
      v
br-provider / br-ex
      |
      v
physical network
```

Ví dụ mapping:

```bash
ovs-vsctl set Open_vSwitch . external-ids:ovn-bridge-mappings=provider:br-provider
```

### 4. Self-service network trong OVN

Self-service network thường dùng Geneve.

```text
VM trên compute A
      |
      v
OVN logical switch
      |
      v
Geneve tunnel
      |
      v
OVN logical switch
      |
      v
VM trên compute B
```

Neutron network được ML2/OVN chuyển thành OVN logical switch. Neutron router được chuyển thành OVN logical router.

## VIII. Đường đi gói tin

### 1. Provider network, VM đi ra ngoài

![Neutron](./images/Neutron_14.png)

```text
VM
 -> tap/qbr hoặc tap trực tiếp
 -> br-int
 -> br-provider/br-ex
 -> NIC vật lý/bond
 -> switch vật lý
 -> router vật lý
 -> mạng ngoài
```

Trường hợp này đơn giản vì VM nằm gần mạng vật lý. Nếu gateway nằm ngoài OpenStack, Neutron router không cần tham gia.

### 2. Provider network, hai VM cùng VLAN

![Neutron](./images/Neutron_15.png)

```text
VM A
 -> br-int
 -> br-provider
 -> physical switch
 -> br-provider trên node đích
 -> br-int
 -> VM B
```

Nếu hai VM nằm cùng compute node và cùng network, traffic có thể chỉ đi trong `br-int`.

### 3. Self-service network, hai VM cùng network khác compute node

![Neutron](./images/Neutron_16.png)

```text
VM A
 -> br-int
 -> br-tun hoặc OVN tunnel
 -> VXLAN/Geneve qua overlay network
 -> br-tun/OVN tunnel node đích
 -> br-int
 -> VM B
```

Traffic không đi qua router vì hai VM cùng L2 tenant network.

### 4. Self-service network, VM đi Internet bằng fixed IP

![Neutron](./images/Neutron_17.png)

```text
VM private IP
 -> tenant network
 -> router namespace hoặc OVN logical router
 -> SNAT sang IP gateway external
 -> provider/external network
 -> Internet/DC network
```

Trong OVS truyền thống, NAT thường nằm trong `qrouter-*`. Trong OVN, NAT nằm trong logical router và được xử lý qua gateway chassis/distributed flow.

### 5. Self-service network, truy cập VM bằng floating IP

![Neutron](./images/Neutron_18.png)

```text
Client ngoài
 -> floating IP trên external network
 -> DNAT trên Neutron router/OVN logical router
 -> fixed IP của VM
 -> VM
```

Floating IP thực chất là NAT 1-1 giữa IP public/external và fixed IP của port VM.

### 6. Self-service network, hai VM khác network

![Neutron](./images/Neutron_19.png)

```text
VM A network A
 -> router
 -> VM B network B
```

Nếu hai network cùng gắn vào một Neutron router, router sẽ route giữa chúng. Nếu không có router hoặc route phù hợp, hai network không nhìn thấy nhau.

## IX. North/South và East/West

| Hướng traffic | Ý nghĩa | Ví dụ |
| --- | --- | --- |
| North/South | Traffic đi vào/ra cloud | VM ra Internet, client ngoài vào floating IP |
| East/West | Traffic giữa workload trong cloud | VM A nói chuyện VM B |

Điểm cần nhớ:

- Provider network North/South thường đi thẳng ra mạng vật lý.
- Self-service North/South thường đi qua router/NAT.
- East/West cùng network không cần router.
- East/West khác network cần router.
- Với OVN hoặc DVR, một phần routing có thể được phân tán xuống compute node.

## X. Security group trong đường đi gói tin

Security group là firewall stateful ở mức Neutron port.

Trong OVS truyền thống:

- `iptables_hybrid`: dùng Linux bridge và iptables.
- `openvswitch`: dùng OpenFlow/conntrack trong OVS, không cần Linux bridge trung gian.

Trong OVN:

- Security group được chuyển thành ACL trong OVN.
- OVN dùng logical flow để enforce rule.

Lưu ý:

- Không ping/SSH được VM thường do thiếu rule ingress.
- Security group áp vào port, không áp vào subnet.
- Port security chống spoofing MAC/IP.
- Appliance, VRRP, load balancer có thể cần `allowed-address-pairs`.

Ví dụ mở ping và SSH:

```bash
openstack security group rule create --proto icmp default
openstack security group rule create --proto tcp --dst-port 22 default
```

## XI. NAT, Floating IP và Metadata

### 1. SNAT

SNAT dùng khi VM private IP đi ra ngoài.

```text
10.0.0.10 -> SNAT -> 203.0.113.10
```

### 2. DNAT/Floating IP

DNAT dùng khi client ngoài truy cập VM qua floating IP.

```text
203.0.113.25 -> DNAT -> 10.0.0.10
```

### 3. Metadata

VM lấy metadata qua địa chỉ:

```text
169.254.169.254
```

Metadata dùng cho:

- SSH key.
- cloud-init user-data.
- hostname.
- network config.

Trong OVS truyền thống, metadata thường đi qua metadata agent. Trong OVN, có OVN metadata path riêng tùy cấu hình triển khai.

## XIII. Lỗi thường gặp khi thiết kế network

### 1. Sai bridge mapping

Ví dụ tạo network với `--provider-physical-network provider`, nhưng node không có:

```ini
bridge_mappings = provider:br-provider
```

Kết quả: VM boot được nhưng không đi được ra provider network.

### 2. VLAN chưa allow trên switch vật lý

Provider VLAN cần được trunk từ host ra switch. Nếu VLAN không được allow, traffic sẽ bị drop ngoài OpenStack.

### 3. Sai MTU khi dùng overlay

VXLAN/Geneve thêm header nên packet lớn hơn. Nếu MTU không đúng, có thể ping nhỏ được nhưng SSH/HTTP lỗi hoặc chập chờn.

### 4. Security group thiếu rule

Mặc định ingress thường bị chặn. Cần mở ICMP/SSH/HTTP tùy nhu cầu.

### 5. Router thiếu external gateway

Self-service network không ra ngoài được nếu router chưa set gateway:

```bash
openstack router set router1 --external-gateway public
```

### 6. Metadata lỗi

Dấu hiệu:

- VM boot không nhận SSH key.
- cloud-init timeout.
- Không truy cập được `169.254.169.254`.

Kiểm tra metadata agent hoặc OVN metadata service, route, security group và Nova metadata API.

## XIV. Best practice ngắn gọn

- Tách management, provider, overlay và storage network.
- Dùng provider network cho public/external hoặc VLAN vật lý rõ ràng.
- Dùng self-service network cho tenant private network.
- Với triển khai mới, nên xem xét OVN trước vì routing/DHCP/security phân tán tốt hơn.
- Với OVS truyền thống, cần hiểu `br-int`, `br-tun`, `br-ex`, `qrouter`, `qdhcp`.
- Luôn kiểm tra MTU khi dùng VXLAN/Geneve.
- Không tắt port security nếu chưa hiểu tác động.
- Thiết kế HA cho network/gateway node nếu production.
- Chuẩn hóa `physical_network`, bridge mapping và VLAN range từ đầu.

## XV. Tổng kết

Kiến trúc mạng OpenStack có thể hiểu theo 3 lớp:

```text
API/control plane: Neutron, ML2, DB, message queue
        |
        v
Virtual network layer: network, subnet, port, router, security group
        |
        v
Datapath: OVS/OVN, bridge, tunnel, namespace, NIC vật lý
```

Nếu học để vận hành, cần nắm chắc:

- Provider network đi gần trực tiếp ra mạng vật lý.
- Self-service network dùng overlay và thường cần router/NAT.
- OVS truyền thống dùng agent, bridge và namespace.
- OVN hiện đại dùng logical switch/router, NB/SB DB và distributed flow.
- Packet flow phải được nhìn theo hướng North/South hoặc East/West.
