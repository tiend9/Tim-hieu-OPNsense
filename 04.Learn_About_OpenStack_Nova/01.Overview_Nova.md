# TÌM HIỂU COMPUTE SERVICE - NOVA

> Tài liệu này được viết lại theo **OpenStack 2026.1 Gazpacho**, bản stable mới nhất tại thời điểm 2026-05-26. Nova trong các bản hiện đại dùng Neutron cho network, Placement cho inventory tài nguyên, Cells v2 cho mô hình database/message queue, và quản trị chủ yếu qua `openstack` CLI.

## 1. Nova là gì?

**Nova** là dịch vụ Compute của OpenStack. Nova cung cấp API để tạo, xóa, quản lý vòng đời của instance, hay nói đơn giản hơn là quản lý máy ảo trong cloud.

Nova không phải hypervisor. Nova là tầng điều phối nằm phía trên hypervisor như KVM/QEMU, VMware vSphere, Ironic bare metal hoặc một số backend khác. Khi user tạo VM, Nova nhận request, kiểm tra quota/policy, hỏi Placement xem host nào còn tài nguyên, gọi Neutron để cấp port mạng, gọi Glance/Cinder khi cần image hoặc volume, rồi yêu cầu `nova-compute` trên compute node tạo instance qua driver hypervisor.

Các dịch vụ Nova cần để hoạt động trong một cloud cơ bản:

| Dịch vụ | Vai trò với Nova |
|---------|------------------|
| Keystone | Xác thực user, service user, token và policy |
| Glance | Cung cấp image để boot instance |
| Neutron | Cấp network, port, security group và floating IP cho instance |
| Placement | Theo dõi inventory và allocation CPU/RAM/disk/resource provider |
| Cinder | Cung cấp volume persistent, boot-from-volume, attach/detach volume |
| RabbitMQ | Message queue cho RPC giữa các service Nova |
| MariaDB/MySQL | Lưu state, mapping cell, instance, service, build request |

## 2. Những điểm đã thay đổi so với tài liệu Nova cũ

Một số khái niệm trong tài liệu cũ không còn phù hợp với Nova hiện đại:

| Nội dung cũ | Trạng thái hiện nay |
|-------------|---------------------|
| `nova-network` | Không dùng trong triển khai mới, thay bằng Neutron |
| EC2 API trong `nova-api` | Không còn là phần baseline của Nova hiện đại |
| `nova-placement-api` | Placement đã tách thành service riêng |
| `nova-consoleauth` | Không còn là service cần cấu hình trong mô hình console proxy hiện đại |
| `rpc_backend = rabbit`, `rabbit_host` | Thay bằng `transport_url = rabbit://...` |
| Keystone admin port `35357` | Không dùng nữa, dùng Keystone v3 qua port `5000` |
| Không có Cells v2 | Cells v2 là bắt buộc trong Nova hiện đại |
| Không có service user token | Nova 2026.1 yêu cầu cấu hình `[service_user]` cho các service Nova |

## 3. Thành phần chính của Nova

### 3.1. `nova-api`

`nova-api` nhận request REST API từ user, Horizon, SDK hoặc CLI. Nó xác thực request qua Keystone, kiểm tra policy/quota, ghi state vào database, gọi Placement/Neutron/Glance/Cinder khi cần, và gửi RPC tới các service nội bộ như scheduler, conductor hoặc compute.

Nova API hiện dùng Compute API v2.1 kèm cơ chế **microversion**. Microversion cho phép API phát triển dần mà không phá vỡ client cũ. Khi cần tính năng mới, client có thể chọn version cụ thể bằng biến môi trường hoặc option:

```bash
export OS_COMPUTE_API_VERSION=2.latest
# hoặc:
openstack --os-compute-api-version 2.latest server list
```

### 3.2. Metadata API

Metadata giúp instance lấy SSH key, hostname, user-data, vendor-data và các thông tin boot khác qua địa chỉ link-local:

```text
http://169.254.169.254
```

Trong môi trường dùng Neutron, luồng metadata thường đi qua `neutron-metadata-agent` hoặc metadata proxy trong namespace/router/DHCP agent, sau đó tới metadata API của Nova.

### 3.3. `nova-scheduler`

`nova-scheduler` chọn compute host để đặt instance. Scheduler không tự đo tài nguyên trực tiếp từ host như các kiến trúc cũ, mà dựa nhiều vào Placement để biết host/resource provider nào còn inventory và chưa bị allocation hết.

Các yếu tố thường ảnh hưởng tới quyết định scheduling:

- Flavor: vCPU, RAM, disk, extra specs.
- Image properties: kiến trúc CPU, machine type, firmware, bus disk/network.
- Host aggregates và availability zone.
- Server group: affinity, anti-affinity.
- Trait/resource class trong Placement.
- Compute service state: `enabled/disabled`, `up/down`.

### 3.4. `nova-conductor`

`nova-conductor` đứng giữa `nova-compute` và database. Compute node không nên truy cập database trực tiếp. Thay vào đó, compute gửi RPC về conductor để conductor xử lý truy vấn DB, điều phối một số workflow như build, resize, migrate, rebuild.

Vai trò này quan trọng cho bảo mật và rolling upgrade, vì control plane có thể nâng cấp trước trong khi compute node cũ vẫn hoạt động.

### 3.5. `nova-compute`

`nova-compute` chạy trên compute node, quản lý instance thực tế trên hypervisor. Với lab phổ biến, driver thường là libvirt/KVM:

```text
nova-compute
  -> libvirt
     -> QEMU/KVM
        -> instance
```

Nếu CPU hỗ trợ virtualization (`vmx` hoặc `svm`) thì dùng KVM. Nếu chạy trong nested lab không bật ảo hóa phần cứng, có thể phải dùng QEMU:

```ini
[libvirt]
virt_type = qemu
```

### 3.6. `nova-novncproxy`

`nova-novncproxy` cho phép user mở console instance qua trình duyệt. Proxy chạy trên controller hoặc node console, còn VNC server chạy trên compute node. Vì vậy compute node phải cấu hình đúng `server_listen`, `server_proxyclient_address`, và URL public của noVNC.

### 3.7. Placement

Placement là service riêng, nhưng Nova phụ thuộc rất mạnh vào nó. Placement lưu inventory và allocation của resource provider.

Ví dụ resource provider:

- Compute node có inventory `VCPU`, `MEMORY_MB`, `DISK_GB`.
- NUMA, huge page, PCI device hoặc GPU có thể được biểu diễn bằng trait/resource class.
- Storage hoặc network resource trong các mô hình nâng cao cũng có thể liên quan tới Placement.

Nếu Placement lỗi, instance thường bị kẹt ở scheduling hoặc lỗi `NoValidHost`.

![Nova](./images/Nova_1.png)

Một luồng tạo instance đơn giản:

```text
User / Horizon / CLI
  |
  v
nova-api
  |
  +--> Keystone: xác thực token
  +--> Glance: kiểm tra image
  +--> Neutron: tạo port mạng
  +--> Cinder: tạo/attach volume nếu boot từ volume
  +--> Placement: claim tài nguyên
  |
  v
nova-scheduler
  |
  v
nova-conductor
  |
  v
nova-compute trên compute node
  |
  v
libvirt/KVM tạo instance
```

Các thành phần giao tiếp với nhau theo hai kiểu chính:

- HTTP API: Nova gọi Keystone, Placement, Neutron, Glance, Cinder.
- RPC qua RabbitMQ: Nova API, scheduler, conductor, compute trao đổi tác vụ nội bộ.

## 5. Cells v2

Cells v2 là mô hình bắt buộc trong Nova hiện đại. Nó chia Nova thành:

```text
API DB
  |
  +-- cell0: chứa instance build lỗi, không có compute host
  |
  +-- cell1: chứa compute host thật, instance thật
  |
  +-- cell2/cell3/...: mở rộng quy mô lớn
```

Trong lab nhỏ, thường chỉ có `cell0` và `cell1`.

Các lệnh quan trọng:

```bash
nova-manage api_db sync
nova-manage cell_v2 map_cell0
nova-manage cell_v2 create_cell --name=cell1 --verbose
nova-manage db sync
nova-manage cell_v2 list_cells
nova-manage cell_v2 discover_hosts --verbose
```

Khi thêm compute node mới, phải discover host để Nova map host đó vào cell:

```bash
su -s /bin/sh -c "nova-manage cell_v2 discover_hosts --verbose" nova
```

Có thể cấu hình tự động discover:

```ini
[scheduler]
discover_hosts_in_cells_interval = 300
```

## 6. Storage trong Nova

Nova có hai kiểu storage phổ biến:

### 6.1. Ephemeral disk

Ephemeral disk do Nova/hypervisor quản lý. Root disk được tạo từ image và thường bị xóa khi xóa instance. Dung lượng disk lấy từ flavor.

Phù hợp cho:

- VM test.
- Workload stateless.
- Lab nhanh.

Không phù hợp nếu muốn dữ liệu tồn tại sau khi xóa instance.

### 6.2. Cinder volume

Cinder cung cấp persistent volume. Volume có thể attach vào instance hoặc dùng làm boot disk.

Phù hợp cho:

- Database.
- VM cần dữ liệu tồn tại.
- Boot-from-volume.
- Snapshot/backup ở tầng block storage.

Nova cần cấu hình giao tiếp Cinder trong section `[cinder]`, tối thiểu nên có:

```ini
[cinder]
region_name = RegionOne
```

## 7. Network trong Nova

Nova không tự quản lý network L2/L3 trong các triển khai mới. Nova gọi Neutron để:

- Tạo port cho instance.
- Gắn security group.
- Gắn fixed IP hoặc floating IP.
- Attach/detach interface.
- Lấy thông tin network khi boot.

Vì vậy lỗi boot VM có thể nằm ở Nova, nhưng cũng có thể nằm ở Neutron. Ví dụ:

- Port không bind được vào compute node.
- Neutron agent chết.
- Provider network mapping sai.
- Security group hoặc metadata route sai.
- DHCP namespace không cấp IP.

Khi debug, luôn xem cả Nova và Neutron:

```bash
openstack server show <vm>
openstack port list --server <vm>
openstack network agent list
openstack compute service list
```

## 8. Hypervisor được Nova hỗ trợ

Nova có nhiều driver, nhưng phổ biến nhất trong lab và production open source là **libvirt/KVM**.

| Driver | Ghi chú |
|--------|---------|
| libvirt/KVM | Phổ biến nhất, phù hợp lab và production |
| QEMU | Dùng khi không có hardware virtualization, chậm hơn KVM |
| Ironic | Bare metal thông qua OpenStack Ironic |
| VMware vSphere | Tích hợp môi trường VMware |
| zVM/Virtuozzo/LXC | Dùng cho các môi trường đặc thù |

Trong lab nested virtualization, kiểm tra CPU:

```bash
egrep -c '(vmx|svm)' /proc/cpuinfo
```

Kết quả `>= 1` thì dùng KVM được. Kết quả `0` thì cân nhắc `virt_type = qemu`.

## 9. Các lỗi Nova hay gặp

| Hiện tượng | Hướng kiểm tra |
|------------|----------------|
| VM kẹt `BUILD` rồi `ERROR` | `openstack server show`, log `nova-api`, `nova-conductor`, `nova-compute` |
| `NoValidHost` | Placement inventory, compute service, flavor/image extra specs, aggregate/AZ |
| Compute node không xuất hiện | Chạy `nova-manage cell_v2 discover_hosts --verbose` |
| Console không mở được | `[vnc] novncproxy_base_url`, firewall port `6080`, route controller-compute |
| VM không có IP | Neutron DHCP agent, port binding, provider mapping, security group |
| Metadata không hoạt động | Neutron metadata agent, DHCP/router namespace, `service_metadata_proxy`, shared secret |
| Attach volume lỗi | Cinder service, iSCSI/Ceph backend, `[cinder] region_name`, service user token |

Log thường dùng:

```bash
journalctl -u nova-api -n 100 --no-pager
journalctl -u nova-scheduler -n 100 --no-pager
journalctl -u nova-conductor -n 100 --no-pager
journalctl -u nova-compute -n 100 --no-pager
tail -f /var/log/nova/nova-compute.log
```

## 10. Kết luận

Nova là control plane điều phối compute, không phải hypervisor. Trong OpenStack hiện đại, Nova hoạt động tốt khi các mảnh sau khớp với nhau:

- Keystone xác thực đúng.
- RabbitMQ thông suốt.
- MariaDB có đủ DB và Cells v2.
- Placement thấy compute resource provider.
- Neutron bind được port.
- Glance/Cinder trả lời API ổn định.
- `nova-compute` nói chuyện được với libvirt/KVM.

Muốn debug Nova hiệu quả thì không chỉ xem riêng Nova. Cần đọc theo luồng build instance: API -> scheduler -> placement -> conductor -> compute -> neutron/glance/cinder.
