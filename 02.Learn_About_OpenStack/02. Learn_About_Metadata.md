# TÌM HIỂU VỀ METADATA SERVICE TRONG OPENSTACK 2026.1 GAZPACHO

Tài liệu này tìm hiểu về **Metadata Service** trong OpenStack phiên bản **2026.1 Gazpacho**, bao gồm khái niệm, các loại metadata, cấu trúc thành phần, luồng hoạt động và hướng dẫn cấu hình.

## I. METADATA SERVICE LÀ GÌ?

### 1. Khái niệm

**Metadata Service** là dịch vụ cho phép instance (VM) lấy thông tin cấu hình của chính nó ngay khi vừa boot, thông qua địa chỉ đặc biệt:

```text
http://169.254.169.254
```

Địa chỉ `169.254.169.254` là một **link-local address** (RFC 3927), không cần kết nối internet. Instance chỉ cần có IP trong dải mạng nội bộ là có thể gửi request đến địa chỉ này.

Mô hình này được OpenStack kế thừa từ **Amazon Web Services (AWS)** - nơi đầu tiên sử dụng `169.254.169.254` làm điểm truy cập metadata cho EC2 instance.

### 2. Vì sao cần Metadata Service?

Khi một VM vừa được boot lần đầu, nó chưa có bất kỳ thông tin cấu hình nào:

| Thông tin         | Trạng thái khi mới boot |
|-------------------|-------------------------|
| Hostname          | Chưa được set           |
| SSH Public Key    | Chưa được inject        |
| User account      | Chưa được tạo           |
| Script cấu hình   | Chưa được chạy          |
| Network info      | Chỉ có IP từ DHCP       |

Tuy nhiên, VM đã có:

- IP từ DHCP
- Default route

Lúc này, **cloud-init** sẽ tự động gọi đến `http://169.254.169.254` để lấy metadata và thực hiện cấu hình hệ thống.

### 3. Phân biệt Metadata Service và Cloud-init

Hai khái niệm này thường bị nhầm lẫn:

| Thành phần        | Vai trò                                         | Chạy ở đâu        |
|-------------------|-------------------------------------------------|-------------------|
| Metadata Service  | Cung cấp dữ liệu (server-side)                  | OpenStack backend |
| Cloud-init        | Đọc dữ liệu và cấu hình hệ thống (client-side)  | Bên trong VM      |

```text
Metadata Service = server cung cấp dữ liệu
Cloud-init       = client đọc và xử lý dữ liệu
```

Cloud-init chỉ là một **HTTP client** gọi đến Metadata Service để lấy thông tin cần thiết.

## II. CÁC LOẠI METADATA

Trong OpenStack 2026.1 Gazpacho, Metadata Service cung cấp 4 nhóm dữ liệu chính:

### 1. Instance Metadata (Meta-Data)

Thông tin mô tả bản thân instance, do Nova cung cấp:

| Trường              | Ý nghĩa                              |
|---------------------|--------------------------------------|
| `instance-id`       | UUID của instance                    |
| `hostname`          | Tên hostname                         |
| `local-ipv4`        | IP private của instance              |
| `public-ipv4`       | Floating IP (nếu có)                 |
| `public-keys`       | SSH public key đã inject             |
| `placement`         | AZ, region                           |
| `instance-type`     | Flavor name                          |

Ví dụ truy cập:

```bash
curl http://169.254.169.254/openstack/latest/meta_data.json
```

### 2. User Data

Dữ liệu tùy chỉnh do người dùng truyền vào khi tạo instance, thường là:

- Ansible playbook

#### Quy trình test user-data đúng

Điều kiện quan trọng: **metadata service phải hoạt động trước khi tạo VM**. `cloud-init` chỉ đọc user-data ở lần boot đầu tiên, nên nếu metadata lỗi rồi mới sửa lại thì VM cũ thường vẫn không tự apply password. Khi test lại, hãy xóa VM cũ và tạo VM mới.

Trên mô hình provider network không có router/L3 agent, cần kiểm tra DHCP agent đã bật metadata route:

```ini
# /etc/neutron/dhcp_agent.ini
[DEFAULT]
interface_driver = linuxbridge
dhcp_driver = neutron.agent.linux.dhcp.Dnsmasq
enable_isolated_metadata = true
force_metadata = true
```

Trên controller, kiểm tra Nova metadata API:

```bash
grep enabled_apis /etc/nova/nova.conf
ss -lntp | grep 8775
```

Kỳ vọng có:

```ini
[DEFAULT]
enabled_apis = osapi_compute,metadata
```

Tạo key pair và lấy public key trên controller/host trước khi tạo VM:

```bash
openstack keypair create mykey > /root/mykey.pem
chmod 600 /root/mykey.pem
ssh-keygen -y -f /root/mykey.pem
```

Nếu `mykey` đã tồn tại nhưng mất file `/root/mykey.pem`, OpenStack **không cho tải lại private key**. Cách sạch nhất là xóa keypair cũ rồi tạo lại:

```bash
openstack keypair delete mykey
rm -i /root/mykey.pem
openstack keypair create mykey > /root/mykey.pem
chmod 600 /root/mykey.pem
ssh-keygen -y -f /root/mykey.pem
```

Tạo file `/root/cloud-init.yaml`:

```bash
nano /root/cloud-init.yaml
```

Nội dung mẫu:

```yaml
#cloud-config
hostname: test-ubuntu

users:
  - default
  - name: tien9a
    sudo: ["ALL=(ALL) NOPASSWD:ALL"]
    groups: [sudo]
    shell: /bin/bash
    lock_passwd: false
    ssh_authorized_keys:
      - ssh-rsa AAAA... thay-bang-public-key-cua-mykey

chpasswd:
  list: |
    tien9a:Cloud2026
  expire: false

ssh_pwauth: true

packages:
  - nginx
  - curl

runcmd:
  - systemctl enable nginx
  - systemctl start nginx
```

Lưu ý:

- `Cloud2026` là mật khẩu plaintext của user `tien9a`. Nên tránh ký tự đặc biệt như `@` khi test qua console/VNC vì rất dễ lệch layout bàn phím.
- Mật khẩu trên chỉ áp dụng cho user `tien9a`. User mặc định của Ubuntu cloud image là `ubuntu` vẫn thường bị khóa password, nên `ubuntu` + `Cloud2026` sẽ báo sai.
- `ssh_authorized_keys` phải là **public key** lấy từ `ssh-keygen -y -f /root/mykey.pem`, không phải nội dung private key trong `/root/mykey.pem`.
- `ssh_pwauth: true` chỉ bật đăng nhập SSH bằng password sau khi `cloud-init` chạy thành công và restart/reload SSH trong VM.
- User-data chỉ được cloud-init xử lý ở lần boot đầu tiên của instance. Nếu sửa file rồi rebuild/reuse volume cũ, hãy tạo VM mới hoặc chạy `cloud-init clean --logs` trong image trước khi đóng gói lại.
- Không dùng CirrOS để test đoạn password này. CirrOS có user mặc định `cirros/gocubsgo`, không phải Ubuntu cloud-init workflow đầy đủ như ví dụ này.

Upload Ubuntu cloud image nếu chưa có:

```bash
curl -O https://cloud-images.ubuntu.com/jammy/current/jammy-server-cloudimg-amd64.img

openstack image create "ubuntu-22.04-server" \
  --file jammy-server-cloudimg-amd64.img \
  --disk-format qcow2 \
  --container-format bare \
  --public
```

Tạo flavor đủ RAM cho Ubuntu cloud image:

```bash
openstack flavor create --vcpus 1 --ram 1024 --disk 8 m1.ubuntu
```

Tạo VM mới và truyền user-data:

```bash
# Nếu đã tạo VM lỗi trước đó, xóa VM cũ rồi tạo lại để cloud-init chạy từ đầu:
openstack server delete test-ubuntu

openstack server create \
  --flavor m1.ubuntu \
  --image ubuntu-22.04-server \
  --nic net-id=$(openstack network show provider -f value -c id) \
  --security-group 19b14873-32d1-4e90-8600-6858bbf5aa90 \
  --key-name mykey \
  --user-data /root/cloud-init.yaml \
  test-ubuntu
```

Sau khi VM active và có IP, SSH bằng private key tương ứng:

```bash
ssh -i /root/mykey.pem tien9a@<VM_IP>

# Hoặc user mặc định của Ubuntu cloud image:
ssh -i /root/mykey.pem ubuntu@<VM_IP>
```

Nếu muốn kiểm tra đăng nhập bằng password:

```bash
ssh tien9a@<VM_IP>
# Password: Cloud2026
```

Nếu SSH vẫn không vào được, kiểm tra security group đã mở port 22:

```bash
openstack security group rule create --proto tcp --dst-port 22 <SECURITY_GROUP_ID_OR_NAME>
# Với ví dụ dùng security group default:
openstack security group rule create --proto tcp --dst-port 22 default
```

Nếu SSH bằng key vào được nhưng SSH bằng password báo sai mật khẩu, kiểm tra trong VM:

```bash
cloud-init status --long
sudo passwd -S tien9a
sudo grep -R "PasswordAuthentication" /etc/ssh/sshd_config /etc/ssh/sshd_config.d/
sudo grep -i "chpasswd\|set-passwords\|admin" /var/log/cloud-init.log /var/log/cloud-init-output.log
```

Nếu chưa SSH được bằng key, xem log console từ controller:

```bash
openstack console log show test-ubuntu | grep -i "cloud-init\|error\|failed\|tien9a"
```

## III. CẤU TRÚC CỦA METADATA SERVICE

Metadata Service trong OpenStack không phải một service đơn lẻ, mà là sự phối hợp của nhiều thành phần:

![OpenStack](./images/OpenStack_8.png)

### 1. nova-api-metadata

Là một **sub-service** của **nova-api**, chịu trách nhiệm chính trong việc phục vụ metadata cho instance.

**Vị trí:** Controller node  
**Port mặc định:** `8775`

Khi nhận request, `nova-api-metadata` sẽ:

1. Xác định instance dựa trên instance-id trong header
2. Truy vấn database lấy metadata của instance đó
3. Trả về dữ liệu JSON tương ứng

Trong `nova.conf`, có thể chạy `nova-api-metadata` tích hợp chung với `nova-api`:

```ini
[DEFAULT]
enabled_apis = osapi_compute,metadata
```

Hoặc chạy tách biệt thành một process riêng.

### 2. neutron-metadata-agent

`neutron-metadata-agent` là cầu nối giữa `neutron-ns-metadata-proxy` và `nova-api-metadata`.

**Vị trí:** Network node hoặc Controller node  
**Giao tiếp:** Unix domain socket (với proxy) và HTTP (với nova-api-metadata)

Nhiệm vụ của `neutron-metadata-agent`:

- Nhận request từ `neutron-ns-metadata-proxy`
- Xác định instance-id dựa trên IP và router-id hoặc network-id
- Thêm header `X-Instance-ID` và `X-Tenant-ID` vào request
- Forward request đến `nova-api-metadata`

File cấu hình: `/etc/neutron/metadata_agent.ini`

```ini
[DEFAULT]
nova_metadata_host = controller
nova_metadata_port = 8775
metadata_proxy_shared_secret = <SECRET>
```

### 3. neutron-ns-metadata-proxy

**neutron-ns-metadata-proxy** là một HTTP proxy chạy bên trong **network namespace** (của DHCP agent hoặc Router namespace).

**Vị trí:** Chạy trong **namespace**, trên network/controller node  
**Giao tiếp:**

- Nhận HTTP request từ instance (qua tap interface của namespace)
- Gửi request đến `neutron-metadata-agent` qua Unix domain socket

neutron-ns-metadata-proxy được tạo tự động bởi:

- **L3 agent** → tạo proxy trong router namespace
- **DHCP agent** → tạo proxy trong DHCP namespace (khi `force_metadata = True`)

## IV. CÁCH THỨC HOẠT ĐỘNG - FLOW CỦA METADATA

### 1. Luồng tổng quan

Khi instance gửi request đến `http://169.254.169.254`:

```text
1. Instance gửi HTTP GET đến 169.254.169.254
2. Request được routing đến neutron-ns-metadata-proxy (qua L3 agent hoặc DHCP agent)
3. neutron-ns-metadata-proxy forward qua Unix Domain Socket đến neutron-metadata-agent
4. neutron-metadata-agent xác định instance-id, thêm header, forward đến nova-api-metadata
5. nova-api-metadata truy vấn DB, trả về metadata
6. Dữ liệu truyền ngược về instance
```

### 2. Luồng qua L3 Agent

Khi network của instance có kết nối với router (L3 agent quản lý):

```text
Instance
  | HTTP GET 169.254.169.254:80
  |
  v (routing table: 169.254.169.254 via gateway 192.168.10.1)
Router namespace (qr-xxx interface)
  |
  v (iptables DNAT rule: 169.254.169.254:80 -> 127.0.0.1:9697)
neutron-ns-metadata-proxy (port 9697 trong router namespace)
  |
  v (Unix Domain Socket)
neutron-metadata-agent
  | Thêm header: X-Forwarded-For, X-Instance-ID, X-Tenant-ID
  | (xác định instance-id qua router-id + instance IP)
  v
nova-api-metadata (port 8775)
  |
  v (query DB)
Trả về metadata JSON
```

**Iptables rule trong router namespace:**

```bash
# Xem iptables rule trong router namespace
ip netns exec qrouter-<router-id> iptables -t nat -L -n

# Kết quả mẫu:
# REDIRECT  tcp  --  0.0.0.0/0  169.254.169.254  tcp dpt:80 redir ports 9697
```

### 3. Luồng qua DHCP Agent

Khi network chỉ có DHCP agent (không có router), hoặc cấu hình `force_metadata = True`:

```text
Instance
  | HTTP GET 169.254.169.254:80
  |
  v (DHCP agent đã cấu hình route: 169.254.169.254 via DHCP server IP)
DHCP namespace (ns-xxx interface)
  |
  v (neutron-ns-metadata-proxy lắng nghe trực tiếp trên 169.254.169.254:80)
neutron-ns-metadata-proxy (port 80 trong DHCP namespace)
  |
  v (Unix Domain Socket)
neutron-metadata-agent
  | Thêm header: X-Forwarded-For, X-Instance-ID, X-Tenant-ID
  | (xác định instance-id qua network-id + instance IP)
  v
nova-api-metadata (port 8775)
```

**Khác biệt giữa L3 agent và DHCP agent:**

| Điểm khác biệt     | L3 Agent                              | DHCP Agent                           |
|--------------------|---------------------------------------|--------------------------------------|
| Namespace          | Router namespace (`qrouter-xxx`)      | DHCP namespace (`qdhcp-xxx`)         |
| Routing            | iptables DNAT rule                    | Gán trực tiếp IP vào interface       |
| Xác định instance  | Dùng router-id + instance IP          | Dùng network-id + instance IP        |
| Yêu cầu            | Network phải có router                | Cần `force_metadata = True`          |

### 4. Cơ chế xác định Instance ID

Instance không biết UUID của chính nó khi gửi metadata request. `neutron-metadata-agent` thực hiện việc này:

**Khi dùng L3 Agent:**

```text
1. neutron-ns-metadata-proxy thêm: X-Forwarded-For (instance IP) + X-Instance-ID-Signature (router-id)
2. neutron-metadata-agent nhận request
3. Dùng router-id -> tìm tất cả subnet kết nối với router
4. Filter subnet chứa instance IP
5. Từ subnet -> tìm port có IP = instance IP
6. Từ port -> lấy instance UUID (device_id)
7. Thêm header X-Instance-ID vào request gửi đến nova-api-metadata
```

**Khi dùng DHCP Agent:**

```text
1. neutron-ns-metadata-proxy thêm: X-Forwarded-For (instance IP) + X-Instance-ID-Signature (network-id)
2. neutron-metadata-agent nhận request
3. Dùng network-id -> tìm tất cả subnet trong network
4. Filter subnet chứa instance IP
5. Từ subnet -> tìm port có IP = instance IP
6. Từ port -> lấy instance UUID (device_id)
7. Thêm header X-Instance-ID vào request gửi đến nova-api-metadata
```

## V. HƯỚNG DẪN CẤU HÌNH METADATA SERVICE

### 1. Cấu hình Nova

Trên **Controller node**, chỉnh sửa `/etc/nova/nova.conf`:

```ini
[DEFAULT]
# Bật cả nova-api và metadata service
enabled_apis = osapi_compute,metadata

[api]
# Shared secret với neutron-metadata-agent (phải khớp)
metadata_proxy_shared_secret = YOUR_SHARED_SECRET

[neutron]
# Cho phép neutron gửi metadata request
service_metadata_proxy = true
metadata_proxy_shared_secret = YOUR_SHARED_SECRET
```

Khởi động lại service:

```bash
systemctl restart nova-api
```

### 2. Cấu hình Neutron Metadata Agent

Trên **Network/Controller node**, chỉnh sửa `/etc/neutron/metadata_agent.ini`:

```ini
[DEFAULT]
# Địa chỉ nova-api-metadata
nova_metadata_host = controller
nova_metadata_port = 8775
nova_metadata_protocol = http

# Shared secret phải khớp với nova.conf
metadata_proxy_shared_secret = YOUR_SHARED_SECRET

# Socket file để kết nối với neutron-ns-metadata-proxy
metadata_proxy_socket = /var/lib/neutron/metadata_proxy

# Log
debug = False
log_dir = /var/log/neutron
log_file = neutron-metadata-agent.log
```

Khởi động lại service:

```bash
systemctl restart neutron-metadata-agent
```

### 3. Cấu hình L3 Agent (dùng với Router)

Trên **Network/Controller node**, chỉnh sửa `/etc/neutron/l3_agent.ini`:

```ini
[DEFAULT]
interface_driver = linuxbridge
# Hoặc nếu dùng OVS:
# interface_driver = openvswitch

# Bật metadata proxy
metadata_port = 9697
```

Khởi động lại service:

```bash
systemctl restart neutron-l3-agent
```

### 4. Cấu hình DHCP Agent (dùng khi không có Router)

Trên **Network/Controller node**, chỉnh sửa `/etc/neutron/dhcp_agent.ini`:

```ini
[DEFAULT]
interface_driver = linuxbridge
# Hoặc nếu dùng OVS:
# interface_driver = openvswitch

dhcp_driver = neutron.agent.linux.dhcp.Dnsmasq

# Bắt buộc bật để metadata hoạt động khi không có router
force_metadata = True

# Bật metadata proxy cho DHCP namespace
enable_metadata_network = True
```

Khởi động lại service:

```bash
systemctl restart neutron-dhcp-agent
```

### 5. Cấu hình Vendor Data (tùy chọn)

Nếu cần cung cấp vendor data tĩnh, tạo file `/etc/nova/vendor_data.json`:

```json
{
  "cloud_name": "My Private Cloud",
  "support_email": "support@example.com",
  "monitoring_endpoint": "http://monitor.internal:9090"
}
```

Khai báo trong `nova.conf`:

```ini
[api]
vendordata_jsonfile_path = /etc/nova/vendor_data.json
vendordata_providers = StaticJSON
```

Nếu dùng Dynamic Vendor Data (gọi external API):

```ini
[api]
vendordata_providers = StaticJSON,DynamicJSON
vendordata_dynamic_targets = myservice@http://vendor-api.internal:9090/v1/
vendordata_dynamic_connect_timeout = 5
vendordata_dynamic_read_timeout = 5
```

## VI. KIỂM TRA VÀ DEBUG

```bash

# Kiểm tra process trong DHCP namespace
ip netns exec qdhcp-<network-id> ps aux | grep metadata
```

ip netns exec qrouter-<router-id> iptables -t nat -L -n | grep 169.254

### 3. Kiểm tra metadata từ trong VM

```bash
# Lấy danh sách version API
curl http://169.254.169.254/openstack/

# Lấy metadata JSON
curl http://169.254.169.254/openstack/latest/meta_data.json

# Lấy user-data
curl http://169.254.169.254/openstack/latest/user_data

# Lấy network data
curl http://169.254.169.254/openstack/latest/network_data.json
```

### 4. Kiểm tra log

```bash
# Log nova-api (metadata)
tail -f /var/log/nova/nova-api.log | grep metadata

# Log neutron-metadata-agent
tail -f /var/log/neutron/neutron-metadata-agent.log

# Log neutron-l3-agent
tail -f /var/log/neutron/neutron-l3-agent.log

# Log neutron-dhcp-agent
tail -f /var/log/neutron/neutron-dhcp-agent.log
```

### 5. Các lỗi thường gặp và cách xử lý

| Lỗi                                        | Nguyên nhân                                    | Cách xử lý                                    |
|--------------------------------------------|------------------------------------------------|-----------------------------------------------|
| VM không lấy được metadata                 | neutron-ns-metadata-proxy chưa chạy           | Kiểm tra L3/DHCP agent, restart service       |
| `Connection refused` tới 169.254.169.254   | Chưa có route hoặc proxy chưa bật             | Kiểm tra iptables rule, bật `force_metadata`  |
| Hostname không được set                    | cloud-init không lấy được metadata            | Kiểm tra cloud-init log trong VM              |
| `Shared secret mismatch`                   | Secret trong nova.conf và metadata_agent.ini khác nhau | Đồng bộ lại secret, restart cả hai service   |
| Metadata trả về 500                        | nova-api-metadata không kết nối được DB       | Kiểm tra nova-api log                         |

## VII. METADATA TRONG MÔI TRƯỜNG OVN (OpenStack 2026.1)

Từ OpenStack 2024.1 trở đi, nhiều deployment chuyển từ OVS/L3-agent truyền thống sang **OVN (Open Virtual Network)**. Trong OVN, cơ chế metadata có một số thay đổi:

### 1. OVN Metadata Agent

Trong OVN, thay vì dùng `neutron-ns-metadata-proxy` bên trong namespace, OVN dùng **ovn-metadata-agent** chạy trực tiếp trên **compute node**:

```text
Instance
  | HTTP GET 169.254.169.254
  v
OVN logical switch port (localnet/geneve)
  v
ovn-metadata-agent (compute node, port 9697)
  |
  v (Unix Domain Socket)
neutron-metadata-agent
  v
nova-api-metadata
```

### 2. Cấu hình OVN Metadata Agent

Trên **compute node**, `/etc/neutron/plugins/ml2/ovn_agent.ini` hoặc `/etc/neutron/neutron.conf`:

```ini
[ovn]
ovn_nb_connection = tcp:controller:6641
ovn_sb_connection = tcp:controller:6642

[agent]
root_helper = sudo neutron-rootwrap /etc/neutron/rootwrap.conf
```

File `/etc/neutron/neutron_ovn_metadata_agent.ini`:

```ini
[DEFAULT]
nova_metadata_host = controller
nova_metadata_port = 8775
metadata_proxy_shared_secret = YOUR_SHARED_SECRET
ovn_sb_connection = tcp:controller:6642
```

Khởi động service:

```bash
systemctl enable neutron-ovn-metadata-agent
systemctl start neutron-ovn-metadata-agent
```

## VIII. KẾT LUẬN

**Metadata Service** là một thành phần cốt lõi của OpenStack, đảm bảo instance có thể tự cấu hình sau khi boot thông qua `cloud-init`.

Tổng kết các điểm quan trọng:

| Chủ đề                  | Tóm tắt                                                             |
|-------------------------|---------------------------------------------------------------------|
| Địa chỉ truy cập        | `http://169.254.169.254` (link-local, không cần internet)          |
| Các loại dữ liệu        | Meta-Data, User-Data, Vendor-Data, Network-Data                    |
| Thành phần chính        | nova-api-metadata, neutron-metadata-agent, neutron-ns-metadata-proxy |
| Hai luồng hoạt động     | Qua L3 Agent (iptables DNAT) hoặc DHCP Agent (force_metadata)     |
| Môi trường OVN          | Dùng ovn-metadata-agent chạy trên compute node                    |
| Shared secret           | Phải khớp giữa nova.conf và metadata_agent.ini                    |
