# DEPLOY OPENSTACK HA 3 NODE CONTROLLER ON OPENSTACK

## I. ĐẶC ĐIỂM CỦA OPSTACK HA

### 1. Đặc điểm của HA trong OPS

**HA (High Availability)** = Tính sẵn sàng cao

Mục tiêu của HA với OPS:

#### **Đảm bảo không downtime (hoặc downtime tối thiểu)**

- Khi một node (controller, network, compute…) bị lỗi → hệ thống vẫn chạy

- Người dùng vẫn:

  - Tạo VM
  - Truy cập VM
  - Sử dụng dịch vụ bình thường

=> Ví dụ: `controller-1` chết → `controller-2/3` tự động tiếp quản

#### **Tự động failover (chuyển đổi khi có lỗi)**

- HA giúp:

  - Phát hiện node/service bị lỗi
  - Tự động chuyển sang node khác (failover)
  - Không cần can thiệp thủ công

=> Thường dùng:

- `Pacemaker` / `Corosync`
- `HAProxy` + `Keepalived` (VIP)

#### **Cân bằng tải (Load Balancing)**

- Nhiều node controller cùng xử lý request

- Tránh quá tải 1 node

=> Ví dụ:

- `API` (Nova, Keystone, Neutron) được load balance qua `HAProxy`

#### **Tăng độ tin cậy (Reliability)**

- Tránh single point of failure (SPOF)

Các thành phần cần HA:

- Controller nodes (`API`, scheduler…)
- Database (`MariaDB`; `Galera` cluster)
- Message Queue (`RabbitMQ` cluster)
- Network services (`L3 agent`, `DHCP`agent…)

#### Bảo vệ dữ liệu & trạng thái hệ thống

DB cluster đảm bảo:

- Không mất dữ liệu khi 1 node chết
- Dữ liệu được replicate giữa các node

#### Đảm bảo SLA (Service Level Agreement)

HA giúp hệ thống:

- Đạt uptime cao (99.9% → 99.99%)
- Phù hợp môi trường production

### 3. Yêu cầu Từ OpenStack hạ tầng (Cụm bên ngoài )

Trước khi tạo VM cho cụm HA phải đảm bảo:

#### 3.1 Nested Virtualization

Trên compute node của OpenStack hạ tầng:

```bash
cat /sys/module/kvm_intel/parameters/nested

# Phải = `Y`
```

Nếu không → cụm HA bên trong sẽ không tạo được VM.

#### 3.2 Flavor cho VM của cụm HA

Tất cả VM controller/compute/storage phải:

- CPU mode: `host-passthrough`
- Expose `VMX`/`SVM`
- RAM đủ lớn
- Disk nên dùng volume (không dùng `ephemeral`)

#### 3.3 Network yêu cầu

- Cho phép `promiscuous mode`
- **Tắt port security** hoặc cấu hình `allowed-address-pairs`
- Hỗ trợ `Trunk` (nếu dùng VLAN)
- Kiểm tra `MTU` (khuyên dùng 1450 cho tenant network)

### 4. Yêu cầu hạ tầng chung trên các node & Service cần có trên từng node

#### 4.1 Cấu hình chung trên tất cả các node (Controller/Compute/Storage)

**OS**:

- Ubuntu 24.04 LTS (khuyến nghị)
- Cấu hình static IP
- Hostname chuẩn
- `/etc/hosts` đầy đủ toàn cluster

Ví dụ:

```bash
192.168.70.81  controller 1
192.162.70.83  controller 2
192.162.70.85  controller 3
```

**System config** bắt buộc:

- Disable swap
- Enable NTP (chrony)
- `net.ipv4.ip_forward = 1` (compute + network)
- `net.bridge.bridge-nf-call-iptables` = 1
- Tắt firewall hoặc mở port đầy đủ
- Cài gói cơ bản: `curl`, `wget`, `vim`, `net-tools`

**Network** theo layout:

| Network    | CIDR              | Dùng cho             |
| ---------- | ----------------- | -------------------- |
| MGMT + API | `10.10.10.0`/24   | Service nội bộ       |
| Tenant     | `10.10.20.0`/24   | VXLAN                |

### 5. Những khó khăn & lưu ý khi cài ManualInstall (so với các cách khác Automation or use Kolla-Ansible)

#### 5.1 HA manual config rất phức tạp

- Sai 1 dòng cấu hình `Galera` → **cluster split-brain**
- Sai cấu hình `Rabbit` → **message queue** không sync
- Sai endpoint → service không register

=> Manual = Rất dễ lệch config giữa các controller

Automation đảm bảo:

- File cấu hình giống nhau
- Restart theo đúng thứ tự
- Sync database migration đúng cách

=> Bản chất của Automation đã chạy các file bash scripts theo thứ tự

#### 5.2 Nested tăng độ khó

Ta đang chạy: OpenStack trên 1 OpenStack hạ tầng khác.

- Nested `KVM`
- Nested `VXLAN`
- Nested routing
- Nested security group

**Manual** cực dễ vỡ ở:

- `MTU` sai
- `iptables rule` xung đột
- `Bridge` mapping sai
- `DVR` không hoạt động do port security

Automation (Kolla/OpenStack-Ansible) xử lý:

- `Bridge` mapping tự động
- `ML2` config chuẩn
- `Sync neutron agent` đồng bộ

#### 5.3 HA yêu cầu cấu hình đồng nhất 100%

Ví dụ:

`nova.conf` trên 3 controller phải giống nhau 99%.

Chỉ cần khác:

```bash
transport_url
memcached_servers
connection
```

→ Service không sync.

=> `Manual` rất dễ sai.
=> `Automation` dùng template → đảm bảo đồng nhất.

#### 5.4 Database migration cực nguy hiểm khi manual

Trong HA:

Chỉ 1 node được chạy:

```bash
nova-manage db sync
```

Nếu **chạy nhầm nhiều node** → có thể **corrupt schema**.

`Automation` kiểm soát:

- Node nào chạy migration
- Chạy đúng thứ tự
- Lock đúng service

#### 5.5 Khi lỗi xảy ra, manual rất khó rollback

Ví dụ:

- `Galera` mất quorum
- `RabbitMQ` mất cluster
- `Keystone` token lỗi
- `Neutron` DVR không route

-> `Manual` sửa = mò từng node.

-> `Automation`: `Re-run playbook` là `self-heal`.

#### 5.6 NGUYÊN TẮC KHI CÀI MANUAL HA

- Chỉ chạy DB migration trên 1 controller duy nhất
- Mọi file config giữa các controller phải giống nhau 100%
- Tất cả endpoint phải trỏ về `VIP`
- `Ceph` phải chạy ổn định trước khi cài `Glance`/`Cinder`
- `Nested KVM` phải `OK` trước khi cài `nova-compute`.
- Test từng `PHASE` một khi được mới sang `PHASE` tiếp

### `Bước 7`: Cài + Config Keepalived + HA Proxy

`Lưu ý`: Nhớ cái cấu hình `safe_to_bootstrap=1` sau mỗi lần snapshot

Trên 3 Node Controller ta cấu hình kiến trúc HaProxy với đường VIP để đáp ứng điều kiện sau:

- Cân bằng tải API giữa 3 controller
- Frontend 1 VIP (VD: 10.10.10.100)
- Backend: controller1, controller2, controller3
- Tất cả Service OpenStack sẽ cấu hình vào VIP này thay vì từng Controller
- `Keepalived` **tạo và quản lí** `VIP`:

  - 1 Node Master
  - 2 Node Backup
- `HAProxy` làm LoadBalance cho các services (MariaDB, Keystone, RabbitMQ…)

Đầu tiên, ta cài `keepalived`+ `HAProxy`:

- Trên cả 3 node Controller:

```bash
apt install keepalived -y
apt install haproxy -y
```

- Enable `keepalived`+ `HAProxy`:

```bash
systemctl enable keepalived
systemctl enable haproxy
# ! Không được start service
```

![OpenStack_HA_01](./images/Deploy_OpenStack_HA_44.png)

Tiếp theo cấu hình `HAProxy`.Trên 3 Node:

```bash
#Lệnh này nói với Linux: "Cứ cho HAProxy chạy đi, IP VIP chưa có trên máy này nhưng lát nữa sẽ có
echo "net.ipv4.ip_nonlocal_bind = 1" >> /etc/sysctl.conf
sysctl -p

# Sửa file
nano /etc/haproxy/haproxy.cfg

# Xoá config cũ và thêm phần này vào cuối file:
global
    log /dev/log local0
    maxconn 4096
    daemon
    stats socket /run/haproxy/admin.sock mode 660 level admin

defaults
    retries 3
    option redispatch
    log global
    mode tcp
    option tcplog
    timeout connect 10s
    timeout client  1m
    timeout server  1m

# MariaDB - Lắng nghe trên VIP External
frontend galera_front
    bind 192.168.70.100:3306
    default_backend galera_back

backend galera_back                
    balance leastconn
    option tcp-check
    # Chuyển tiếp về IP nội bộ của 3 node
    server controller1 10.10.10.11:3306 check
    server controller2 10.10.10.12:3306 check backup 
    server controller3 10.10.10.13:3306 check backup

# RabbitMQ - Lắng nghe trên VIP External
frontend rabbit_front
    bind 192.168.70.100:5672
    default_backend rabbit_back

backend rabbit_back
    balance leastconn
    option tcp-check
    # Chuyển tiếp về IP nội bộ của 3 node
    server controller1 10.10.10.11:5672 check inter 3s rise 2 fall 3
    server controller2 10.10.10.12:5672 check inter 3s rise 2 fall 3
    server controller3 10.10.10.13:5672 check inter 3s rise 2 fall 3

# Về sau khi cài Keystone, Nova, Horizon, bạn cũng viết tiếp block frontend/backend tương tự, ví dụ: Horizon thì bind 192.168.70.100:80, trỏ về 10.10.10.x:80

# Qua Config VIP rồi mới restart thì HAProxy nó nhận VIP
```

Rồi sau đó, ta cấu hình `keepalived`

- Cấu hình Controller 1 (`MASTER NODE`):

```bash
nano /etc/keepalived/keepalived.conf

# Cấu hình
global_defs {
    script_user root
    enable_script_security
}

vrrp_script chk_haproxy {
    script "/usr/bin/pgrep haproxy"  # Keepalived phiên bản mới rất khắt khe về việc chạy script kiểm tra (chk_haproxy)
    interval 2
    weight -40              # Nếu HaProxy Master lỗi sẽ trừ priority đi 40 và trao VIP cho node Backup
}

vrrp_instance VN_1 {        # Tạo 1 instance vrrp có tên VN_1
    state MASTER            # Node Master để giữ VIP
    interface eth2          # VIP gắn vào interface này
    virtual_router_id 51    # ID cụm vrrp
    priority 150            # Độ ưu tiên (cao nhất là node master)
    advert_int 1            # Time gửi gói vrrp

    authentication {        # Cơ chế bảo mật giữa các node
        auth_type PASS      # Kiểu xác thực Pass
        auth_pass Tien@123  # Mật khẩu dùng giữa các node
    }
    virtual_ipaddress {     # Đây là VIP
        192.168.70.100/24   # Keepalived tự add/remove khi failover
    }

    track_script {
    chk_haproxy
    } 
}

# Check cấu hình haproxy đúng chưa
haproxy -c -f /etc/haproxy/haproxy.cfg

# nếu hiện valid là OKE
```

- Cấu hình Controller 2,3 (`BACK NODE`)

```bash
# Đối với Controller 2 đổi 2 dòng sau và giữ nguyên all
state BACKUP
priority 120
nopreempt      # Thêm dưới cấu hình vrrp_instance

# Đối với Controller 3 đổi 2 dòng sau và giữ nguyên all
state BACKUP
priority 100
nopreempt
```

Sau đó Restart với thứ tự đúng(Làm trên NODE MASTER trước rồi đến node piority thấp hơn !):

- Restart `keepalived`:

```bash
systemctl restart keepalived
```

#### `Bước 9.4`: Debug lỗi `DBConnectionError`

**Nguyên nhân gây lỗi**:

Trong chuỗi kết nối Database: `mysql+pymysql://keystone:Tien@123@10.10.10.100/keystone`

Hệ thống sẽ đi tìm ký tự `@` để phân tách giữa **Cụm User:Pass** và **Cụm Host (IP)**.

Vì mật khẩu của bạn là `Tien@123` (có dấu @), nên Python bị "lú". Nó tưởng user là `keystone`, pass là `Tien`, còn **Host/Server** là cái cụm còn lại: `123@10.10.10.100`.

Tất nhiên là không có cái máy chủ nào tên là `123@10.10.10.100` cả, nên nó báo lỗi `Name or service not known`.

**Cách Fix**:

`Cách 1`: **Mã hóa ký tự `@` (Khuyên dùng)**

Bạn không cần đổi pass, chỉ cần viết lại cái dấu `@` trong mật khẩu thành định dạng URL Encoding là `%%%%40`.

Mở file `/etc/keystone/keystone.conf`, sửa dòng connection thành:


Trên `NodeController1`:

```bash
keystone-manage fernet_setup --keystone-user keystone --keystone-group keystone
```

`LƯU Ý QUAN TRỌNG`: Bây giờ bạn phải copy toàn bộ thư mục `/etc/keystone/fernet-keys/` và `/etc/keystone/credential-keys/` từ `Node 1` sang `Node 2` và `Node 3`. Nếu không, khi bạn truy cập qua `VIP`, nếu request rơi vào `Node 2/3`, nó sẽ không giải mã được token và báo lỗi `500` hoặc `401`. Và nhớ phân quyền trên khi copy sang Node 2,3 để cho có thể truy cập file để lấy **key**

Vẫn trên `Node1`:

```bash
# Copy từ Node 1 sang Node 2
scp -r /etc/keystone/fernet-keys root@controller2:/etc/keystone/
scp -r /etc/keystone/credential-keys root@controller2:/etc/keystone/
# Tương tự cho controller3
scp -r /etc/keystone/fernet-keys root@controller3:/etc/keystone/
scp -r /etc/keystone/credential-keys root@controller3:/etc/keystone/
```
