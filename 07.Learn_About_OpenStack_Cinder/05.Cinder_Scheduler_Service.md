## 1. Tổng quan về cinder-scheduler

`cinder-scheduler` là service chịu trách nhiệm **chọn backend storage phù hợp nhất** để xử lý các yêu cầu của Cinder, đặc biệt là:

- Tạo volume mới.
- Tạo group volume.
- Retype volume sang volume type khác.
- Migrate volume sang backend khác.
- Manage existing volume/snapshot.
- Validate capacity khi tạo snapshot hoặc extend volume trong một số luồng.
- Chọn backup host trong các trường hợp backup cần đi qua scheduler.

Trong OpenStack Cinder, `cinder-api` không tự quyết định volume sẽ nằm ở backend nào. API nhận request, validate, ghi metadata vào database, sau đó gửi RPC message tới `cinder-scheduler`. Scheduler lấy thông tin request, đối chiếu với trạng thái các backend mà `cinder-volume` đã report, rồi chọn ra backend/pool phù hợp. Sau đó request được chuyển tiếp tới `cinder-volume` tương ứng để driver storage thực thi thao tác thật.

### 1.1. Vì sao cần Scheduler?

Trong môi trường production, một cloud thường có nhiều loại storage:

- Ceph RBD SSD cho workload hiệu năng cao.
- Ceph RBD HDD cho workload dung lượng lớn.
- LVM/iSCSI cho lab hoặc local storage.
- NFS, NetApp, Dell PowerStore, Pure Storage, Hitachi, IBM Storage Virtualize, VAST Data, v.v.

Scheduler giúp:

- Tự động chọn backend còn đủ dung lượng.
- Tôn trọng `availability_zone`.
- Tôn trọng `volume_type` và `extra_specs`.
- Tránh backend đã thử và thất bại trong cùng request.
- Cân bằng tải theo dung lượng trống, số volume, capacity đã cấp phát hoặc hàm đánh giá tùy chỉnh.
- Tách logic ra quyết định khỏi API và driver storage.

### 1.2. Scheduler không làm gì?

`cinder-scheduler` **không trực tiếp tạo volume vật lý**. Nó không gọi Ceph, LVM, NetApp hay iSCSI target. Các thao tác thật do `cinder-volume` và volume driver xử lý.

Scheduler cũng không thay thế quota. Quota thường được kiểm tra ở API trước khi request đi tới scheduler. Scheduler chỉ kiểm tra khả năng backend có thể nhận workload hay không.

## 2. Request đi qua Scheduler chứa những gì?

Một request scheduling thường có:

- Volume ID.
- Size.
- Volume type ID.
- Extra specs của volume type.
- Availability zone được yêu cầu.
- Snapshot/source volume/image/backup nếu tạo từ nguồn có sẵn.
- Retry info nếu request đã thử backend khác trước đó.
- Project/user context.

## 3. Khi nào volume không cần Scheduler?

Không phải mọi thao tác đều cần chọn backend mới. Ví dụ:

- Delete volume: đã biết volume nằm ở backend nào.
- Attach volume: thường gửi tới `cinder-volume` đang quản lý volume đó.
- Detach volume: tương tự attach.

Scheduler chủ yếu xuất hiện khi cần **chọn nơi đặt tài nguyên** hoặc cần xác minh backend đích.

## 4. Các thành phần nội bộ của Scheduler

Trong Cinder 28.x, các module chính liên quan tới scheduler gồm:

| Module/Class | Vai trò |
| ------------ | ------- |
| `cinder.scheduler.manager.SchedulerManager` | Service manager nhận RPC từ API/volume, gọi scheduler driver. |
| `cinder.scheduler.rpcapi.SchedulerAPI` | Client-side RPC API dùng để gửi request tới `cinder-scheduler`. |
| `cinder.scheduler.filter_scheduler.FilterScheduler` | Scheduler driver mặc định, thực hiện filter và weigh backend. |
| `cinder.scheduler.host_manager.HostManager` | Quản lý cache trạng thái backend/pool và capability do `cinder-volume` report. |
| `BackendState` / `PoolState` | Đại diện trạng thái backend hoặc pool: capacity, allocated, protocol, capability, AZ... |
| `cinder.scheduler.filters.*` | Các filter loại backend không phù hợp. |
| `cinder.scheduler.weights.*` | Các weigher chấm điểm backend còn lại. |

### 4.1. SchedulerManager

`SchedulerManager` là phần service runtime của `cinder-scheduler`. Nó nhận các RPC method như:

- `create_volume`
- `create_group`
- `create_snapshot`
- `extend_volume`
- `migrate_volume`
- `retype`
- `manage_existing`
- `manage_existing_snapshot`
- `create_backup`
- `get_pools`
- `update_service_capabilities`
- `notify_service_capabilities`

Trong Cinder latest, Scheduler RPC API version đang là `3.12`. Điều này quan trọng khi rolling upgrade, vì Cinder có cơ chế version cap RPC để các service phiên bản khác nhau vẫn nói chuyện được trong giai đoạn nâng cấp.

### 4.2. FilterScheduler

`FilterScheduler` là scheduler driver mặc định:

```ini
[DEFAULT]
scheduler_driver = cinder.scheduler.filter_scheduler.FilterScheduler
```

Driver này làm 2 bước:

1. **Filtering**: loại backend không thỏa điều kiện.
2. **Weighing**: chấm điểm backend còn lại và chọn backend tốt nhất.

### 4.3. HostManager

`HostManager` giữ trạng thái các backend mà scheduler biết. Nó nhận thông tin từ `cinder-volume` qua RPC capability update.

Backend report thường có các thông tin:

```text
volume_backend_name
vendor_name
driver_version
storage_protocol
pools:
  - pool_name
    total_capacity_gb
    free_capacity_gb
    allocated_capacity_gb
    provisioned_capacity_gb
    reserved_percentage
    max_over_subscription_ratio
    thin_provisioning_support
    thick_provisioning_support
    QoS_support
```

Với backend có nhiều pool, scheduler chọn tới mức `host@backend#pool`, không chỉ chọn host chung.

## 5. Dữ liệu Scheduler sử dụng để ra quyết định

Scheduler không tự đo storage. Nó dựa vào dữ liệu được `cinder-volume` và driver report.

### 5.1. Dữ liệu từ request

| Dữ liệu | Ví dụ | Tác dụng |
| ------- | ----- | -------- |
| `size` | `100` | CapacityFilter kiểm tra đủ dung lượng hay không. |
| `volume_type` | `ceph-ssd` | CapabilitiesFilter so khớp extra specs. |
| `availability_zone` | `az1` | AvailabilityZoneFilter chọn backend đúng AZ. |
| `source_volid` | volume nguồn | Same/DifferentBackendFilter, retype/migration. |
| `snapshot_id` | snapshot nguồn | Scheduler có thể cần kiểm tra backend/capacity. |
| `metadata` | key/value user đặt | Có thể dùng trong custom filter function. |
| `qos_specs` | IOPS, bandwidth | Có thể dùng trong filter/goodness function. |

### 5.2. Dữ liệu từ backend

| Dữ liệu | Ý nghĩa |
| ------- | ------- |
| `total_capacity_gb` | Tổng capacity backend/pool report. |
| `free_capacity_gb` | Dung lượng trống thực hoặc logic do driver report. |
| `allocated_capacity_gb` | Dung lượng đã cấp phát. |
| `provisioned_capacity_gb` | Dung lượng đã provision trong thin provisioning. |
| `reserved_percentage` | Phần trăm capacity giữ lại, không dùng để schedule. |
| `max_over_subscription_ratio` | Tỷ lệ oversubscription khi thin provisioning. |
| `thin_provisioning_support` | Backend có hỗ trợ thin provisioning hay không. |
| `thick_provisioning_support` | Backend có hỗ trợ thick provisioning hay không. |
| `storage_protocol` | `iSCSI`, `FC`, `RBD`, `NFS`, `NVMeOF`... |
| `volume_backend_name` | Tên backend dùng để map với volume type. |
| `backend_availability_zone` | AZ riêng của backend nếu cấu hình. |

### 5.3. Backend ID trong Cinder

Khi dùng multi-backend, service name thường có dạng:

```text
host@backend
host@backend#pool
```

Ví dụ:

```text
controller01@ceph-ssd#volumes-ssd
controller01@ceph-hdd#volumes-hdd
storage01@lvm#LVM
```

Ý nghĩa:

- `controller01` hoặc `storage01`: host chạy `cinder-volume`.
- `ceph-ssd`, `ceph-hdd`, `lvm`: backend section trong `cinder.conf`.
- `volumes-ssd`, `volumes-hdd`, `LVM`: pool do driver report.

## 6. FilterScheduler: cơ chế Filter và Weigher

FilterScheduler chạy theo thứ tự:

```text
Danh sách backend active
        |
        v
Chạy filter 1 -> loại backend không phù hợp
        |
        v
Chạy filter 2 -> tiếp tục loại
        |
        v
Chạy filter N
        |
        v
Danh sách backend hợp lệ
        |
        v
Chạy weigher -> tính điểm
        |
        v
Chọn backend/pool điểm cao nhất
```

### 6.1. Filter là gì?

Filter là điều kiện **pass/fail**. Backend chỉ cần fail một filter là bị loại.

Ví dụ:

- Backend sai AZ -> fail `AvailabilityZoneFilter`.
- Backend không đủ capacity -> fail `CapacityFilter`.
- Backend không match `volume_backend_name` trong volume type -> fail `CapabilitiesFilter`.

### 6.2. Weigher là gì?

Weigher dùng sau filter. Khi nhiều backend đều pass, weigher tính điểm để chọn backend tốt nhất.

Ví dụ:

- `CapacityWeigher`: ưu tiên backend nhiều free capacity hơn hoặc stack volume vào backend ít free hơn tùy multiplier.
- `VolumeNumberWeigher`: ưu tiên backend có ít volume hơn hoặc nhiều volume hơn tùy multiplier.
- `GoodnessWeigher`: dùng hàm đánh giá do admin tự cấu hình.

### 6.3. Vì sao thứ tự Filter quan trọng?

Filter chạy tuần tự, backend bị loại sớm sẽ không đi tiếp. Nên đặt filter bắt buộc và rẻ trước:

```ini
scheduler_default_filters = AvailabilityZoneFilter,CapacityFilter,CapabilitiesFilter
```

Với custom policy, có thể thêm:

```ini
scheduler_default_filters = AvailabilityZoneFilter,CapacityFilter,CapabilitiesFilter,DriverFilter
```

Không nên thêm filter tùy chỉnh khi chưa hiểu rõ dữ liệu backend report, vì rất dễ gây lỗi `No valid host was found`.

## 7. Các Scheduler Filter quan trọng

Cinder 28.x vẫn dùng nhóm filter chính sau.

### 7.1. AvailabilityZoneFilter

Lọc backend theo Availability Zone.

Ví dụ request:

```bash
openstack volume create --size 10 --availability-zone az-storage-1 my-vol
```

Backend chỉ pass nếu:

- Backend thuộc `az-storage-1`, hoặc
- cấu hình fallback AZ cho phép fallback.

Cấu hình liên quan:

```ini
[DEFAULT]
storage_availability_zone = nova
default_availability_zone = nova
allow_availability_zone_fallback = false

[ceph-ssd]
backend_availability_zone = az-storage-1
```

Lưu ý:

- `storage_availability_zone` là AZ mặc định của node/backend.
- `backend_availability_zone` có thể override theo từng backend.
- `allow_availability_zone_fallback = false` là an toàn hơn trong production vì request sai AZ sẽ fail rõ ràng.

### 7.2. CapacityFilter

Kiểm tra backend có đủ capacity để tạo volume hay không.

CapacityFilter xét:

- `free_capacity_gb`
- `reserved_percentage`
- `max_over_subscription_ratio`
- thin/thick provisioning
- size volume request

Với thick provisioning, scheduler thường dựa vào free capacity thực tế sau khi trừ reserved capacity.

Với thin provisioning, scheduler xét virtual free capacity:

```text
virtual_free = total_capacity_gb * max_over_subscription_ratio - provisioned_capacity_gb
```

Nếu backend không đủ capacity hợp lệ, volume sẽ fail với lỗi thường gặp:

```text
No valid host was found. There are not enough hosts available.
```

### 7.3. CapabilitiesFilter

`CapabilitiesFilter` so khớp extra specs của volume type với capability backend.

Ví dụ volume type:

```bash
openstack volume type create ceph-ssd
openstack volume type set --property volume_backend_name=Ceph-SSD ceph-ssd
```

Backend:

```ini
[ceph-ssd]
volume_backend_name = Ceph-SSD
```

Nếu extra spec yêu cầu `volume_backend_name=Ceph-SSD` nhưng backend report `Ceph_SSD` hoặc `ceph-ssd`, scheduler sẽ loại backend vì không match chính xác.

Đây là nguyên nhân rất phổ biến của lỗi `No valid host`.

### 7.4. DriverFilter

`DriverFilter` dùng `filter_function` do admin định nghĩa trong backend section.

Ví dụ:

```ini
[DEFAULT]
scheduler_default_filters = AvailabilityZoneFilter,CapacityFilter,CapabilitiesFilter,DriverFilter

[lvm-small]
filter_function = "volume.size < 100"

[lvm-large]
filter_function = "volume.size >= 100"
```

Khi request volume 50 GB, `lvm-small` pass, `lvm-large` fail.

Khi request volume 500 GB, `lvm-large` pass, `lvm-small` fail.

### 7.5. JsonFilter

`JsonFilter` cho phép dùng query hint dạng JSON để chọn backend.

Ví dụ kiểu cũ bằng `cinder` CLI:

```bash
cinder create --hint query='["=", "$backend_id", "host@ceph#volumes"]' 10
```

Filter này hữu ích trong lab hoặc automation đặc biệt, nhưng không nên dùng đại trà cho user thường vì nó làm lộ chi tiết backend và dễ phá chính sách scheduling.

### 7.6. SameBackendFilter

Dùng để schedule volume cùng backend với một volume khác. Hữu ích cho một số workflow cần locality hoặc phụ thuộc backend.

### 7.7. DifferentBackendFilter

Dùng để schedule volume khác backend với một tập volume khác. Hữu ích khi muốn phân tán rủi ro hoặc tách replica.

### 7.8. InstanceLocalityFilter

Chọn backend storage nằm cùng host với hypervisor đang chạy instance. Filter này chỉ phù hợp khi storage backend có locality theo compute host, ví dụ một số mô hình local storage.

Điều kiện:

- Nova phải trả được thông tin host qua extended server attributes.
- Cinder cần quyền phù hợp để đọc thông tin instance từ Nova, hoặc user request phải có quyền cần thiết.

Với Ceph RBD cluster dùng chung, filter này thường không cần thiết.

### 7.9. RetryFilter / IgnoreAttemptedHostsFilter

Mục tiêu là tránh thử lại backend đã fail trong cùng một request scheduling. Khi `scheduler_max_attempts` lớn hơn 1, retry info giúp scheduler không lặp lại backend đã thất bại.

Trong cấu hình mới, cần kiểm tra tên filter thực tế theo tài liệu/code của bản đang dùng. Tài liệu cấu hình public vẫn nhắc `RetryFilter`, còn API docs latest có `IgnoreAttemptedHostsFilter`. Không nên tự thêm filter này nếu chưa xác nhận trong môi trường của bạn bằng:

```bash
cinder list-filters
```

## 8. Các Scheduler Weigher quan trọng

### 8.1. CapacityWeigher

Đây là weigher mặc định:

```ini
scheduler_default_weighers = CapacityWeigher
capacity_weight_multiplier = 1.0
```

Ý nghĩa:

- `capacity_weight_multiplier > 0`: ưu tiên backend nhiều free capacity hơn, giúp spread volume.
- `capacity_weight_multiplier < 0`: ưu tiên backend ít free capacity hơn, giúp stack volume.
- `capacity_weight_multiplier = 0`: CapacityWeigher gần như không ảnh hưởng.

Ví dụ:

```ini
[DEFAULT]
scheduler_default_weighers = CapacityWeigher
capacity_weight_multiplier = 1.0
```

Phù hợp đa số production vì volume được phân tán đều hơn theo capacity.

Stacking có thể dùng trong vài trường hợp:

```ini
[DEFAULT]
capacity_weight_multiplier = -1.0
```

Cách này dồn volume vào một số backend trước, giữ backend khác rảnh. Chỉ nên dùng khi có chiến lược vận hành rõ ràng.

### 8.2. AllocatedCapacityWeigher

Weigher theo allocated capacity:

```ini
scheduler_default_weighers = AllocatedCapacityWeigher
allocated_capacity_weight_multiplier = -1.0
```

Mặc định `allocated_capacity_weight_multiplier = -1.0`, nghĩa là ưu tiên backend có allocated capacity thấp hơn, giúp spread.

Nếu đặt số dương, scheduler sẽ có xu hướng stack vào backend đã allocated nhiều hơn.

### 8.3. VolumeNumberWeigher

Weigher theo số lượng volume trên backend:

```ini
scheduler_default_weighers = CapacityWeigher,VolumeNumberWeigher
volume_number_multiplier = -1.0
```

Ý nghĩa:

- `volume_number_multiplier < 0`: ưu tiên backend có ít volume hơn, giúp spread.
- `volume_number_multiplier > 0`: ưu tiên backend có nhiều volume hơn, giúp stack.

Hữu ích khi backend bị ảnh hưởng bởi số lượng volume/LUN nhiều hơn là dung lượng.

### 8.4. ChanceWeigher

Chấm điểm ngẫu nhiên. Dùng để phân tán ngẫu nhiên giữa các backend đều hợp lệ.

Không nên dùng làm chính trong production nếu bạn cần kiểm soát capacity rõ ràng.

### 8.5. GoodnessWeigher

`GoodnessWeigher` dùng `goodness_function` do admin định nghĩa. Điểm thường trong khoảng 0 đến 100:

- `0`: backend rất kém.
- `50`: backend chấp nhận được.
- `100`: backend tốt nhất.

Ví dụ:

```ini
[DEFAULT]
scheduler_default_weighers = CapacityWeigher,GoodnessWeigher

[ceph-ssd]
goodness_function = "(stats.free_capacity_gb > 1000) ? 100 : 50"
```

Cần thận trọng vì GoodnessWeigher có thể lấn át CapacityWeigher nếu multiplier/logic không hợp lý.

## 9. Multi-backend, Pool và Volume Type

### 9.1. Multi-backend là gì?

Multi-backend cho phép một Cinder deployment quản lý nhiều backend storage cùng lúc.

Ví dụ:

```ini
[DEFAULT]
enabled_backends = ceph-ssd,ceph-hdd,lvm-local

[ceph-ssd]
volume_driver = cinder.volume.drivers.rbd.RBDDriver
rbd_pool = volumes-ssd
volume_backend_name = Ceph-SSD

[ceph-hdd]
volume_driver = cinder.volume.drivers.rbd.RBDDriver
rbd_pool = volumes-hdd
volume_backend_name = Ceph-HDD

[lvm-local]
volume_driver = cinder.volume.drivers.lvm.LVMVolumeDriver
volume_group = cinder-volumes
volume_backend_name = LVM-Local
```

`enabled_backends` trỏ tới tên các section cấu hình. Tên section không bắt buộc trùng `volume_backend_name`.

### 9.2. `volume_backend_name` và Volume Type

Volume type là cách phổ biến nhất để user chọn loại storage mà không biết backend thật.

Ví dụ:

```bash
openstack volume type create ceph-ssd
openstack volume type set --property volume_backend_name=Ceph-SSD ceph-ssd

openstack volume type create ceph-hdd
openstack volume type set --property volume_backend_name=Ceph-HDD ceph-hdd
```

Khi user tạo:

```bash
openstack volume create --size 100 --type ceph-ssd db-volume
```

Scheduler sẽ dùng `CapabilitiesFilter` để chọn backend có:

```ini
volume_backend_name = Ceph-SSD
```

### 9.3. Nhiều backend cùng `volume_backend_name`

Cinder cho phép nhiều backend có cùng `volume_backend_name`.

Ví dụ:

```ini
[DEFAULT]
enabled_backends = lvm1,lvm2

[lvm1]
volume_backend_name = LVM
volume_group = cinder-volumes-1

[lvm2]
volume_backend_name = LVM
volume_group = cinder-volumes-2
```

Nếu volume type yêu cầu `volume_backend_name=LVM`, cả `lvm1` và `lvm2` đều pass `CapabilitiesFilter`. Sau đó `CapacityWeigher` hoặc weigher khác sẽ chọn backend phù hợp hơn.

### 9.4. Pool-level scheduling

Một backend có thể report nhiều pool.

Ví dụ Ceph có thể có nhiều pool hoặc một enterprise array có nhiều storage pool. Scheduler không chỉ chọn backend mà còn chọn pool:

```text
host@backend#pool
```

Các filter/weigher chạy trên `PoolState` khi backend report pool. Vì vậy lỗi capacity có thể xảy ra ở cấp pool dù backend tổng vẫn còn dung lượng.

### 9.5. Retype và migration

Khi `openstack volume set --type ... --retype-policy ...` hoặc `cinder retype`, scheduler phải tìm backend mới phù hợp với volume type mới.

Ví dụ:

```bash
openstack volume set --type ceph-ssd --retype-policy on-demand my-volume
```

Nếu backend hiện tại không match type mới, Cinder có thể migrate dữ liệu sang backend khác tùy policy và khả năng driver.

## 10. Cấu hình cinder-scheduler trong cinder.conf

### 10.1. Cấu hình mặc định quan trọng

Theo sample config Cinder latest/2026.1, các option scheduler quan trọng nằm trong `[DEFAULT]`:

```ini
[DEFAULT]
# Scheduler driver mặc định
scheduler_driver = cinder.scheduler.filter_scheduler.FilterScheduler

# Host manager quản lý cache backend/pool
scheduler_host_manager = cinder.scheduler.host_manager.HostManager

# Số lần thử schedule một volume
scheduler_max_attempts = 3

# Filter mặc định
scheduler_default_filters = AvailabilityZoneFilter,CapacityFilter,CapabilitiesFilter

# Weigher mặc định
scheduler_default_weighers = CapacityWeigher

# Handler chọn backend/pool sau khi weigh
scheduler_weight_handler = cinder.scheduler.weights.OrderedHostWeightHandler

# Thời gian chờ scheduler driver report ready
scheduler_driver_init_wait_time = 60

# File JSON cấu hình scheduler, thường để trống
scheduler_json_config_location =

# Điều chỉnh cách CapacityWeigher chấm điểm
capacity_weight_multiplier = 1.0

# Điều chỉnh AllocatedCapacityWeigher
allocated_capacity_weight_multiplier = -1.0

# Điều chỉnh VolumeNumberWeigher
volume_number_multiplier = -1.0
```

### 10.2. Cấu hình service state

Scheduler dựa vào trạng thái service để biết backend còn sống hay không:

```ini
[DEFAULT]
report_interval = 10
service_down_time = 60
periodic_interval = 60
periodic_fuzzy_delay = 60
```

Ý nghĩa:

| Option | Ý nghĩa |
| ------ | ------- |
| `report_interval` | Tần suất service report state vào datastore. |
| `service_down_time` | Quá thời gian này không check-in thì service bị xem là down. |
| `periodic_interval` | Tần suất chạy periodic task. |
| `periodic_fuzzy_delay` | Delay ngẫu nhiên khi start periodic task để tránh nhiều service chạy cùng lúc. |

Nếu `service_down_time` quá thấp trong môi trường MQ/DB chậm, scheduler có thể xem backend là down nhầm.

### 10.3. Cấu hình Availability Zone

```ini
[DEFAULT]
storage_availability_zone = nova
default_availability_zone = nova
allow_availability_zone_fallback = false

[ceph-ssd]
backend_availability_zone = az-storage-1

[ceph-hdd]
backend_availability_zone = az-storage-2
```

Khuyến nghị:

- Production nên đặt AZ rõ ràng theo backend.
- Không bật `allow_availability_zone_fallback` nếu bạn muốn request sai AZ fail rõ ràng.
- Đồng bộ tên AZ giữa Nova và Cinder nếu user dùng boot-from-volume theo AZ.

### 10.4. Cấu hình Multi-backend

```ini
[DEFAULT]
enabled_backends = ceph-ssd,ceph-hdd
default_volume_type = ceph-hdd

[ceph-ssd]
volume_driver = cinder.volume.drivers.rbd.RBDDriver
rbd_pool = volumes-ssd
rbd_ceph_conf = /etc/ceph/ceph.conf
rbd_user = cinder
rbd_secret_uuid = 457eb676-33da-42ec-9a8c-9293d545c337
volume_backend_name = Ceph-SSD
backend_availability_zone = az-storage-1
reserved_percentage = 5
max_over_subscription_ratio = 10.0

[ceph-hdd]
volume_driver = cinder.volume.drivers.rbd.RBDDriver
rbd_pool = volumes-hdd
rbd_ceph_conf = /etc/ceph/ceph.conf
rbd_user = cinder
rbd_secret_uuid = 457eb676-33da-42ec-9a8c-9293d545c337
volume_backend_name = Ceph-HDD
backend_availability_zone = az-storage-1
reserved_percentage = 10
max_over_subscription_ratio = 5.0
```

Sau khi sửa:

```bash
sudo systemctl restart cinder-volume cinder-scheduler
openstack volume service list
cinder get-pools --detail
```

### 10.5. Cấu hình filter/weigher nâng cao

Ví dụ thêm DriverFilter và GoodnessWeigher:

```ini
[DEFAULT]
scheduler_default_filters = AvailabilityZoneFilter,CapacityFilter,CapabilitiesFilter,DriverFilter
scheduler_default_weighers = CapacityWeigher,GoodnessWeigher
capacity_weight_multiplier = 1.0

[ceph-ssd]
filter_function = "volume.size <= 2048"
goodness_function = "(stats.free_capacity_gb > 5000) ? 100 : 70"

[ceph-hdd]
filter_function = "volume.size >= 100"
goodness_function = "(stats.free_capacity_gb > 10000) ? 90 : 60"
```

## 11. DriverFilter và GoodnessWeigher nâng cao

DriverFilter/GoodnessWeigher cho phép admin viết biểu thức dựa trên:

- Thông tin volume request: `volume.size`, `volume.volume_type_id`, `volume.metadata`...
- Thống kê backend: `stats.free_capacity_gb`, `stats.total_capacity_gb`, `stats.allocated_capacity_gb`...
- Capability backend: `capabilities.<property>`.
- Extra specs volume type.
- QoS specs.

### 11.1. Khi nào nên dùng?

Nên dùng khi default scheduler chưa đủ:

- Backend có giới hạn số volume/LUN.
- Backend có tier đặc biệt theo size.
- Backend có performance metric riêng.
- Muốn policy theo workload: database, archive, backup, analytics.
- Muốn tránh backend khi capacity còn nhiều nhưng performance đã suy giảm.

Không nên dùng nếu chỉ cần map volume type tới backend. Trường hợp đó dùng `volume_backend_name` là đủ.

### 11.2. Các phép toán hỗ trợ

Custom function hỗ trợ:

- Toán học: `+`, `-`, `*`, `/`, `^`.
- Logic: `and`, `or`, `not`, `&`, `|`, `!`.
- So sánh: `>`, `>=`, `<`, `<=`, `==`, `!=`.
- Toán tử ba ngôi: `condition ? value_if_true : value_if_false`.
- Hàm: `abs(x)`, `min(x, y)`, `max(x, y)`.

### 11.3. Ví dụ phân backend theo size

```ini
[DEFAULT]
scheduler_default_filters = AvailabilityZoneFilter,CapacityFilter,CapabilitiesFilter,DriverFilter
enabled_backends = small-volumes,large-volumes

[small-volumes]
volume_driver = cinder.volume.drivers.lvm.LVMVolumeDriver
volume_backend_name = LVM-SMALL
filter_function = "volume.size < 100"

[large-volumes]
volume_driver = cinder.volume.drivers.lvm.LVMVolumeDriver
volume_backend_name = LVM-LARGE
filter_function = "volume.size >= 100"
```

### 11.4. Ví dụ ưu tiên backend theo free capacity

```ini
[DEFAULT]
scheduler_default_weighers = CapacityWeigher,GoodnessWeigher

[ceph-ssd]
goodness_function = "(stats.free_capacity_gb >= 2000) ? 100 : 40"

[ceph-hdd]
goodness_function = "(stats.free_capacity_gb >= 5000) ? 90 : 30"
```

### 11.5. Cảnh báo khi dùng custom function

- Lỗi cú pháp trong `filter_function` hoặc `goodness_function` thường chỉ lộ ra khi có request tạo volume.
- Nếu filter quá chặt, tất cả backend bị loại và user thấy `No valid host`.
- Nếu goodness luôn trả cùng một điểm, scheduler quay lại phụ thuộc weigher khác hoặc thứ tự backend.
- Không nên đưa policy phức tạp vào scheduler nếu có thể biểu diễn bằng volume type/extra specs đơn giản.

## 12. Triển khai HA và Active/Active

### 12.1. Có thể chạy nhiều cinder-scheduler không?

Có. Trong môi trường HA, có thể chạy nhiều instance `cinder-scheduler` trên nhiều controller node. Các scheduler cùng đọc DB, nhận capability update qua MQ và xử lý request.

Ví dụ:

```text
controller01: cinder-api, cinder-scheduler
controller02: cinder-api, cinder-scheduler
controller03: cinder-api, cinder-scheduler
storage01:    cinder-volume@ceph-ssd
storage02:    cinder-volume@ceph-hdd
```

Lưu ý:

- MQ và DB phải HA.
- Đồng bộ `cinder.conf` trên các scheduler node.
- Log nằm trên từng node, cần log tập trung để debug.

### 12.2. Active/Active cho cinder-volume

Cinder hỗ trợ nhóm volume hosts chia sẻ cùng backend bằng option:

```ini
[DEFAULT]
cluster = cinder-volume-ceph
```

`cluster` dùng để group các volume host có cùng backend configuration trong mô hình HA Active/Active. Scheduler nhận cả `host` và `cluster_name` trong capability update để chọn đúng backend.

Không phải mọi driver đều phù hợp Active/Active. Cần kiểm tra support matrix của driver trước khi bật.

### 12.3. Service down detection

Scheduler xem backend có usable hay không dựa vào service heartbeat.

Kiểm tra:

```bash
openstack volume service list
```

Ví dụ output:

```text
+------------------+---------------------------+------+---------+-------+----------------------------+
| Binary           | Host                      | Zone | Status  | State | Updated At                 |
+------------------+---------------------------+------+---------+-------+----------------------------+
| cinder-scheduler | controller01              | nova | enabled | up    | 2026-05-07T03:00:10.000000 |
| cinder-volume    | storage01@ceph-ssd        | nova | enabled | up    | 2026-05-07T03:00:09.000000 |
| cinder-volume    | storage02@ceph-hdd        | nova | enabled | up    | 2026-05-07T03:00:08.000000 |
+------------------+---------------------------+------+---------+-------+----------------------------+
```

Nếu `cinder-volume` là `down`, scheduler sẽ không chọn backend đó dù storage thật vẫn chạy.

## 15. Các lỗi thường gặp

### 15.1. `No valid host was found`

Triệu chứng:

```text
No valid host was found. There are not enough hosts available.
```

Nguyên nhân phổ biến:

- `cinder-volume` backend đang `down`.
- Sai `volume_backend_name` giữa volume type và backend.
- Không đủ `free_capacity_gb`.
- `reserved_percentage` quá cao.
- `max_over_subscription_ratio` quá thấp với thin provisioning.
- Request sai Availability Zone.
- Driver không report pool/capability.
- Custom `filter_function` loại hết backend.

Cách xử lý:

```bash
openstack volume service list
cinder get-pools --detail
openstack volume type show <type-name>
grep -R "volume_backend_name" /etc/cinder/cinder.conf
```

### 15.2. Backend có dung lượng nhưng vẫn bị loại

Kiểm tra:

- Backend có đúng AZ không?
- Volume type có extra specs khác ngoài `volume_backend_name` không?
- Backend report `free_capacity_gb` là số hay `unknown`?
- `reserved_percentage` có làm usable capacity về 0 không?
- Thin provisioning có bật đúng không?
- Pool cụ thể có đủ capacity không, hay chỉ backend tổng còn dung lượng?

Ví dụ:

```bash
cinder get-pools --detail | grep -E "name|free_capacity|reserved_percentage|max_over_subscription"
```

### 15.3. Sai `volume_backend_name`

Volume type:

```bash
openstack volume type show ceph-ssd
```

Thấy:

```text
volume_backend_name='ceph-ssd'
```

Nhưng `cinder.conf`:

```ini
[ceph-ssd]
volume_backend_name = Ceph-SSD
```

Hai giá trị này khác nhau, scheduler sẽ không match. Cần thống nhất:

```bash
openstack volume type set --property volume_backend_name=Ceph-SSD ceph-ssd
```

### 15.4. `cinder get-pools --detail` không thấy backend

Nguyên nhân:

- Backend chưa được thêm vào `enabled_backends`.
- `cinder-volume` chưa restart.
- Driver init fail.
- Thiếu credential storage.
- Service `cinder-volume` down.
- `host` hoặc backend service đổi tên sau khi bật multi-backend.

Kiểm tra:

```bash
systemctl status cinder-volume
tail -100 /var/log/cinder/cinder-volume.log
openstack volume service list
```

Nếu bật `enabled_backends` trên hệ thống đã có volume cũ, cần chú ý host service đổi từ `host` sang `host@backend`. Có thể cần dùng:

```bash
cinder-manage volume update_host --currenthost <old-host> --newhost <old-host>@<backend>
```

### 15.5. Volume type đúng nhưng Scheduler vẫn chọn backend không mong muốn

Kiểm tra:

- Nhiều backend có cùng `volume_backend_name`.
- `scheduler_default_weighers` đang ưu tiên backend khác.
- `capacity_weight_multiplier` âm làm scheduler stack.
- `GoodnessWeigher` trả điểm cao cho backend không mong muốn.
- Volume type không có extra spec `volume_backend_name`.

Xem extra specs:

```bash
openstack volume type show <type-name>
cinder extra-specs-list
```

### 15.6. Scheduler service up nhưng không xử lý request

Nguyên nhân có thể:

- RabbitMQ lỗi.
- `transport_url` sai.
- RPC version pin trong rolling upgrade.
- Scheduler process treo.
- DB connection lỗi.

Kiểm tra:

```bash
grep "transport_url" /etc/cinder/cinder.conf
journalctl -u cinder-scheduler -n 200
grep -E "ERROR|CRITICAL|Traceback|AMQP|OperationalError" /var/log/cinder/cinder-scheduler.log
```

### 15.7. Lỗi sau khi nâng cấp phiên bản

Kiểm tra:

- Các option scheduler cũ có bị đổi tên/deprecated không.
- Filter custom còn tồn tại không.
- Driver còn supported không.
- RPC services đã được restart đúng thứ tự chưa.
- `cinder-manage db sync` đã chạy chưa.
- Release notes của Cinder version mới có yêu cầu upgrade nào không.

## 16. Best Practices cho môi trường Production

### 16.1. Giữ cấu hình Scheduler đơn giản trước

Khuyến nghị ban đầu:

```ini
scheduler_default_filters = AvailabilityZoneFilter,CapacityFilter,CapabilitiesFilter
scheduler_default_weighers = CapacityWeigher
capacity_weight_multiplier = 1.0
```

Chỉ thêm `DriverFilter`, `GoodnessWeigher`, `VolumeNumberWeigher` khi có yêu cầu thật và có test.

### 16.2. Chuẩn hóa volume type

Nên tạo volume type rõ ràng:

```text
ceph-ssd
ceph-hdd
ceph-replicated
ceph-erasure-coded
lvm-local
nfs-standard
```

Mỗi type nên có extra specs tối thiểu:

```bash
openstack volume type set --property volume_backend_name=<BackendName> <type>
```

Nếu có QoS:

```bash
openstack volume qos create high-iops consumer=front-end read_iops_sec=10000 write_iops_sec=5000
openstack volume qos associate high-iops ceph-ssd
```

### 16.3. Không để user biết backend thật nếu không cần

User nên chọn volume type, không chọn trực tiếp backend/pool. Backend naming nên là chi tiết vận hành nội bộ.

### 16.4. Theo dõi capacity định kỳ

Các chỉ số cần monitor:

- `free_capacity_gb`
- `provisioned_capacity_gb`
- `allocated_capacity_gb`
- `max_over_subscription_ratio`
- số volume per backend/pool
- số request `No valid host`
- trạng thái `cinder-volume`
- thời gian từ request create tới volume available

### 16.5. Cẩn thận với oversubscription

Thin provisioning rất hữu ích nhưng phải kiểm soát:

```ini
max_over_subscription_ratio = 10.0
reserved_percentage = 5
```

Không đặt tỷ lệ quá cao nếu backend không có cảnh báo capacity tốt.

### 16.6. Bật log tập trung

Với HA, log scheduler nằm trên nhiều controller. Nên gom về ELK, OpenSearch, Loki hoặc Graylog.

Keyword cần alert:

```text
No valid host
Failed to schedule
CapacityFilter
CapabilitiesFilter
AMQP server is unreachable
OperationalError
Traceback
```

## 18. Những điểm cần chú ý ở bản mới nhất

### 18.1. Phiên bản mới nhất tại thời điểm cập nhật

Tại ngày 2026-05-07:

- OpenStack mới nhất là **2026.1 Gazpacho**, phát hành tháng 04/2026.
- Cinder stable trong 2026.1 là **28.0.0**.
- Trang Cinder `latest` đang hiển thị nhánh phát triển sau 2026.1, ví dụ `28.1.0.dev`.

Do đó tài liệu này lấy **2026.1/Cinder 28.0.0** làm baseline production, đồng thời kiểm tra các option scheduler trên trang `latest`.

### 18.2. Scheduler core không thay đổi lớn trong release notes 2026.1

Release notes Cinder 28.0.0 tập trung nhiều vào driver, backup, multi-region Glance/Swift, `disk_geometry`, loại bỏ Windows driver/service support và các bug fix backend. Không có thay đổi lớn được nêu cho core scheduler như default scheduler driver, default filters hoặc default weighers.

Các default quan trọng vẫn là:

```ini
scheduler_driver = cinder.scheduler.filter_scheduler.FilterScheduler
scheduler_default_filters = AvailabilityZoneFilter,CapacityFilter,CapabilitiesFilter
scheduler_default_weighers = CapacityWeigher
```

### 18.3. Driver support ảnh hưởng gián tiếp tới Scheduler

Trong 2026.1, một số driver bị loại bỏ hoặc thay đổi support. Điều này ảnh hưởng scheduler theo hướng:

- Backend dùng driver đã bị remove sẽ không start được `cinder-volume`.
- Backend không report capability thì scheduler không thấy pool.
- Driver unsupported cần `enable_unsupported_driver = true`, nhưng đây là lựa chọn rủi ro và có thể bị remove ở release sau.

Luôn kiểm tra driver support matrix và release notes trước khi nâng cấp.

### 18.4. `disk_geometry` là option mới cấp driver/backend

Cinder 28.0.0 bổ sung `disk_geometry` cho một số volume driver để advertise logical/physical block size cho guest. Đây không phải scheduler option, nhưng có thể nên đặt theo backend type:

```ini
[ceph-hdd]
disk_geometry = 512e
```

Scheduler vẫn chọn backend như bình thường; `disk_geometry` ảnh hưởng cách volume được attach/advertise tới guest.

### 18.5. Multi-region options mới ảnh hưởng luồng tạo volume từ image/backup

Các option như:

```ini
[glance]
region_name = RegionOne

[DEFAULT]
backup_swift_region_name = RegionOne
```

không phải scheduler option trực tiếp, nhưng trong multi-region deployment, chọn sai region có thể làm workflow tạo volume từ image hoặc backup fail sau khi scheduler đã chọn backend.

## 19. Tóm tắt nhanh

| Nội dung | Ghi nhớ |
| -------- | ------- |
| Service | `cinder-scheduler` chọn backend/pool cho request Cinder. |
| Driver mặc định | `cinder.scheduler.filter_scheduler.FilterScheduler`. |
| Filter mặc định | `AvailabilityZoneFilter`, `CapacityFilter`, `CapabilitiesFilter`. |
| Weigher mặc định | `CapacityWeigher`. |
| Lỗi phổ biến nhất | `No valid host was found`. |
| Debug quan trọng | `cinder-scheduler.log`, `cinder get-pools --detail`, `openstack volume service list`. |
| Map type -> backend | Dùng `volume_backend_name` trong volume type extra specs. |
| Multi-backend | Dùng `enabled_backends` và backend section riêng. |
| Production baseline | Giữ filter/weigher đơn giản, thêm custom policy sau khi test. |

Checklist nhanh khi Scheduler lỗi:

```bash
openstack volume service list
cinder get-pools --detail
openstack volume type show <type>
openstack volume message list
grep "No valid host" /var/log/cinder/cinder-scheduler.log
grep -E "CapacityFilter|CapabilitiesFilter|AvailabilityZoneFilter|DriverFilter" /var/log/cinder/cinder-scheduler.log
```
