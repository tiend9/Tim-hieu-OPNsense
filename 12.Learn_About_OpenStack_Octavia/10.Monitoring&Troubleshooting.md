# TROUBLESHOOTING & MONITORING OCTAVIA

> **Phiên bản tham chiếu**: OpenStack **2026.1 Gazpacho** + Octavia **14.x**

## I. HEALTH MANAGER HOẠT ĐỘNG NHƯ THẾ NÀO (HEARTBEAT UDP)

Cấu phần **Octavia Health Manager** chịu trách nhiệm giám sát tính sẵn sàng của toàn bộ máy ảo Amphora đang chạy trong cụm đám mây. Cơ chế hoạt động của Health Manager dựa trên giao thức gửi gói tin UDP không hướng kết nối siêu nhẹ.

### Cơ chế hoạt động chi tiết

- **Phát nhịp tim (UDP Heartbeat)**:

  - Tiến trình `octavia-amphora-agent` chạy bên trong từng máy ảo Amphora định kỳ (mặc định mỗi `10` giây) sẽ gửi một gói tin UDP mã hóa (chứa thông tin trạng thái hoạt động, tải trọng CPU/RAM và trạng thái các listener) về phía địa chỉ IP của Health Manager trên cổng **`5555`**.
  - Luồng truyền tin này chạy hoàn toàn qua card mạng quản trị (LB Network).

- **Lắng nghe và cập nhật**:

  - Health Manager liên tục lắng nghe cổng `5555`. Mỗi khi nhận được gói tin heartbeat hợp lệ, nó sẽ cập nhật mốc thời gian sống cuối cùng (`last_seen`) của Amphora đó vào Database của Octavia.

- **Xác định sự cố**:

  - Nếu một Amphora không gửi heartbeat và mốc `last_seen` cũ quá khoảng thời gian timeout quy định (mặc định cấu hình `heartbeat_timeout = 60` giây):
  - Health Manager sẽ lập tức đánh dấu Amphora đó bị lỗi và gọi Controller Worker tiến hành quy trình tự động thay thế (failover).

## II. VỊ TRÍ VÀ PHÂN TÍCH LOG CỦA CÁC SERVICE CHÍNH

Khi hệ thống gặp lỗi tạo Load Balancer hoặc lỗi phân phối tải, việc đầu tiên người vận hành cần làm là truy vết log của các tiến trình Octavia.

### 1. Trên hệ thống cài đặt chuẩn (Systemd)

Đường dẫn lưu log mặc định nằm tại thư mục `/var/log/octavia/`:

- **`octavia-api.log`**: Ghi nhận các yêu cầu REST API của người dùng gửi tới, lỗi xác thực Keystone hoặc lỗi cú pháp gửi yêu cầu.
- **`octavia-worker.log`**: Nơi ghi nhận nhật ký của luồng xử lý chính. Nếu quá trình spawn máy ảo Amphora hoặc cắm card mạng (Plugging) bị thất bại, toàn bộ dấu vết sẽ hiển thị ở đây.
- **`octavia-health-manager.log`**: Ghi nhận các sự kiện mất nhịp tim của Amphora và quyết định thực thi failover.
- **`octavia-housekeeping.log`**: Nhật ký dọn dẹp tài nguyên rác và xoay vòng chứng chỉ bảo mật TLS.

### 2. Trên hệ thống triển khai qua Container (Kolla-Ansible)

Kolla-Ansible đẩy log tập trung ra hệ thống hoặc có thể truy cập trực tiếp qua Docker log:

```bash
# Xem log API:
docker logs magnum_api  # Hoặc octavia_api tương ứng

# Theo dõi trực tiếp log của Controller Worker chạy ngầm:
docker logs -f octavia_worker
```

## III. XỬ LÝ TRẠNG THÁI ERROR — QUY TRÌNH DEBUG TỪNG BƯỚC

Trạng thái `ERROR` của Load Balancer xuất hiện khi Octavia Controller Worker không thể hoàn thành việc khởi tạo cơ sở hạ tầng vật lý hoặc không thể cấu hình được phần mềm trên Amphora.

```text
  [LB Status: ERROR]
         │
         ├──► Bước 1: Tra log /var/log/octavia/octavia-worker.log để tìm Exception
         │
         ├──► Bước 2: Kiểm tra Quota (vCPU, RAM, IPs) trong Nova và Neutron
         │
         ├──► Bước 3: Xác minh kênh mTLS (Cổng 9443) có bị Firewall chặn không
         │
         └──► Bước 4: Kiểm tra trạng thái máy ảo Amphora chạy trong Nova
```

### Quy trình debug từng bước cụ thể:

#### Bước 1: Tra cứu log của Controller Worker

Đây là bước quan trọng nhất. Hãy tìm kiếm các từ khóa lỗi như `ERROR`, `Exception`, hoặc `Traceback` trong tệp `octavia-worker.log`. Lỗi thường rơi vào các trường hợp:

- Không tìm thấy image có tag cấu hình.
- Thất bại khi cắm card mạng Neutron (Hot-plug interface).

#### Bước 2: Kiểm tra trạng thái máy ảo Amphora trong Nova

Sử dụng tài khoản admin để quét tìm máy ảo Amphora tương ứng với Load Balancer bị lỗi:

```bash
source /etc/kolla/admin-openrc

# Liệt kê các máy ảo của dự án dịch vụ (thường thuộc project "service"):
openstack server list --all-projects | grep amphora
```

Nếu máy ảo ở trạng thái `ERROR` hoặc `shutdown` trong Nova, ta cần kiểm tra tài nguyên Compute Node hoặc xem log của Nova để biết lý do máy ảo không thể spawn (ví dụ: lỗi RAM, lỗi ổ cứng đầy).

#### Bước 3: Xác minh kết nối mạng điều khiển

Kiểm tra xem máy chủ Controller có ping được địa chỉ IP quản trị của Amphora hay không, và cổng bảo mật `9443` của Amphora có bị chặn bởi Security Group hoặc Firewall hệ điều hành (iptables/firewalld) hay không:

```bash
# Kiểm tra kết nối tới cổng API của Amphora:
curl -k https://<IP_QUẢN_TRỊ_AMPHORA>:9443/v1/details
```

Nếu trả về lỗi kết nối (`Connection refused` hoặc `Timeout`), có nghĩa là tiến trình agent bên trong Amphora chưa khởi động thành công hoặc mạng quản trị đang gặp sự cố định tuyến.

## IV. PHÂN TÍCH AMPHORA-AGENT LOG BÊN TRONG VM AMPHORA

Trong trường hợp máy ảo Amphora vẫn chạy bình thường nhưng Load Balancer không thể chuyển sang trạng thái `ACTIVE` (bị kẹt ở `PENDING_CREATE`), ta cần truy cập trực tiếp vào bên trong máy ảo Amphora để phân tích log hệ thống lớp sâu.

### 1. Truy cập vào máy ảo Amphora bằng SSH

Do máy ảo Amphora nằm trong mạng quản trị riêng biệt và sử dụng SSH key cấu hình riêng, ta cần thực hiện kết nối bắc cầu từ Controller Node:

```bash
# Sử dụng Private Key của Octavia (thường lưu tại /etc/octavia/.ssh/octavia_key):
ssh -i /etc/octavia/.ssh/octavia_key core@<IP_QUẢN_TRỊ_AMPHORA>
```

*(Lưu ý: Username đăng nhập mặc định là `core` đối với Fedora CoreOS, `ubuntu` đối với Ubuntu hoặc `cloud-user` tùy thuộc vào Image OS lúc build).*

### 2. Đọc tệp tin nhật ký bên trong Amphora

Khi đã đăng nhập thành công vào VM, sử dụng `journalctl` để đọc nhật ký hoạt động:

```bash
# Xem log của tiến trình Amphora Agent nhận lệnh từ Controller:
sudo journalctl -u amphora-agent

# Xem log hoạt động của công cụ cân bằng tải chính HAProxy:
sudo journalctl -u haproxy

# Xem log của Keepalived nếu chạy cụm HA Active-Standby:
sudo journalctl -u keepalived
```

Lỗi thường gặp bên trong Amphora là:

- Chứng chỉ client/server hết hạn hoặc không khớp chữ ký CA (gây lỗi xác thực mTLS trên cổng 9443).

- Cú pháp cấu hình HAProxy sinh ra bị lỗi do khai báo ký tự lạ hoặc sai port backend.

## V. CÁC CÂU LỆNH KIỂM TRA NHANH TRẠNG THÁI VÀ SỨC KHỎE HỆ THỐNG

Dưới đây là tập hợp các câu lệnh CLI OpenStack hữu ích giúp quản trị viên nhanh chóng đánh giá sức khỏe và chẩn đoán lỗi của hệ thống Octavia.

### 1. Hiển thị mô hình trạng thái phân cấp (Status Show)

Lệnh này trả về cấu trúc cây logic của toàn bộ Load Balancer, hiển thị trực quan trạng thái hoạt động (`operating_status`) và trạng thái triển khai (`provisioning_status`) của từng thành phần cấp dưới:

```bash
openstack loadbalancer status show web-lb
```

### 2. Kiểm tra thông tin các máy ảo Amphora liên quan

```bash
# Xem danh sách chi tiết các Amphora ảo đang chạy phục vụ Load Balancer:
openstack loadbalancer amphora list --loadbalancer web-lb
```

Lệnh này hiển thị rõ địa chỉ IP quản trị (`compute_ip`), IP VIP (`vrrp_ip`), ID máy ảo Nova tương ứng (`compute_id`) và vai trò của từng máy ảo (`role: MASTER` hoặc `BACKUP`), giúp khoanh vùng nhanh máy ảo bị lỗi để tiến hành xử lý kỹ thuật.
