# TÌM HIỂU VỀ HOST AGGREGATE VÀ AVAILABILITY ZONE TRONG NOVA

![Nova](./images/Nova_17.png)

> Phiên bản tham chiếu: OpenStack `2026.1 Gazpacho` / Nova `33.x`.
> Điểm mới cần nhớ so với tài liệu cũ: scheduler hiện đại dùng **Placement** rất nhiều, đặc biệt với Availability Zone và tenant isolation.

## A. TÌM HIỂU VỀ HOST AGGREGATE

### 1. Host Aggregate là gì?

**Host Aggregate** là nhóm logic của các compute host do admin tạo ra để phân loại host theo đặc điểm nào đó.

Ví dụ:

```text
Aggregate: gpu-hosts
  - compute01
  - compute02

Aggregate: ssd-hosts
  - compute03
  - compute04
```

Host aggregate thường dùng để:

- gom host theo phần cứng: GPU, SSD, CPU generation;
- gom host theo hypervisor/driver;
- gom host theo license;
- gom host theo rack/datacenter;
- điều khiển scheduler bằng metadata;
- tạo Availability Zone cho user.

### 2. Đặc điểm của Host Aggregate

| Thuộc tính | Host Aggregate |
| ---------- | -------------- |
| User nhìn thấy trực tiếp | Không |
| Admin quản lý | Có |
| Có metadata `key=value` | Có |
| Scheduler có thể dùng | Có |
| Một host nằm trong nhiều aggregate | Có |
| Một aggregate chứa nhiều host | Có |

Ví dụ một host có thể nằm trong nhiều aggregate:

```text
compute01
  - gpu-hosts
  - ssd-hosts
  - intel-cpu-hosts
```

Nhưng nếu các aggregate đó được expose thành **Availability Zone**, một host chỉ được thuộc **một AZ**.

### 3. Metadata trong Host Aggregate

Điểm mạnh của host aggregate là metadata:

```bash
ssd=true
gpu=true
cpu_type=intel
license=windows
```

Scheduler có thể match metadata này với:

- flavor extra specs;
- image metadata;
- tenant/project isolation;
- weight multiplier theo aggregate.

Ví dụ:

| Flavor extra spec | Aggregate metadata | Ý nghĩa |
| ----------------- | ------------------ | ------- |
| `aggregate_instance_extra_specs:ssd=true` | `ssd=true` | chỉ boot trên host SSD |
| `aggregate_instance_extra_specs:gpu=true` | `gpu=true` | chỉ boot trên host GPU |
| `aggregate_instance_extra_specs:license=windows` | `license=windows` | chỉ boot trên host có license |

### 4. Host Aggregate khác Placement Aggregate như nào?

Trong Nova hiện đại, cần phân biệt rõ:

| Loại aggregate | Thuộc service | Chứa gì | Có metadata Nova không? | Dùng cho |
| -------------- | ------------- | ------- | ----------------------- | -------- |
| Host Aggregate | Nova | compute host | Có | admin grouping, scheduler filter, AZ |
| Placement Aggregate | Placement | resource provider | Không theo kiểu Nova | prefilter nhanh ở Placement |

Compute host trong Nova được biểu diễn trong Placement bằng **resource provider**.

Ví dụ:

```text
Nova host: compute01
Placement resource provider: UUID của compute01
```

Từ Nova `18.0.0` trở đi, `nova-api` cố gắng tự mirror việc add/remove host trong Nova host aggregate sang Placement aggregate tương ứng. Vì vậy trong đa số deployment mới, admin không cần tự chạy `openstack resource provider aggregate set`, trừ khi cần debug hoặc sửa dữ liệu lệch.

### 5. Scheduler filters liên quan Host Aggregate

#### 5.1 `AggregateInstanceExtraSpecsFilter`

Filter này match flavor extra specs với aggregate metadata.

Ví dụ aggregate:

```bash
openstack aggregate set --property ssd=true fast-io
```

Flavor:

```bash
openstack flavor set \
  --property aggregate_instance_extra_specs:ssd=true \
  ssd.large
```

Kết quả:

```text
VM dùng flavor ssd.large chỉ được schedule vào host thuộc aggregate có ssd=true
```

Lưu ý:

- Nên dùng prefix `aggregate_instance_extra_specs:`.
- Extra spec không có prefix vẫn còn hỗ trợ vì backward compatibility, nhưng không nên dùng vì dễ xung đột với `ComputeCapabilitiesFilter`.

#### 5.2 `AggregateImagePropertiesIsolation`

Filter này match image metadata với aggregate metadata.

Ví dụ:

```bash
openstack aggregate set --property os_distro=windows windows-hosts
openstack image set --property os_distro=windows Win-2022
```

Kết quả:

```text
Image Windows chỉ chạy trên host aggregate phù hợp
```

Lưu ý quan trọng:

- Từ Liberty, filter này chỉ xử lý các **standard image metadata**.
- Nếu muốn match metadata tùy ý, nên dùng `AggregateInstanceExtraSpecsFilter` hoặc traits trong Placement.
- Với bản mới, nếu làm isolation theo capability/trait thì nên ưu tiên Placement trait khi có thể.

#### 5.3 `AggregateMultiTenancyIsolation`

Filter này giới hạn project/tenant vào aggregate.

Ví dụ:

```bash
openstack aggregate set \
  --property filter_tenant_id=<project_id> \
  private-tenant-a
```

Từ các bản mới, cách tốt hơn là dùng Placement tenant isolation:

```ini
[scheduler]
limit_tenants_to_placement_aggregate = True
```

Điều kiện:

- Nova host aggregate và Placement aggregate phải match membership/UUID.
- Metadata vẫn dùng key dạng `filter_tenant_id`.
- Có thể dùng nhiều key như `filter_tenant_id`, `filter_tenant_id2`, `filter_tenant_id3`.

#### 5.4 Các filter aggregate khác

| Filter | Chức năng |
| ------ | --------- |
| `AggregateIoOpsFilter` | giới hạn workload I/O theo aggregate |
| `AggregateNumInstancesFilter` | giới hạn số instance trên host/aggregate |
| `AggregateTypeAffinityFilter` | chỉ cho một số flavor/type chạy trên aggregate |
| `AggregateImagePropertiesIsolation` | match image metadata |
| `AggregateInstanceExtraSpecsFilter` | match flavor extra specs |
| `AggregateMultiTenancyIsolation` | cô lập tenant/project |

## B. CONFIG HOST AGGREGATE

### 1. Bật filter aggregate cho flavor extra specs

Trên node chạy `nova-scheduler`, cấu hình:

```ini
[filter_scheduler]
enabled_filters = ComputeFilter,ComputeCapabilitiesFilter,ImagePropertiesFilter,ServerGroupAntiAffinityFilter,ServerGroupAffinityFilter,AggregateInstanceExtraSpecsFilter
```

Trong bản Nova 2026.1, default `enabled_filters` là:

```text
ComputeFilter
ComputeCapabilitiesFilter
ImagePropertiesFilter
ServerGroupAntiAffinityFilter
ServerGroupAffinityFilter
```

Vì vậy nếu muốn dùng `AggregateInstanceExtraSpecsFilter`, bạn cần thêm nó vào danh sách enabled filters.

### 2. Config tenant isolation bằng Placement

```ini
[scheduler]
limit_tenants_to_placement_aggregate = True
placement_aggregate_required_for_tenants = False
```

Ý nghĩa:

| Option | Ý nghĩa |
| ------ | ------- |
| `limit_tenants_to_placement_aggregate` | giới hạn project vào Placement aggregate match metadata |
| `placement_aggregate_required_for_tenants` | nếu `True`, project không có aggregate match sẽ không được schedule |

### 3. Config liên quan AZ

```ini
[DEFAULT]
default_availability_zone = nova
default_schedule_zone = <None>
```

Ý nghĩa:

| Option | Ý nghĩa |
| ------ | ------- |
| `default_availability_zone` | AZ mặc định của compute service nếu host không thuộc aggregate có AZ metadata |
| `default_schedule_zone` | AZ mặc định cho instance nếu user không chọn AZ; nếu set, instance bị gắn với AZ này suốt vòng đời |

## C. VÍ DỤ HOST AGGREGATE CHO SSD

### 1. Mục tiêu

User cần flavor `ssd.large` và VM dùng flavor này chỉ chạy trên host có SSD.

### 2. Tạo aggregate

Nếu chỉ muốn phân nhóm host SSD, không cần tạo AZ:

```bash
openstack aggregate create fast-io
```

Gắn metadata:

```bash
openstack aggregate set --property ssd=true fast-io
```

Thêm host:

```bash
openstack aggregate add host fast-io compute01
openstack aggregate add host fast-io compute02
```

Kiểm tra:

```bash
openstack aggregate show fast-io
```

### 3. Tạo flavor

```bash
openstack flavor create \
  --ram 8192 \
  --disk 80 \
  --vcpus 4 \
  ssd.large
```

Gắn extra spec:

```bash
openstack flavor set \
  --property aggregate_instance_extra_specs:ssd=true \
  ssd.large
```

### 4. User tạo VM

```bash
openstack server create \
  --image ubuntu-24.04 \
  --flavor ssd.large \
  --network private \
  vm-ssd-01
```

Scheduler sẽ:

```text
1. đọc flavor extra specs
2. chạy AggregateInstanceExtraSpecsFilter
3. chỉ giữ host thuộc aggregate có ssd=true
4. tiếp tục filter/weigh
5. chọn host tốt nhất
```

### 5. Cách hiện đại hơn: dùng Placement trait

Nếu bạn muốn mô tả capability của host ở Placement, có thể dùng trait:

```bash
openstack resource provider trait set \
  --trait CUSTOM_DISK_SSD \
  <resource-provider-uuid>
```

Flavor yêu cầu trait:

```bash
openstack flavor set \
  --property trait:CUSTOM_DISK_SSD=required \
  ssd.large
```

Ưu điểm:

- Placement lọc candidate sớm hơn;
- rõ ràng với các capability dạng hardware;
- phù hợp mô hình scheduler hiện đại.

Host aggregate vẫn hữu ích khi bạn cần gom host theo logic vận hành hoặc dùng metadata/AZ.

## D. CLI HOST AGGREGATE

### 1. Tạo aggregate và thêm host

```bash
openstack aggregate create my-aggregate
openstack aggregate add host my-aggregate compute01
```

### 2. Xem danh sách và chi tiết

```bash
openstack aggregate list
openstack aggregate list --long
openstack aggregate show my-aggregate
```

### 3. Gắn hoặc xóa metadata

```bash
openstack aggregate set --property pinned=true my-aggregate
openstack aggregate unset --property pinned my-aggregate
```

### 4. Đổi tên

```bash
openstack aggregate set --name my-awesome-aggregate my-aggregate
```

### 5. Gỡ host và xóa aggregate

```bash
openstack aggregate remove host my-aggregate compute01
openstack aggregate delete my-aggregate
```

### 6. Pre-cache image theo aggregate

Host aggregate còn có thể dùng để yêu cầu compute nodes pre-cache image:

```bash
nova aggregate-cache-images my-aggregate image1 image2
```

Việc cache chạy bất đồng bộ và theo best-effort. Kết quả theo dõi trong log của từng compute.

## E. TÌM HIỂU VỀ AVAILABILITY ZONE

### 1. Availability Zone là gì?

**Availability Zone (AZ)** là logical partition hiển thị cho user.

User có thể chọn AZ khi tạo VM:

```bash
openstack server create \
  --availability-zone dc1 \
  --image ubuntu-24.04 \
  --flavor m1.small \
  --network private \
  vm01
```

AZ thường đại diện cho:

| Mục đích | Ví dụ |
| -------- | ----- |
| Datacenter | `dc1`, `dc2` |
| Rack | `rack-a`, `rack-b` |
| Power domain | `power-a`, `power-b` |
| Network domain | `net-a`, `net-b` |

Lưu ý rất quan trọng:

```text
AZ không tự tạo High Availability.
```

AZ chỉ là cách partition cloud. HA còn phụ thuộc storage, network, service architecture, workload design.

### 2. AZ được tạo từ Host Aggregate

Trong Nova, AZ không phải một bảng DB riêng. AZ được tạo bằng metadata trên host aggregate:

```bash
availability_zone=dc1
```

Ví dụ:

```bash
openstack aggregate create --zone dc1 agg-dc1
openstack aggregate add host agg-dc1 compute01
openstack aggregate add host agg-dc1 compute02
```

Hoặc set AZ cho aggregate đã có:

```bash
openstack aggregate set \
  --property availability_zone=dc1 \
  agg-dc1
```

User sẽ thấy AZ `dc1`.

### 3. Quy tắc giữa Host Aggregate và AZ

| Rule | Đúng/Sai |
| ---- | -------- |
| Một host có thể nằm trong nhiều host aggregate | Đúng |
| Một host có thể nằm trong nhiều AZ | Sai |
| Host aggregate visible trực tiếp với user | Sai |
| AZ visible với user | Đúng |
| AZ được tạo từ aggregate metadata | Đúng |

Nếu bạn cố add một host vào hai aggregate có hai AZ khác nhau, Nova sẽ reject.

### 4. Default Availability Zone

Nếu host không thuộc aggregate có metadata AZ, host đó thuộc default AZ:

```ini
[DEFAULT]
default_availability_zone = nova
```

Warning quan trọng:

- Không nên yêu cầu boot vào AZ tên `nova` một cách explicit.
- Operator cũng không nên set aggregate metadata `availability_zone=nova`.

Lý do: `nova` vừa là tên default AZ, vừa có thể là tên metadata AZ nếu admin set nhầm. Điều này làm user và Nova khó phân biệt, có thể gây lỗi khi migrate/move instance.

### 5. AZ với Placement

Từ Nova `28.0.0` (Bobcat), để Placement honor AZ request, phải có Placement aggregate match với Nova host aggregate dùng làm AZ.

Nói dễ hiểu:

```text
Nova host aggregate: agg-dc1
  UUID: abc
  hosts: compute01, compute02
  metadata: availability_zone=dc1

Placement aggregate:
  UUID: abc
  resource providers: compute01, compute02
```

Khi user boot:

```bash
openstack server create --availability-zone dc1 ...
```

Scheduler sẽ map AZ sang Placement aggregate và Placement chỉ trả candidate trong aggregate đó.

Trong các bản mới, `nova-api` thường tự mirror host membership sang Placement khi admin add/remove host khỏi aggregate. Nhưng khi debug, vẫn nên biết kiểm tra Placement resource provider aggregate.

### 6. Không move instance giữa AZ tùy tiện

Nova không cho phép thao tác add/remove host khỏi aggregate nếu việc đó làm instance đang chạy bị "chuyển AZ" theo nghĩa logic.

Best practice:

```text
Drain instance khỏi host trước
Sau đó mới đổi AZ/aggregate membership của host
```

Các thao tác move như resize, cold migrate, live migrate, evacuate, unshelve thường đi qua scheduler và chịu ràng buộc AZ nếu instance đã được tạo trong AZ cụ thể.

### 7. Cinder cross AZ attach

Nova có option:

```ini
[cinder]
cross_az_attach = True
```

Mặc định thường cho phép server và volume ở khác AZ.

Nếu set:

```ini
[cinder]
cross_az_attach = False
```

Thì Nova cố giữ server và volume cùng AZ. Cách này hữu ích cho HPC hoặc môi trường cần compute-storage affinity, nhưng tài liệu Nova cảnh báo option này không được dùng/test rộng rãi như các đường phổ biến.

## F. FLOW THỰC TẾ KHI USER CHỌN AZ

Ví dụ:

```bash
openstack server create \
  --availability-zone dc1 \
  --image ubuntu-24.04 \
  --flavor m1.small \
  --network private \
  vm-dc1
```

Flow:

```text
1. nova-api nhận request AZ=dc1
2. nova-conductor gọi scheduler
3. scheduler map AZ dc1 -> Placement aggregate
4. Placement trả allocation candidates trong dc1
5. Nova chạy filter/weigher
6. Scheduler chọn host tốt nhất trong dc1
7. Conductor gửi RPC tới compute
8. VM được spawn
```

## G. CHỌN HOST CỤ THỂ

Nova vẫn hỗ trợ cú pháp:

```bash
openstack server create --availability-zone ZONE:HOST:NODE ...
```

Nhưng đây là kiểu legacy và có thể bypass scheduler filters.

Cách hiện đại hơn cho admin là dùng microversion `2.74`:

```bash
openstack --os-compute-api-version 2.74 server create \
  --host compute01 \
  --hypervisor-hostname compute01 \
  --image ubuntu-24.04 \
  --flavor m1.small \
  --network private \
  vm-on-compute01
```

Lưu ý:

- Đây mặc định là thao tác admin-only.
- Không nên dùng để thay thế scheduler trong vận hành bình thường.

## H. VÍ DỤ PRODUCTION

### 1. GPU workload

```bash
openstack aggregate create gpu-hosts
openstack aggregate set --property gpu=true gpu-hosts
openstack aggregate add host gpu-hosts compute-gpu01

openstack flavor set \
  --property aggregate_instance_extra_specs:gpu=true \
  gpu.large
```

VM dùng `gpu.large` chỉ chạy trên host aggregate GPU.

### 2. Windows license

```bash
openstack aggregate create windows-license-hosts
openstack aggregate set --property license=windows windows-license-hosts
openstack aggregate add host windows-license-hosts compute-win01

openstack flavor set \
  --property aggregate_instance_extra_specs:license=windows \
  win.large
```

### 3. Multi datacenter bằng AZ

```bash
openstack aggregate create --zone dc1 agg-dc1
openstack aggregate add host agg-dc1 compute01
openstack aggregate add host agg-dc1 compute02

openstack aggregate create --zone dc2 agg-dc2
openstack aggregate add host agg-dc2 compute03
openstack aggregate add host agg-dc2 compute04
```

User chọn:

```bash
openstack server create --availability-zone dc1 ...
openstack server create --availability-zone dc2 ...
```

## I. LỖI THƯỜNG GẶP

### 1. User chọn AZ nhưng NoValidHost

Kiểm tra:

```bash
openstack availability zone list --compute
openstack aggregate list --long
openstack aggregate show <aggregate>
openstack compute service list --service nova-compute
```

Nguyên nhân thường gặp:

- AZ không có host;
- compute trong AZ bị down/disabled;
- Placement aggregate không match;
- flavor/image yêu cầu trait/filter làm hết candidate;
- host còn trong maintenance.

### 2. Flavor extra specs không có tác dụng

Kiểm tra scheduler config:

```ini
[filter_scheduler]
enabled_filters = ...,AggregateInstanceExtraSpecsFilter
```

Kiểm tra flavor:

```bash
openstack flavor show ssd.large
```

Key nên có dạng:

```text
aggregate_instance_extra_specs:ssd=true
```

### 3. Host không add được vào aggregate AZ

Có thể host đã thuộc aggregate khác có AZ khác.

Kiểm tra:

```bash
openstack aggregate list --long
```

Nếu host đang có instance, cần drain instance trước khi đổi AZ membership.
