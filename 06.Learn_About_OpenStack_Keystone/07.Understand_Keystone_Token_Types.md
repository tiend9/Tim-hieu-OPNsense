# TÌM HIỂU CÁC LOẠI TOKEN TRONG KEYSTONE (OPENSTACK)

## 1. Tổng quan về Token trong Keystone

Trong OpenStack Keystone, Token là một chuỗi ký tự đại diện cho quyền truy cập (thường được gọi là "thẻ thông hành"). Sau khi người dùng hoặc dịch vụ (service) xác thực thành công (cung cấp đúng username/password), Keystone sẽ cấp phát một Token.

Token này đại diện cho định danh (Identity) và quyền hạn (Authorization) của người dùng đó (chứa User ID, Project ID, Role, thời gian hết hạn...). Khi người dùng muốn giao tiếp với các dịch vụ khác trong OpenStack (như Nova để tạo máy ảo, Glance để tải image, Neutron để tạo mạng...), họ phải gửi kèm Token này. Dịch vụ đó sẽ dùng Token để xác minh với Keystone hoặc tự xác minh xem yêu cầu đó có hợp lệ hay không.

## 2. Các loại Token cũ (Legacy Tokens)

Trước khi tìm ra giải pháp tối ưu nhất, Keystone đã trải qua nhiều định dạng Token khác nhau. Hiện tại chúng đều đã **bị loại bỏ (deprecated)**, nhưng việc phân tích lại chúng sẽ giúp ta hiểu rõ tại sao hệ thống cần sự thay đổi.

### 2.1. UUID Token

- **Cơ chế:** Token chỉ là một chuỗi ký tự định danh ngẫu nhiên (UUID) gồm 32 ký tự. Bản thân chuỗi này không chứa bất kỳ thông tin nào về user hay quyền hạn.

- **Ưu điểm:** Kích thước rất nhỏ (chỉ 32 bytes), dễ dàng truyền qua HTTP Header mà không lo bị chặn hoặc lỗi.

- **Nhược điểm:**

  - **Không tự chứa thông tin (Non-bearer):** Mỗi khi có request gửi đến Nova, Glance... các dịch vụ này bắt buộc phải gửi lại chuỗi UUID về cho Keystone để hỏi: "Token này của ai? Có quyền gì? Còn hạn không?". Điều này làm tăng độ trễ (latency).

  - **Nút thắt cổ chai DB (Database Bottleneck):** Keystone bắt buộc phải lưu trữ toàn bộ UUID Tokens đang hoạt động vào cơ sở dữ liệu (Database). Khi hệ thống có hàng vạn request, DB của Keystone sẽ bị quá tải. Ngoài ra, việc dọn dẹp các token đã hết hạn trong DB (token flush) ngốn rất nhiều tài nguyên.

### 2.2. PKI và PKIZ Token (Public Key Infrastructure)

- **Cơ chế:** Nhằm giải quyết điểm yếu của UUID. PKI Token là một chuỗi JSON chứa đầy đủ thông tin của user (thậm chí chứa cả Service Catalog - danh sách tất cả các API endpoint của hệ thống), sau đó được **ký điện tử (Signed)** bằng Private Key của Keystone. Các dịch vụ khác (như Nova, Cinder...) có thể dùng Public Key của Keystone để tự xác thực tính toàn vẹn của Token mà không cần liên tục hỏi lại Keystone. (PKIZ là phiên bản nén Zlib của PKI).

- **Ưu điểm:** Giảm tải việc các service phải liên tục gọi về Keystone.

- **Nhược điểm:**

  - **Kích thước khổng lồ:** Vì chứa toàn bộ Service Catalog và được ký mã hóa, kích thước của PKI Token có thể lên tới 8KB - 16KB. Kích thước này thường xuyên gây lỗi `HTTP 413 Request Entity Too Large` hoặc vượt quá giới hạn Header của các web server như Nginx, Apache.

  - Vẫn cần lưu trữ một phần vào Database để quản lý việc thu hồi (Revoke).

## 3. Token JWT (JSON Web Token)

Mặc dù JWT (chuẩn RFC 7519) rất phổ biến trong các ứng dụng Web hiện đại, nhưng nó chưa từng là token mặc định trên toàn hệ thống OpenStack.

- **Cơ chế:** JWT gồm 3 phần `Header.Payload.Signature` được mã hóa Base64. Nó chứa dữ liệu (Payload) và được ký (Signature) tương tự ý tưởng của PKI nhưng chuẩn hóa và gọn hơn.

- **Tính chất:** JWT là dạng token **Stateless (không lưu trạng thái)**, không cần lưu vào DB.

- **Tuy nhiên**, OpenStack đã chọn phát triển Fernet thay vì JWT vì Fernet cung cấp tính năng **mã hóa hoàn toàn (Encryption)** thay vì chỉ ký (Signing) để dữ liệu bên trong Token không bị lộ ra ngoài, và Fernet có kích thước nhỏ gọn hơn rất nhiều.

## 4. Fernet Token - Tiêu chuẩn hiện tại (Mặc định)

Bắt đầu từ phiên bản Kilo và trở thành chuẩn mặc định không thể thay thế từ Mitaka, **Fernet** là định dạng token hoàn hảo nhất cho OpenStack.

### 4.1. Fernet Token là gì?

**Fernet** là một định dạng bảo mật thông báo được thiết kế có kích thước nhỏ, tốc độ cao và **hoàn toàn không lưu trạng thái (Stateless)** (tuyệt đối không lưu bất cứ gì vào Database). Thay vì chỉ ký để xác thực như PKI, Fernet **mã hóa toàn bộ (Encrypt)** thông tin bên trong.

### 4.2. Cơ chế mã hóa và giải mã của Fernet

- **Mã hóa đối xứng (Symmetric Encryption):** Fernet sử dụng chuẩn `AES-128-CBC` để mã hóa dữ liệu và `HMAC-SHA256` để chống giả mạo. Việc này đồng nghĩa nó dùng chung một khóa (Key) để vừa mã hóa (khi tạo Token) vừa giải mã (khi xác thực).

- **Thư mục quản lý khóa (Key Repository):** Keystone duy trì một thư mục (mặc định tại `/etc/keystone/fernet-keys/`) chứa các file khóa được đặt tên bằng số thứ tự (ví dụ: `0`, `1`, `2`...).

  - **Primary Key (Khóa chính):** File có số cao nhất. Dùng để tạo ra các Token mới và giải mã.

  - **Secondary Key (Khóa phụ):** Các file còn lại. Dùng để giải mã các Token được tạo ra trước đó (nhưng vẫn chưa hết hạn).

  - **Staged Key (Khóa chờ):** Luôn mang tên là `0`, sẵn sàng để được thăng cấp thành Primary Key trong tương lai.

- **Quá trình tạo (Issue):** Keystone đóng gói thông tin tối giản nhất (User ID, Project ID, Thời gian tạo, Thời gian hết hạn) -> Mã hóa bằng Primary Key -> Sinh ra Fernet Token (khoảng ~250 bytes). (Fernet không nhét Service Catalog vào token để giảm dung lượng).

- **Quá trình giải mã (Validate):** Khi nhận được Token, Keystone dùng các khóa trong Key Repository để giải mã. Nếu giải mã thành công và thời gian `Expires` chưa tới -> Token hợp lệ.

### 4.3. Tại sao OpenStack chọn dùng Fernet Token? (Lợi ích tuyệt đối)

- **Hoàn toàn Stateless (Không tốn Database):** Fernet giải phóng hoàn toàn DB của Keystone khỏi việc phình to do lưu trữ Token. Loại bỏ thao tác `keystone-manage token_flush` tốn kém. Tốc độ I/O tăng vọt.

- **Kích thước cực nhỏ:** Kích thước của Fernet Token chỉ lớn hơn UUID một chút (~250 bytes), hoàn toàn không bao giờ gây đầy HTTP Header như PKI.

- **Hiệu suất siêu cao:** Thuật toán mã hóa đối xứng (Symmetric) như AES hoạt động nhanh hơn rất nhiều so với mã hóa bất đối xứng của PKI.

- **Bảo mật dữ liệu:** Nội dung của Token bị mã hóa hoàn toàn, người bắt được Token cũng không thể đọc được nội dung (như User ID hay Project ID bên trong) nếu không có Key giải mã.
