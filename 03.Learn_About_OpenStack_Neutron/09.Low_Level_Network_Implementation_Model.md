## 4. Đường đi của packet trên Compute Node

**Nếu dùng sơ đồ mạng VLAN/ FLAT để tách Network các Node Compute trong cụm OpenStack**:

![Neutron](./images/Neutron_34.png)

**Nếu dùng sơ đồ mạng VXLAN/ GRE để tách các Node Compute trong cụm OpenStack**:

![Neutron](./images/Neutron_35.png)

Bây giờ đi từng bước.

### `Bước 1` — VM → vNIC

VM có virtual NIC.

Ví dụ:

![Neutron](./images/Neutron_37.png)

- vNIC thực chất được kết nối với một TAP device trên host.
- TAP cho phép QEMU/VM trao đổi packet với kernel Linux.

Hiểu đơn giản:

- vNIC là card mạng ảo của VM.

### `Bước 2` — vNIC → qbr → br-int

![Neutron](./images/Neutron_38.png)

Điểm dễ nhầm ở đây:

- qbr là Linux Bridge.

- Tài liệu giải thích qbr là viết tắt lịch sử của Quantum Bridge. Nó từng được dùng để hỗ trợ Security Group bằng iptables.

Hiểu đơn giản

- qbr nằm : Cung cấp lớp xử lý firewall/security group trong mô hình OVS cũ.

### `Bước 3` — qbr ↔ br-int

![Neutron](./images/Neutron_39.png)

Hai bridge không nối trực tiếp bằng dây thật.

Chúng nối bằng: qvb, qvo

Trong đó:

- qvb: đầu veth phía Linux Bridge
- qvo: đầu veth phía OVS
- qvb ↔ qvo là một cặp veth.

Hiểu đơn giản:

- veth pair giống như một sợi dây mạng ảo có hai đầu.

### `Bước 4` — br-int

- br-int = Integration Bridge.

Đây là một virtual switch của OVS trên Compute Node.

Có thể hình dung:

```text
             br-int
          /    |    \
        VM1   VM2   VM3
```

Nó xử lý traffic nội bộ của các VM.

Đặc biệt, br-int sử dụng Local VLAN ID để phân biệt các network khác nhau trên chính node đó.

Ví dụ:

- Tenant Network A → Local VLAN 10
- Tenant Network B → Local VLAN 20
- Tenant Network C → Local VLAN 30

**Note**: Local VLAN này không nhất thiết là VLAN thật trên physical network. Đây là điểm rất quan trọng.

### `Bước 5` — br-int → br-ethX / br-tun

Sau br-int, packet đi tiếp tùy loại network.

#### Nếu VLAN/Flat

Thì điểm cuối trước khi ra khỏi Compute Node là br-ethX. Rồi mới đi ra Physical NIC.

#### Nếu VXLAN/GRE

Đi qua: br-tun rồi mới đi ra Physical NIC.

> Tài liệu gọi chung br-ethX và br-tun là Tenant Network Layer Bridge để dễ mô tả.

#### Patch Port là gì?

br-int và br-tun có thể nối với nhau bằng patch port.

Ví dụ:

```text
br-int
  │
patch-tun
  │
patch-int
  │
br-tun
```

Patch port cũng giống như dây mạng ảo, nhưng được OVS thực hiện.

Vì vậy cần phân biệt:

```text
veth pair
qvb ↔ qvo
```

>Là virtual network device của Linux.

```text
patch port
patch-tun ↔ patch-int
```

>Là kết nối ảo do OVS thực hiện.

**Note**: Chức năng chính của nó là ánh xạ chuyển đồi VLAN local thành VLAN extrenal hoặc VXLAN external. Hoặc ngược lại

### `Bước 6` — VID Conversion

Đây là phần dễ gây rối nhất.

Có hai loại VLAN ID cần phân biệt:

- Local VID

>Dùng bên trong node.

- External/Tenant VID

> Dùng để biểu diễn network trên tenant/physical network.

Ví dụ:

```text
VM
 ↓
br-int
 ↓
Local VID = 10
 ↓
VID Conversion
 ↓
External VLAN = 100
 ↓
Physical Network
```

Tức là:

> VLAN 10 bên trong node không nhất thiết phải bằng VLAN 100 bên ngoài.

#### Vì sao phải chuyển VID?

Giả sử: `Tenant VLAN = 100` và VXLAN Network cũng được ánh xạ vào: `Local VLAN = 100`

Nếu không có cơ chế chuyển đổi thì có thể xảy ra xung đột.(Tạo sự `isolated` giữa các `tenant` với nhau)

Do đó OVS Flow Table sẽ thực hiện việc mapping.

Ví dụ:

```text
Tenant Network A
External VID 100
       ↓
Local VID 10
```

và:

```text
Tenant Network B
External VID 200
       ↓
Local VID 20
```

Như vậy br-int chỉ cần xử lý:

- `VID 10` → Network A
- `VID 20` → Network B

#### `ml2_conf.ini` liên quan gì?

Giả sử trong file cấu hình `ml2_conf.ini` có đoạn:

```text
[ml2_type_vlan]
network_vlan_ranges = public:3001:4000

[ml2_type_vxlan]
vni_ranges = 1:1000

[ml2_type_gre]
tunnel_id_ranges = 1:1000
```

Hiểu đơn giản:

```text
VLAN
- 3001 → 4000
```

>là các VLAN ID(VLAN Identifier) mà Neutron được phép sử dụng.

```text
VXLAN
VNI 1 → 1000
```

>là range VNI(VXLAN Network Identifier) được phép sử dụng.

```text
GRE
Tunnel ID 1 → 1000
```

> là range tunnel ID.

### `Bước 7` — ra Physical NIC

Cuối cùng:

```text
br-int
   ↓
br-ethX / br-tun
   ↓
ethX
   ↓
Physical Network
```

> Packet lúc này đã rời khỏi virtual switch và đi ra card mạng vật lý.

### Bước 8 — Physical Network

**Node**: Từ đây trở đi, Neutron không còn xử lý toàn bộ đường đi nữa.

Packet đi qua:

```text
Compute Node
     ↓
Physical NIC
     ↓
Physical Switch
     ↓
Physical Network
     ↓
Compute Node khác
```

Nếu là VXLAN thì packet được encapsulate để đi qua mạng vật lý.

## 5. Node Network dùng để làm gì?

Nếu Compute Node chỉ cần cho:

```text
VM1 ↔ VM2
```

thì network path tương đối đơn giản.

Nhưng nếu VM muốn:

```text
VM
 ↓
Private Network
 ↓
Router
 ↓
External Network
 ↓
Internet
```

thì cần thành phần thực hiện L3 routing/NAT.

Đó là vai trò của Network Node trong mô hình truyền thống của Neutron.

## 7. qrouter-XXX là gì?

`qrouter-XXX` là một Network Namespace đại diện cho một Neutron Router trong mô hình L3 agent.

Ví dụ tạo: **Router**

Neutron tạo namespace:

`qrouter-xxxx`

Bên trong namespace đó có interface kết nối tới các network.

Ví dụ:

```text
Private Network
      │
      ▼
   qr-xxx
      │
 qrouter namespace
      │
      ▼
   qg-xxx
      │
      ▼
External Network
```

Tài liệu cũng giải thích rằng mỗi Router tạo một `qrouter-XXX` namespace.

![Neutron](./images/Neutron_44.png)

## 11. Routing giữa hai Private Network

Ví dụ:

```text
Network A
10.0.1.0/24
     │
     │
   qr-1
     │
  qrouter
     │
   qr-2
     │
     │
Network B
10.0.2.0/24
```

VM A gửi packet tới VM B.

Packet vào:

`qr-1`

Linux kernel kiểm tra routing table:

`10.0.2.0/24` → `qr-2`

Sau đó gửi ra:

`qr-2`

=> Đây chính là L3 routing giữa các subnet/network.

## 12. Floating IP hoạt động thế nào?

Nếu VM có:

```text
Private IP
10.0.0.10
```

và Floating IP:

`203.0.113.10`

thì Router thực hiện NAT.

Có thể hiểu đơn giản:

```text
Private IP
10.0.0.10
      ↓
   NAT/Floating IP
      ↓
203.0.113.10
      ↓
External Network
```

## 13. Controller Node làm gì?

Controller không phải nơi xử lý toàn bộ data-plane traffic của VM trong mô hình tách node truyền thống.

Controller chủ yếu chạy: `neutron-server`

neutron-server nhận API request.

Ví dụ:

```text
User
 │
 │ openstack network create
 ▼
neutron-server
 │
 ▼
Neutron Agent / Backend
 │
 ▼
OVS / Linux / OVN
```

Vì vậy cần nhớ:

Controller chủ yếu xử lý control plane; Compute/Network node mới trực tiếp xử lý data plane theo mô hình triển khai tương ứng.

Tài liệu cũng nhấn mạnh Controller không chịu trách nhiệm trực tiếp về data plane trong mô hình được mô tả
