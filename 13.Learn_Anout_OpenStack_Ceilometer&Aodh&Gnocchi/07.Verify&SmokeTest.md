# VERIFY & SMOKETEST CHO TELEMETRY, GNOCCHI & AODH

> **Phiên bản tham chiếu**: OpenStack **2026.1 Gazpacho**

## I. TELEMETRY VÀ CEILOMETER — QUY TRÌNH KIỂM TRA VÀ SỬA LỖI THƯỜNG GẶP

Sau khi hoàn tất quá trình cài đặt, bước đầu tiên là xác minh khả năng thu thập và vận chuyển dữ liệu của Ceilometer.

### 1. Quy trình kiểm tra trạng thái

- **Kiểm tra trạng thái Service**:

  ```bash
  # Trên Controller:
  sudo systemctl status ceilometer-agent-notification
  
  # Trên Compute Node:
  sudo systemctl status ceilometer-agent-compute
  ```

- **Kiểm tra Log hoạt động**:

  Theo dõi tệp log để đảm bảo không xuất hiện các lỗi kết nối RabbitMQ hoặc lỗi mTLS với Libvirt:

  ```bash
  # Đọc log trên Compute Node:
  sudo journalctl -u ceilometer-agent-compute -n 50 --no-pager
  ```

- **Liệt kê danh sách Metrics**:
  Do Ceilometer đẩy dữ liệu qua Gnocchi, ta sử dụng OpenStack client tích hợp gnocchi-plugin để truy vấn:

  ```bash
  source /etc/kolla/admin-openrc
  
  # Xem danh sách tất cả các metric đo lường hiện có:
  openstack metric list --limit 10
  ```

### 2. Các lỗi thường gặp và cách xử lý

#### Lỗi 1: Không có dữ liệu đo lường ("No meter" hoặc Danh sách trống)

- *Nguyên nhân*:

  - Chưa khởi chạy máy ảo (Instance) nào trên Compute Node nên Polling Agent không có đối tượng để cào chỉ số.
  - Cấu hình file `/etc/ceilometer/polling.yaml` sai cú pháp dẫn tới tiến trình bỏ qua việc cào dữ liệu.

- *Giải pháp*:

  - Khởi tạo ít nhất một máy ảo và đảm bảo máy ảo đang ở trạng thái `ACTIVE`.
  - Kiểm tra tính hợp lệ của file yaml bằng lệnh `yamllint /etc/ceilometer/polling.yaml`.

#### Lỗi 2: Lỗi đẩy dữ liệu ("Publisher fail" hoặc Connection Refused)

- *Nguyên nhân*: Ceilometer cào được dữ liệu nhưng không thể đẩy sang Gnocchi API (thường hiển thị lỗi HTTP `401 Unauthorized` hoặc `Connection refused` trong `ceilometer-agent-notification.log`).

- *Giải pháp*:

  - Xác minh địa chỉ Gnocchi API URL trong tệp `polling.yaml` có khớp với Endpoint đã đăng ký trong Keystone hay không.
  - Kiểm tra cấu hình `[service_credentials]` trong `ceilometer.conf` đã khai báo đúng thông tin xác thực chưa.

## II. GNOCCHI — QUY TRÌNH KIỂM TRA VÀ SỬA LỖI THƯỜNG GẶP

Gnocchi đóng vai trò trung tâm lưu trữ chuỗi thời gian, việc kiểm tra sức khỏe dịch vụ cần thực hiện qua cả API và tiến trình xử lý nền.

### 1. Quy trình kiểm tra trạng thái trong Gnocchi

- **Kiểm tra hiệu năng nạp Gnocchi**:

  ```bash
  # Xem thống kê số lượng điểm dữ liệu đang chờ xử lý:
  gnocchi status
  ```

  *Lưu ý*: Chỉ số `measures to process` (số lượng gói dữ liệu thô đang nằm chờ trong Incoming Storage) nên duy trì ở mức thấp hoặc bằng **`0`**. Nếu con số này liên tục tăng cao, hệ thống đang bị quá tải hoặc tiến trình xử lý nền đang gặp sự cố.

- **Liệt kê tài nguyên được lập chỉ mục (Resource List)**:

  ```bash
  # Xem tất cả các tài nguyên (VM, Volume, Network) đã được Gnocchi đăng ký:
  gnocchi resource list
  ```

### 2. Các lỗi thường gặp và cách xử lý trong Gnocchi

#### Lỗi 1: Tiến trình xử lý nền bị sập ("metricd down" hoặc Measures bị nghẽn)

- *Nguyên nhân*: `gnocchi-metricd` dừng hoạt động hoặc xử lý quá chậm khiến dữ liệu thô bị ứ đọng tại phân vùng Incoming Storage, làm Aodh không thể đọc được dữ liệu mới để đánh giá alarm.
- *Giải pháp*:

  - Khởi động lại dịch vụ: `sudo systemctl restart gnocchi-metricd`.
  - Trong môi trường lớn, cấu hình chạy song song nhiều tiến trình `gnocchi-metricd` trên các Controller Node khác nhau để tăng tốc độ xử lý song song.

#### Lỗi 2: Lỗi Indexer Database ("Indexer error" / "PostgreSQL Connection Fail")

- *Nguyên nhân*: Gnocchi API không thể kết nối tới cơ sở dữ liệu Indexer PostgreSQL do sai mật khẩu, hoặc tường lửa chặn cổng `5432`.

- *Giải pháp*:

  - Kiểm tra kết nối thô bằng CLI: `psql -h <PG_HOST> -U gnocchi -d gnocchi`.
  - Xác minh cấu hình `indexer.url` trong file `/etc/gnocchi/gnocchi.conf` đã được đồng bộ chuẩn.

## III. AODH — QUY TRÌNH KIỂM TRA VÀ SỬA LỖI THƯỜNG GẶP

Aodh chịu trách nhiệm bắn cảnh báo tự động, việc kiểm tra cần xác minh luồng từ lúc nhận dữ liệu đến lúc trigger thành công.

### 1. Quy trình kiểm tra trạng thái trong Aodh

- **Tạo thử nghiệm một Alarm mẫu**:

  ```bash
  # Tạo một cảnh báo nếu CPU của máy ảo vượt quá 85%:
  aodh alarm create --name "cpu_high_alarm" \
    --type gnocchi_resources_threshold \
    --metric cpu_util \
    --threshold 85.0 \
    --comparison-operator gt \
    --aggregation-method mean \
    --granularity 60 \
    --resource-id <UUID_MÁY_ẢO> \
    --alarm-action "log://"
  ```

- **Liệt kê danh sách Alarms**:

  ```bash
  # Xem danh sách và trạng thái các Alarms đang có:
  aodh alarm list
  ```

- **Xem lịch sử kích hoạt**:
  
  ```bash
  # Tra cứu nhật ký thay đổi trạng thái của alarm cụ thể:
  aodh alarm-history show <ALARM_ID>
  ```

### 2. Các lỗi thường gặp và cách xử lý trong Aodh

#### Lỗi 1: Cảnh báo bị kẹt ở trạng thái "insufficient data"

- *Nguyên nhân*:

  - Aodh không tìm thấy điểm dữ liệu nào của metric chỉ định trong Gnocchi trong khoảng thời gian kiểm tra.
  - Tham số `granularity` cấu hình trong Alarm (ví dụ: kiểm tra mỗi 60 giây) nhỏ hơn chu kỳ cào dữ liệu thực tế của Ceilometer (ví dụ: Ceilometer chỉ cào mỗi 300 giây).

- *Giải pháp*:

  - Điều chỉnh tham số `granularity` của alarm lớn hơn hoặc bằng chu kỳ cào dữ liệu (`interval`) cấu hình trong `polling.yaml` của Ceilometer.
  - Sử dụng lệnh `gnocchi measures show cpu_util --resource-id <UUID>` để xác minh Gnocchi thực sự đang có dữ liệu cho tài nguyên đó.

#### Lỗi 2: Cảnh báo không thực hiện hành động ("Alarm stuck" / Cảnh báo treo)

- *Nguyên nhân*: Trạng thái Alarm đã chuyển sang `alarm` nhưng tiến trình `aodh-notifier` không thể gửi yêu cầu webhook hoặc ghi log do cấu hình sai endpoint nhận.

- *Giải pháp*:

  - Đảm bảo service `aodh-notifier` đang chạy: `sudo systemctl status aodh-notifier`.
  - Kiểm tra log `/var/log/aodh/aodh-notifier.log` để xác minh xem lệnh gọi Webhook HTTP có bị lỗi mạng (ví dụ: lỗi DNS hoặc Gateway) hay không.
