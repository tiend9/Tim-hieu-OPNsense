# ADVANCE KNOWLEDGE: COLD MIGRATE, LIVE MIGRATE, RESIZE, RESCUE, EVACUATE TRONG NOVA

> Phiên bản tham chiếu: OpenStack `2026.1 Gazpacho` / Nova `33.x`.
> Tài liệu này chỉ giải thích khái niệm, workflow và lưu ý vận hành. Phần lab thao tác CLI sẽ tách riêng sau.

## I. TỔNG QUAN

Trong Nova, các thao tác như **cold migrate**, **live migrate**, **resize**, **rescue** và **evacuate** đều là các operation nâng cao trên vòng đời instance.

Chúng giống nhau ở điểm:

- đều thay đổi trạng thái hoặc vị trí chạy của instance;
- đều cần `nova-api`, `nova-conductor`, `nova-scheduler`, `nova-compute`;
- đều có liên quan tới Placement allocation;
- đều có thể đụng tới Neutron, Cinder, Glance;
- đều cần đọc log kỹ khi lỗi vì workflow thường dài.

Sơ đồ chung:

```text
User / Admin
    |
    v
nova-api
    |
    v
nova-conductor
    |
    +--> nova-scheduler <--> Placement
    |
    v
nova-compute source  <-->  nova-compute destination
    |
    v
Hypervisor / Libvirt / QEMU
```

Điểm cần nhớ:

```text
Placement giữ tài nguyên
Scheduler chọn host
Conductor điều phối workflow
Compute thao tác với hypervisor
```

## II. CÁC TRẠNG THÁI INSTANCE LIÊN QUAN

Một vài state hay gặp:

| State | Ý nghĩa |
| ----- | ------- |
| `ACTIVE` | VM đang hoạt động bình thường |
| `SHUTOFF` | VM đã tắt |
| `MIGRATING` | đang live migrate |
| `RESIZE` | đang resize hoặc cold migrate |
| `VERIFY_RESIZE` | resize/cold migrate xong, chờ confirm hoặc revert |
| `RESCUED` | đang ở rescue mode |
| `ERROR` | workflow lỗi |

Một số operation có thêm `task_state`, ví dụ:

```text
resize_migrating
resize_migrated
resize_finish
migrating
rescuing
unrescuing
rebuilding
```

Khi debug không nên chỉ nhìn `status`. Cần xem thêm:

- `task_state`;
- migration record;
- Placement allocation;
- log `nova-conductor`;
- log `nova-scheduler`;
- log `nova-compute` ở source và destination.

## III. COLD MIGRATION

![Nova](./images/Nova_19.png)

### 1. Cold Migration là gì?

**Cold migration** là di chuyển instance từ compute host này sang compute host khác trong trạng thái không chạy.

Tên khác:

```text
Non-live migration
Migration
```

Nova documentation mô tả cold migration gần giống resize, điểm khác là:

```text
Resize     -> đổi flavor
Cold migrate -> không đổi flavor
```

Cả hai đều thường đưa instance qua state `VERIFY_RESIZE` để admin/user confirm hoặc revert.

### 2. Khi nào dùng cold migrate?

Cold migrate phù hợp khi:

- bảo trì compute host nhưng chấp nhận downtime;
- live migration không khả thi;
- workload không yêu cầu chạy liên tục;
- muốn scheduler chọn lại host khác;
- cần move instance nhưng không muốn đổi flavor.

Không phù hợp khi:

- ứng dụng không chịu được reboot;
- disk instance quá lớn và không có shared storage;
- compute node/source network quá yếu cho việc copy disk.

### 3. Workflow cold migration

Luồng khái niệm:

```text
1. nova-api nhận yêu cầu migrate
2. nova-conductor tạo migration record
3. nova-scheduler chọn destination host
4. source compute shutdown instance
5. source/destination xử lý disk và metadata
6. destination compute spawn instance
7. instance vào VERIFY_RESIZE
8. confirm thì xóa dữ liệu tạm ở source
9. revert thì quay lại host cũ
```

Với KVM/libvirt:

- nếu dùng shared storage, destination có thể dùng cùng disk backend;
- nếu không dùng shared storage, Nova cần copy instance disk giữa compute hosts;
- các compute host cần resolve hostname đúng;
- môi trường truyền thống thường cần SSH giữa compute nodes cho việc copy disk.

### 4. Placement allocation trong cold migration

Trong migration/resize, Nova cần đảm bảo tài nguyên không bị double-book sai.

Ý tưởng:

```text
Before migrate:
  allocation nằm ở source host

During migrate:
  Nova giữ trạng thái migration và allocation liên quan source/destination

After confirm:
  allocation chính thức nằm ở destination

After revert:
  allocation quay về source
```

Nếu workflow fail giữa chừng, có thể xuất hiện orphaned allocation hoặc migration record kẹt. Khi đó cần debug từ Nova trước, không nên xóa allocation thủ công nếu chưa hiểu state.

### 5. Ưu điểm và hạn chế

Ưu điểm:

- đơn giản hơn live migration;
- không cần giữ VM chạy trong lúc move;
- dễ áp dụng với nhiều loại workload;
- ít nhạy cảm hơn với dirty memory, CPU model, QEMU live migration compatibility.

Hạn chế:

- có downtime;
- VM bị shutdown/reboot;
- copy disk có thể lâu;
- cần confirm hoặc revert;
- vẫn cần scheduler và Placement chọn được host hợp lệ.

## IV. LIVE MIGRATION

![Nova](./images/Nova_20.png)

### 1. Live Migration là gì?

**Live migration** là di chuyển VM sang compute host khác trong khi VM vẫn đang chạy.

Mục tiêu:

- giảm downtime;
- bảo trì compute host;
- cân bằng tải;
- xử lý host có dấu hiệu rủi ro trước khi lỗi thật.

Live migration phức tạp hơn cold migration vì Nova/QEMU/libvirt phải chuyển trạng thái runtime của VM, đặc biệt là RAM, CPU state, device state và network state.

### 2. Các loại live migration

| Loại | Ý nghĩa |
| ---- | ------- |
| Shared storage-based live migration | ephemeral disk nằm trên storage dùng chung giữa source và destination |
| Block live migration | ephemeral disk không shared, phải copy disk qua network |
| Volume-backed live migration | VM boot từ Cinder volume, không cần copy root ephemeral disk kiểu block migration |

So sánh nhanh:

| Loại | Copy disk? | Downtime | Load network | Ghi chú |
| ---- | ---------- | -------- | ------------ | ------- |
| Shared storage | Không hoặc rất ít | Thấp | Chủ yếu copy RAM | cần storage chung |
| Block live migration | Có | Thấp nhưng dễ kéo dài | Cao | không hợp với disk quá lớn |
| Volume-backed | Không copy root disk local | Thấp | Chủ yếu copy RAM | phụ thuộc Cinder backend |

### 3. Workflow live migration

Luồng khái niệm:

```text
1. nova-api nhận yêu cầu live migrate
2. nova-conductor validate request
3. nova-scheduler chọn destination nếu admin không chỉ định host
4. Placement kiểm tra tài nguyên/trait/aggregate
5. destination compute chuẩn bị network, volume, instance directory
6. source compute yêu cầu libvirt/QEMU bắt đầu migration
7. QEMU copy memory/device state sang destination
8. VM switch sang destination trong khoảng downtime ngắn
9. source cleanup resource
10. Nova cập nhật DB và Placement allocation
```

Trong live migration, phần khó nhất thường là:

- copy RAM đủ nhanh;
- giữ network không mất quá lâu;
- đảm bảo storage compatible;
- đảm bảo CPU model/feature compatible;
- cleanup đúng nếu migration fail.

### 4. Live migration chỉ trong cùng cell

Trong Cells v2, live migration chỉ hỗ trợ migrate instance sang host khác **trong cùng cell**.

```text
cell1/compute01  ->  cell1/compute02   OK
cell1/compute01  ->  cell2/compute09   Không phải live migration thông thường
```

Nếu cần move qua cell khác, đó là một workflow khác, phức tạp hơn nhiều và phụ thuộc tính năng cross-cell move/resize của Nova.

### 5. Timeout, auto-converge và post-copy

Live migration có thể bị kẹt nếu VM ghi RAM quá nhanh:

```text
QEMU vừa copy memory page sang destination
Guest lại ghi vào page đó
Page phải copy lại
```

Nova/libvirt có các cơ chế xử lý:

| Cơ chế | Ý nghĩa |
| ------ | ------- |
| completion timeout | giới hạn thời gian migration hoàn tất |
| abort | hủy migration khi timeout |
| force-complete | ép hoàn tất migration |
| auto-converge | giảm tốc CPU của guest để RAM dirty chậm lại |
| post-copy | chuyển VM sang destination trước, page thiếu thì kéo từ source |

Trade-off:

- `auto-converge` làm VM chậm lại trong lúc migrate;
- `post-copy` giảm khả năng kẹt nhưng nếu network đứt giữa chừng VM có thể bị ảnh hưởng nặng;
- `force-complete` có thể pause VM một khoảng thời gian tùy cấu hình.

### 6. Điểm mới đáng chú ý trong OpenStack 2026.1

Nova `33.0.0` có một số điểm mới liên quan live migration:

- hỗ trợ **parallel live migrations** cho libvirt thông qua `[libvirt] live_migration_parallel_connections`;
- hỗ trợ live migration cho instance có **emulated vTPM** khi dùng `hw:tpm_secret_security=host`;
- cải thiện graceful shutdown cho các tác vụ dài như live migration, cold migration, resize;
- API microversion mới nhất của Nova trong 2026.1 là `2.103`;
- `max_concurrent_live_migrations = 0` theo nghĩa "unlimited" đã bị deprecate, operator nên rất cẩn thận với option này.

Ý nghĩa vận hành:

```text
Muốn live migration nhanh hơn -> cân nhắc parallel connections
Muốn migrate vTPM instance -> phải dùng TPM secret security mode phù hợp
Muốn restart service an toàn hơn -> chú ý graceful shutdown
```

### 7. Ưu điểm và hạn chế

Ưu điểm:

- downtime thấp;
- phù hợp bảo trì host;
- user ít bị ảnh hưởng hơn cold migration;
- có thể dùng cho vận hành production nếu hạ tầng chuẩn.

Hạn chế:

- phụ thuộc mạnh vào libvirt/QEMU/CPU compatibility;
- block live migration gây tải network và storage;
- VM RAM lớn hoặc dirty memory cao dễ timeout;
- live migration với PCI, vGPU, vDPA, NUMA, pinned CPU, huge pages, vTPM có yêu cầu riêng;
- debug khó hơn cold migration.

## V. RESIZE

### 1. Resize là gì?

**Resize** là thay đổi flavor của instance.

Ví dụ về ý nghĩa:

```text
m1.small  ->  m1.medium
2 vCPU / 4 GB RAM  ->  4 vCPU / 8 GB RAM
```

Resize làm VM restart. Đây không phải hot-add CPU/RAM theo nghĩa guest đang chạy mà không bị restart.

### 2. Resize khác cold migrate như nào?

| Tiêu chí | Cold migrate | Resize |
| -------- | ------------ | ------ |
| Đổi host | Có thể | Có thể |
| Đổi flavor | Không | Có |
| Có downtime | Có | Có |
| Có `VERIFY_RESIZE` | Có | Có |
| Có confirm/revert | Có | Có |

Resize có thể xảy ra:

- cùng host, nếu policy và cấu hình cho phép;
- khác host, nếu scheduler chọn destination khác;
- khác cell trong một số workflow cross-cell resize, nhưng phức tạp hơn live migration thông thường.

### 3. Workflow resize

```text
1. nova-api nhận yêu cầu đổi flavor
2. nova-conductor tạo migration/resize record
3. scheduler chọn host phù hợp với flavor mới
4. Placement kiểm tra allocation cho flavor mới
5. source compute shutdown instance
6. disk/metadata được chuẩn bị ở destination
7. destination compute spawn instance với flavor mới
8. instance vào VERIFY_RESIZE
9. confirm -> chốt flavor mới
10. revert -> quay lại flavor/host cũ
```

Trong trạng thái `VERIFY_RESIZE`, instance đã chạy ở flavor mới nhưng workflow chưa được chốt hoàn toàn. Đây là cơ chế an toàn để user/admin có thể kiểm tra trước khi confirm.

### 4. Auto confirm resize

Nova có option:

```text
resize_confirm_window
```

Nếu được cấu hình khác `0`, Nova có thể tự confirm các instance ở trạng thái resized quá thời gian cho phép.

Ý nghĩa:

- tránh VM kẹt `VERIFY_RESIZE` quá lâu;
- giảm việc admin/user quên confirm;
- nhưng cần policy rõ vì confirm sẽ xóa đường quay lại trạng thái cũ.

### 5. Lưu ý vận hành

Resize thường lỗi vì:

- flavor mới không đủ tài nguyên trong Placement;
- image/flavor extra specs không match host;
- host aggregate/AZ giới hạn candidate;
- disk copy giữa compute lỗi;
- volume attachment cleanup lỗi;
- Neutron port binding ở destination lỗi;
- instance đang có operation khác.

Khi resize lỗi, cần xem cả:

```text
nova-conductor.log
nova-scheduler.log
nova-compute.log ở source
nova-compute.log ở destination
Placement allocation
Neutron/Cinder logs nếu có volume/port liên quan
```

## VI. RESCUE

### 1. Rescue là gì?

**Rescue** là boot instance vào môi trường cứu hộ để truy cập disk/root filesystem khi VM bị lỗi.

Use case:

- quên password;
- bootloader lỗi;
- cấu hình network trong guest sai;
- `/etc/fstab` sai làm guest không boot;
- cần mount root disk để sửa file;
- cần khôi phục dữ liệu.

Rescue không phải migration và không dùng để tăng tài nguyên.

### 2. Hai kiểu rescue

Nova hiện có hai cơ chế:

| Kiểu | Ý nghĩa |
| ---- | ------- |
| Legacy rescue | boot từ rescue image hoặc copy image gốc, attach root disk để recovery |
| Stable device rescue | giữ thứ tự device ổn định hơn, hỗ trợ volume-backed instance từ microversion `2.87` |

Điểm quan trọng:

- legacy rescue không hỗ trợ volume-backed instance;
- stable device rescue hỗ trợ volume-backed instance;
- stable device rescue dùng image properties như `hw_rescue_device` và `hw_rescue_bus`;
- tính năng stable device rescue chỉ hỗ trợ với libvirt driver, không hỗ trợ LXC.

### 3. Workflow rescue

```text
1. nova-api nhận yêu cầu rescue
2. nova-conductor điều phối
3. nova-compute soft shutdown instance
4. compute chuẩn bị rescue image
5. root disk gốc được attach vào rescue environment
6. instance boot lên ở RESCUED
7. admin/user sửa lỗi trong disk
8. unrescue để boot lại từ root disk gốc
```

Trong rescue mode, một số thao tác như pause, suspend, stop không được phép vì có thể làm mất state gốc và khiến unrescue không an toàn.

### 4. Rescue không phải backup

Điểm cần nhớ:

```text
Rescue giúp truy cập disk để sửa lỗi.
Rescue không thay thế snapshot, backup hoặc replication.
```

Nếu dữ liệu quan trọng, nên có backup/snapshot trước khi sửa. Trong production, rescue chỉ là thao tác khôi phục tình huống, không phải chiến lược bảo vệ dữ liệu.

## VII. EVACUATE

### 1. Evacuate là gì?

**Evacuate** là rebuild hoặc đưa instance chạy lại trên compute host khác khi compute host hiện tại đã lỗi.

Use case:

```text
compute node chết
hypervisor hỏng
host mất nguồn
host mất network quản trị
```

Evacuate là thao tác sau sự cố. Không dùng evacuate cho host còn đang chạy bình thường. Nếu host còn chạy và cần bảo trì, ưu tiên live migration hoặc cold migration tùy tình huống.

### 2. Evacuate khác live migrate như nào?

| Tiêu chí | Live migration | Evacuate |
| -------- | -------------- | -------- |
| Source host còn hoạt động | Có | Không |
| VM tiếp tục chạy trong lúc move | Có | Không |
| Mục tiêu | bảo trì/cân tải | phục hồi sau lỗi host |
| Cần source compute phối hợp | Có | Không đáng tin cậy hoặc không có |
| Dữ liệu ephemeral local | có thể copy nếu block migration | có thể mất nếu không shared storage |

### 3. Dữ liệu khi evacuate

Điểm quan trọng nhất:

```text
Nếu muốn giữ dữ liệu trên ephemeral/root disk local, cần shared storage hoặc backend phù hợp.
```

Nếu instance boot từ volume:

- root disk nằm ở Cinder;
- evacuate thường an toàn hơn về dữ liệu root disk;
- vẫn phải xử lý network binding, volume attachment, state cleanup.

Nếu instance dùng ephemeral disk local trên host chết:

- dữ liệu đó có thể không truy cập được;
- Nova có thể rebuild từ image gốc;
- dữ liệu ghi trên ephemeral local sau khi boot có thể mất.

### 4. Workflow evacuate

```text
1. Admin xác nhận source compute thật sự down
2. nova-api nhận yêu cầu evacuate
3. nova-conductor tạo/recover workflow
4. scheduler chọn destination nếu không chỉ định host
5. Placement claim tài nguyên ở destination
6. destination compute rebuild/spawn instance
7. Neutron/Cinder cập nhật binding/attachment nếu cần
8. instance quay lại ACTIVE hoặc ERROR nếu fail
```

Từ compute API `2.14`, Nova có thể tự detect shared storage trong evacuate, không cần admin khai báo thủ công theo kiểu cũ.

### 5. Lưu ý

Trước khi evacuate cần chắc chắn:

- source compute không còn chạy instance đó;
- tránh split-brain, tức cùng một instance chạy ở hai host;
- fencing/power-off host lỗi là cực kỳ quan trọng trong môi trường production;
- hiểu rõ dữ liệu root disk/ephemeral nằm ở đâu;
- kiểm tra Neutron port và Cinder volume sau khi evacuate.

Evacuate dễ lỗi nếu:

- source host thực ra vẫn `up`;
- destination không đủ tài nguyên;
- instance có local ephemeral disk quan trọng nhưng không có shared storage;
- volume attachment còn kẹt ở source;
- Neutron port binding lỗi;
- cell mapping hoặc Placement allocation sai.

## VIII. SO SÁNH NHANH CÁC OPERATION

| Operation | Mục tiêu | Downtime | Đổi host | Đổi flavor | Khi dùng |
| --------- | -------- | -------- | -------- | ---------- | -------- |
| Cold migrate | chuyển VM sang host khác | Có | Có | Không | bảo trì, chấp nhận reboot |
| Live migrate | chuyển VM khi đang chạy | Rất thấp | Có | Không | bảo trì không muốn downtime |
| Resize | đổi kích thước VM | Có | Có thể | Có | tăng/giảm tài nguyên |
| Rescue | cứu lỗi guest/disk | Có | Không phải mục tiêu chính | Không | sửa lỗi boot, lấy dữ liệu |
| Evacuate | phục hồi VM từ host chết | Có | Có | Không | compute host lỗi |

## IX. QUAN HỆ VỚI SCHEDULER VÀ PLACEMENT

Các operation move/resize không chỉ là thao tác ở hypervisor. Chúng còn cần scheduler và Placement.

### 1. Scheduler

Scheduler quyết định destination host dựa trên:

- Availability Zone;
- host aggregate;
- flavor extra specs;
- image metadata;
- Placement candidates;
- server group policy;
- compute service state;
- filters và weighers.

### 2. Placement

Placement giữ thông tin:

- inventory;
- allocation;
- trait;
- resource provider aggregate;
- allocation candidates.

Khi move/resize, Nova phải đảm bảo allocation cuối cùng đúng với host đang chạy instance.

Ví dụ khái niệm:

```text
Before:
  VM allocation -> compute01

After migration confirm:
  VM allocation -> compute02
```

Nếu operation fail:

```text
DB state, migration record và Placement allocation có thể lệch nhau
```

Đây là lý do không nên sửa Placement allocation thủ công nếu chưa debug Nova state.

## X. LIÊN QUAN TỚI CELLS V2

Cells v2 ảnh hưởng mạnh tới các operation nâng cao.

Điểm cần nhớ:

- live migration chỉ trong cùng cell;
- cold migration/resize có thể có workflow phức tạp hơn nếu cross-cell;
- mỗi cell có DB và message queue riêng;
- conductor phải route RPC đúng cell;
- Placement vẫn là global service theo dõi resource providers.

Mô hình:

```text
API level
  nova-api
  nova-scheduler
  super conductor
  API DB

Cell 1
  nova-conductor
  nova-compute
  cell DB
  cell MQ

Cell 2
  nova-conductor
  nova-compute
  cell DB
  cell MQ
```

Khi debug migration trong multi-cell, cần biết instance đang thuộc cell nào.

## XI. LIÊN QUAN TỚI STORAGE

Storage quyết định rất nhiều tới migration.

### 1. Local ephemeral disk

Nếu instance dùng local ephemeral disk:

- cold migrate/resize có thể phải copy disk;
- block live migration phải copy disk;
- evacuate từ host chết có thể mất dữ liệu ephemeral nếu không shared storage.

### 2. Shared storage

Nếu `/var/lib/nova/instances` hoặc backend instance disk được shared:

- cold migrate/resize nhẹ hơn;
- live migration không cần copy disk local;
- evacuate có cơ hội giữ data tốt hơn;
- nhưng phải đảm bảo locking, performance và failure domain của storage.

### 3. Volume-backed instance

Nếu VM boot từ Cinder volume:

- root disk không nằm local trên compute;
- migration thường tập trung vào RAM, network, attachment;
- evacuate thường tốt hơn về dữ liệu root disk;
- volume attachment cleanup rất quan trọng khi lỗi.

## XII. LIÊN QUAN TỚI NETWORK

Trong migration/evacuate, Neutron phải xử lý port binding.

Luồng khái niệm:

```text
source host binding -> destination host binding
```

Rủi ro hay gặp:

- port binding destination fail;
- security group/OVN/Open vSwitch flow cập nhật chậm;
- live migration downtime tăng vì network chưa sẵn sàng;
- trunk/SR-IOV/vDPA port có yêu cầu riêng.

Trong OpenStack 2026.1, Nova có cải tiến liên quan việc pre-create TAP device cho OVN ports để giảm downtime trong live migration khi OVN bị tải cao.

## XIII. LIÊN QUAN TỚI CPU, NUMA, PCI, VGPU, VTPM

Live migration với workload nâng cao không đơn giản.

Các yếu tố cần kiểm tra:

| Yếu tố | Ảnh hưởng |
| ------ | --------- |
| CPU model | source/destination phải compatible |
| NUMA topology | cần host phù hợp, Placement và libvirt support |
| CPU pinning | cần dedicated CPU và NUMA placement đúng |
| Huge pages | destination phải còn page size phù hợp |
| PCI passthrough | cần cấu hình device live migratable nếu muốn live migrate |
| vGPU | phụ thuộc driver/hardware support |
| vDPA | có lifecycle và live migration yêu cầu riêng |
| vTPM | 2026.1 hỗ trợ live migration với `host` TPM secret security mode |

Best practice:

```text
Workload càng gần hardware thật thì migration càng cần test kỹ.
```

## XIV. GRACEFUL SHUTDOWN TRONG NOVA 2026.1

OpenStack 2026.1 đưa vào cơ chế graceful shutdown cho Nova services ở mức experimental.

Ý nghĩa:

- khi service nhận `SIGTERM`, service ngừng nhận RPC mới;
- các tác vụ đang chạy có thời gian đi tới điểm kết thúc an toàn;
- compute có thêm RPC server phụ để xử lý một số operation đang chạy.

Các operation được nhắc trong release notes:

- live migration;
- cold migration;
- resize;
- revert resize;
- external server event;
- get console output.

Điều này quan trọng vì migration/resize là operation dài. Nếu restart service quá thô, instance có thể kẹt ở state khó recover.

## XVI. TÓM TẮT DỄ NHỚ

```text
Cold migrate = move host, VM tắt/reboot, không đổi flavor
Live migrate = move host, VM vẫn chạy, downtime thấp
Resize = đổi flavor, có confirm/revert
Rescue = boot môi trường cứu hộ để sửa disk/guest
Evacuate = phục hồi instance khi compute host chết
```

Tư duy vận hành:

```text
Muốn bảo trì không downtime -> live migrate
Chấp nhận reboot -> cold migrate
Muốn tăng/giảm tài nguyên -> resize
VM không boot được -> rescue
Compute chết thật -> evacuate
```
