# Tìm hiểu về Policy trong OpenStack Keystone

Tài liệu này trình bày chi tiết về cách cấu hình, đọc hiểu file policy của Keystone và cách thay đổi quyền hạn (permissions) của user/project trong môi trường OpenStack.

## 1. Tổng quan về Policy trong Keystone

**Policy** trong OpenStack (nói chung) và Keystone (nói riêng) là cơ chế phân quyền (Authorization) dựa trên RBAC (Role-Based Access Control - Kiểm soát truy cập dựa trên vai trò).
Sau khi người dùng xác thực (Authentication) thành công và nhận được Token, Keystone sẽ dựa vào file Policy để quyết định xem Token đó (chứa role gì, thuộc project nào) có được phép thực hiện một hành động (API request) cụ thể hay không.

- **Vị trí file cấu hình:** Thường nằm ở `/etc/keystone/policy.json` (các bản cũ) hoặc `/etc/keystone/policy.yaml` (các bản OpenStack mới, từ Queens/Rocky trở lên ưu tiên dùng `YAML`).

- **Trạng thái mặc định:** Nếu không định nghĩa file policy, Keystone sẽ sử dụng policy mặc định được hardcode trong mã nguồn. Người quản trị có thể tạo file policy để "ghi đè" (override) các luật mặc định này.

## 2. Cấu trúc của file Policy

File policy định nghĩa một tập hợp các quy tắc (rules). Mỗi quy tắc gắn một **Action** (hành động, thường tương ứng với một API endpoint) với một **Rule** (điều kiện để thực hiện hành động đó).

### 2.1 Cấu trúc cơ bản

```json
{
    "hành_động_API": "điều_kiện_để_cho_phép"
}
```

#### Ví dụ với JSON (`policy.json`)

```json
{
    "admin_required": "role:admin",
    "identity:list_users": "rule:admin_required",
    "identity:get_user": "rule:admin_required or user_id:%(user_id)s"
}
```

#### Ví dụ với YAML (`policy.yaml`)

```yaml
"admin_required": "role:admin"
"identity:list_users": "rule:admin_required"
"identity:get_user": "rule:admin_required or user_id:%(user_id)s"
```

#### Phân tích

- **`"admin_required": "role:admin"`**: Đây là một *Alias* (bí danh/rule cơ bản). Nghĩa là điều kiện "admin_required" sẽ thỏa mãn nếu user có role là `admin`.

- **`"identity:list_users": "rule:admin_required"`**: Hành động liệt kê danh sách user (`identity:list_users`) chỉ được phép thực hiện nếu thỏa mãn rule `admin_required` (tức là user phải là admin).

- **`"identity:get_user": "rule:admin_required or user_id:%(user_id)s"`**: Hành động xem thông tin user được phép nếu người yêu cầu là admin, HOẶC người yêu cầu đang cố gắng xem thông tin của chính họ (trùng `user_id`).

## 3. Các thành phần chính trong điều kiện Policy

Điều kiện trong policy có thể sử dụng các toán tử logic để kết hợp:

- **`role:<role_name>`**: Kiểm tra xem user có role được chỉ định không (vd: `role:member`).

- **`rule:<rule_name>`**: Kế thừa một rule khác đã được định nghĩa.

- **`is_admin:True`**: Cờ báo hiệu user có quyền admin toàn hệ thống (thường do cấu hình `admin_token` hoặc role đặc quyền).

- **Toán tử so sánh (`:`)**: So sánh các thuộc tính trong Token với các thuộc tính của đối tượng đang bị thao tác. Ví dụ: `project_id:%(project_id)s` (User phải thuộc project đang thao tác).

- **Toán tử Logic (`and`, `or`, `not`)**: Kết hợp nhiều điều kiện. Ví dụ: `role:admin or role:project_admin`.

## 4. Cách thay đổi quyền hạn của User / Project

### Mục tiêu: Đọc hiểu và tinh chỉnh quyền

Giả sử bạn muốn thay đổi chính sách mặc định: "Chỉ admin mới được tạo Project", bạn muốn cho phép user có role `project_creator` cũng có quyền tạo project.

**Bước 1: Xác định Action tương ứng với API**
Hành động tạo project trong Keystone có action name là: `identity:create_project`.

**Bước 2: Chỉnh sửa file Policy (`/etc/keystone/policy.yaml`)**
Tìm dòng chứa `identity:create_project` và thay đổi nó.
*Mặc định:*

```yaml
"identity:create_project": "rule:admin_required"
```

*Sửa thành:*

```yaml
"identity:create_project": "rule:admin_required or role:project_creator"
```

**Bước 3: Khởi động lại dịch vụ Keystone**
Sau khi lưu file, bạn cần restart lại dịch vụ web server chạy Keystone (thường là Apache HTTPD hoặc uWSGI).

```bash
# Trên Ubuntu/Debian
sudo systemctl restart apache2

# Trên CentOS/RHEL
sudo systemctl restart httpd
```

**Bước 4: Kiểm tra lại quyền**
Tạo một user, gán role `project_creator` cho user đó và thử dùng user đó để chạy lệnh `openstack project create <name>`. Nếu thành công nghĩa là policy đã hoạt động.

## 5. Các công cụ hỗ trợ thao tác với Policy (oslo.policy CLI)

OpenStack cung cấp thư viện `oslo.policy` chứa các công cụ giúp quản trị viên dễ dàng làm việc với file policy.

- **`oslopolicy-policy-generator`**: Tạo ra file policy chứa tất cả các rule (bao gồm cả mặc định). Rất hữu ích khi bạn muốn xem toàn bộ quyền mặc định của Keystone.

```bash
# Tạo file policy chứa tất cả các rule mặc định của Keystone
oslopolicy-policy-generator --namespace keystone --output-file /tmp/keystone-policy.yaml
```

- **`oslopolicy-sample-generator`**: Tạo file policy mẫu.

- **`oslopolicy-checker`**: Kiểm tra xem một user có được phép thực hiện một API không dựa trên file policy hiện tại.
