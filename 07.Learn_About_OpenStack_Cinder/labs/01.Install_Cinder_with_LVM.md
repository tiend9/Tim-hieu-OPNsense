## II. SETUP MÔI TRƯỜNG VÀ QUY HOẠCH IP

### 1. Set up môi trường

- Phiên bản chúng ta chạy cho cụm lab này là **OpenStack - Zed**

- Backend Cinder ta dùng: LVM + iSCSI

  - Cinder Volume Group: `cinder-volumes`
  - iSCSI target IP: `10.0.0.7`

- 3 Node là VM trên VMWare , Node Compute chạy ảo hoá KVM và chạy hệ điều hành Ubuntu 22.04

  - Trên **Node Controller**, ta sẽ cài sẵn các gói NTP, MariaDB và KeyStone, Glance, Nova và cả Horizon (DashBoard), Rabbit MQ và quan trọng nhất cài Cinder control-plane: `cinder-api`, `cinder-scheduler`, database cho cinder. Ngoài ra ,thêm 3 endpoint public/internal/ admin và thêm `Region` trong `nova.conf` và cả placement service + nova-control-plane service(`nova-api`, `nova-scheduler`, `nova-conductor`, `nova-novncproxy`) + Neutron Services.

  - Trên **Node Compute**, ta cài sẵn các service `nova-compute`,`neutron-openvswitch-agent` (hoặc linuxbridge).

  - Trên **Storage Node**, ta cài Cinder và các service liên quan + cài đặt LVM. Ngoài ra cần thêm 1 Disk ảo thứ 2 (Ví dụ: `/dev/sdb`) trên VM này để tạo LVM Volume Group cho Cinder - Không dùng chung disk OS được.

- Ngoài ra mật khẩu thiết lập cho các service, các Databases của từng service và mật khẩu user `admin` trong OpenStack: `Tien123`

### `Bước 5`: Cài đặt Service nền trên Controller Node

Thực hiện trên **Controller Node**: Cài MariaDB, RabbitMQ và Memcached:

```bash
apt update
apt -y install mariadb-server python3-pymysql rabbitmq-server memcached python3-memcache
```

Cấu hình MariaDB cho OpenStack:

```bash
nano /etc/mysql/mariadb.conf.d/99-openstack.cnf

# Dán nội dung:
[mysqld]
bind-address = 10.0.0.5

default-storage-engine = innodb
innodb_file_per_table = on
max_connections = 4096
collation-server = utf8_general_ci
character-set-server = utf8
```

**Note**: Trường `innodb_file_per_table = on`. Cụ thể với MariaDB/MySQL InnoDB:

- Nếu `OFF`: nhiều table dùng chung tablespace hệ thống, thường là file ibdata1.
- Nếu `ON`: mỗi table có file riêng dạng:

```bash
/var/lib/mysql/<database>/<table>.ibd

# Ví dụ: database cinder có table <volumes>, <snapshots>, <backups> thì có các file riêng.

/var/lib/mysql/cinder/volumes.ibd
/var/lib/mysql/cinder/snapshots.ibd
/var/lib/mysql/cinder/backups.ibd

# => Lợi ích dễ quản lí dung lượng từng database/table.
# => Khi drop/truncate table, dung lượng file .ibd có thể thu hồi tốt hơn
# => Backup/restore hoặc tối ưu table linh hoạt hơn
# => Phù hợp vì Openstack có Nova, Neutron, Cinder, KeyStone tạo nhiều database/table riêng

# Restart MariaDB:
systemctl restart mariadb
systemctl enable mariadb
```

Thiết lập bảo mật MariaDB:

```bash
mysql_secure_installation

# Setup:

Enter current password for root (enter for none):  # Enter vì root chưa có pass

Switch to unix_socket authentication [Y/n] # No vì sau này phải sudo mới vào được database

Change the root password? [Y/n]            # Y (đặt password mới tại đây)

Remove anonymous users? [Y/n]              # → Y Bỏ ẩn danh

Disallow root login remotely? [Y/n]        # → n   (lab cần remote)

Remove test database? [Y/n]                # → Y (thừa)

Reload privilege tables? [Y/n]             # → Y (reload bảng quyền)
```

## `Bước 20`: Kiểm tra và hoàn thiện Metadata Service

### Tổng quan

**Metadata Service** cho phép VM lấy thông tin cấu hình của chính nó (hostname, SSH key, user-data...) qua địa chỉ đặc biệt `http://169.254.169.254` ngay khi boot — đây là địa chỉ **link-local** (RFC 3927), không cần internet.

> **Lưu ý về CirrOS:** CirrOS **có hỗ trợ metadata** (curl đến `169.254.169.254` hoạt động bình thường), nhưng DHCP client tối giản của nó **không áp dụng DHCP option 121** (classless static route) vào bảng routing. Do đó VM CirrOS sẽ không tự có route đến `169.254.169.254` sau khi nhận DHCP lease — cần add route thủ công để test:
>
> ```bash
> # Trong VM CirrOS — thay IP bằng IP DHCP server thực tế (xem trong file opts):
> sudo ip route add 169.254.169.254 via 192.168.122.100 dev eth0
> curl -s http://169.254.169.254/openstack/latest/meta_data.json
> ```
>
> Với Ubuntu/CentOS cloud image, DHCP client hỗ trợ option 121 đầy đủ nên route tự động được inject — không cần add tay.

Trong lab này ta dùng **provider network + Linux Bridge + DHCP agent** (không có router), nên luồng metadata đi qua **DHCP namespace**:

```text
VM (test-cirros)
  │  HTTP GET 169.254.169.254:80
  ▼
DHCP namespace (qdhcp-<network-id>)
  │  neutron-ns-metadata-proxy lắng nghe tại 169.254.169.254:80
  ▼
neutron-metadata-agent  (Unix Domain Socket)
  │  Thêm header: X-Instance-ID, X-Tenant-ID
  │  Tra cứu instance qua network-id + IP
  ▼
nova-api-metadata  (port 8775 trên Controller)
  │  Truy vấn DB → trả về metadata JSON
  ▼
VM nhận dữ liệu
```

> **Lưu ý:** Vì không có router/L3 agent, metadata **bắt buộc** phải đi qua DHCP agent. Tham số `enable_isolated_metadata = true` trong `dhcp_agent.ini` đã cấu hình ở Bước 11 là đúng — nhưng cần bổ sung thêm `force_metadata = true` để DHCP agent inject route `169.254.169.254` vào VM ngay cả khi không phải isolated network.

### a. Rà soát lại cấu hình đã làm (recap)

Các phần đã cấu hình rải rác trong lab:

| File | Section | Tham số đã có | Đánh giá |
|------|---------|--------------|----------|
| `/etc/neutron/metadata_agent.ini` | `[DEFAULT]` | `nova_metadata_host = controller`, `metadata_proxy_shared_secret = Tien123` |  Đủ |
| `/etc/nova/nova.conf` | `[neutron]` | `service_metadata_proxy = true`, `metadata_proxy_shared_secret = Tien123` |  Đủ |
| `/etc/neutron/dhcp_agent.ini` | `[DEFAULT]` | `enable_isolated_metadata = true` |  Thiếu `force_metadata` |

### b. Bổ sung `force_metadata` vào DHCP Agent (trên Controller)

`enable_isolated_metadata` chỉ bật metadata proxy khi mạng **không có gateway**. Mạng provider của ta có gateway `192.168.122.2` nên DHCP agent sẽ **không** tự inject route `169.254.169.254` → VM không thể reach metadata endpoint.

Cần thêm `force_metadata = true` để bắt buộc inject route dù mạng có gateway:

```bash
nano /etc/neutron/dhcp_agent.ini

# Đảm bảo section [DEFAULT] có đủ 3 dòng sau:
[DEFAULT]
interface_driver = linuxbridge
dhcp_driver = neutron.agent.linux.dhcp.Dnsmasq
enable_isolated_metadata = true
force_metadata = true
```

Sau đó restart DHCP agent:

```bash
systemctl restart neutron-dhcp-agent
systemctl status neutron-dhcp-agent --no-pager -l
```

> **Giải thích:**
>
> - `enable_isolated_metadata = true` → bật metadata proxy trong DHCP namespace
> - `force_metadata = true` → buộc inject route `169.254.169.254/32` vào DHCP response dù network có default gateway

Kiểm tra `neutron-ns-metadata-proxy` đang chạy bên trong namespace:

Kiểm tra địa chỉ `169.254.169.254` đã được gán vào interface trong namespace:


```bash
systemctl restart neutron-dhcp-agent
```

### f. Test metadata từ bên trong VM `test-cirros`

Đây là bước quan trọng nhất — xác nhận end-to-end.

SSH vào VM:

```bash
# Trên Controller:
ssh -i mykey.pem cirros@192.168.122.116
```

Trong VM, kiểm tra route đến `169.254.169.254`:

```bash
ip r

# Kỳ vọng thấy dòng:
# 169.254.169.254 via <dhcp-server-ip> dev eth0
# hoặc
# 169.254.169.254 dev eth0 src ...
```

Test metadata endpoint:

```bash
# Lấy danh sách API version:
curl -s http://169.254.169.254/openstack/

# Kỳ vọng:
# ["2012-08-10", "2013-04-04", ..., "latest"]

# Lấy metadata JSON của instance:
curl -s http://169.254.169.254/openstack/latest/meta_data.json

# Kỳ vọng trả về JSON chứa uuid, hostname, public_keys...
```

Ví dụ output khi thành công:

```json
{
  "uuid": "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx",
  "hostname": "test-cirros.novalocal",
  "availability_zone": "nova",
  "launch_index": 0,
  "public_keys": {
    "mykey": "ssh-rsa AAAA..."
  }
}
```

Kiểm tra thêm network-data và user-data:

```bash
curl -s http://169.254.169.254/openstack/latest/network_data.json

# CirrOS không truyền user-data khi tạo VM ở bước 14 nên sẽ trả về 404 — bình thường
curl -s http://169.254.169.254/openstack/latest/user_data
```

> **Lưu ý:** Nếu curl trả về trống/lỗi với VM CirrOS, **không phải do metadata stack sai** mà do CirrOS không có route đến `169.254.169.254` (DHCP client bỏ qua option 121). Cần add route tay `sudo ip route add 169.254.169.254 via 192.168.122.100 dev eth0` trong VM trước khi curl. Với Ubuntu/CentOS cloud image thì route được inject tự động qua DHCP.

### g. Troubleshoot nếu metadata không trả về

| Triệu chứng | Nguyên nhân | Cách xử lý |
|-------------|-------------|------------|
| `curl: (7) Failed to connect` | Không có route đến `169.254.169.254` trong VM | Kiểm tra `force_metadata = true` trong `dhcp_agent.ini`, restart dhcp-agent |
| `curl: (7) Failed to connect` | DHCP namespace chưa có metadata proxy | Kiểm tra `ip netns exec qdhcp-... ps aux \| grep metadata` |
| HTTP 500 | nova-api-metadata lỗi | `journalctl -u nova-api -n 50 --no-pager \| grep metadata` |
| HTTP 403 Forbidden | Shared secret không khớp | Kiểm tra `metadata_proxy_shared_secret` trong `nova.conf` và `metadata_agent.ini` phải giống nhau |
| HTTP 404 `/user_data` | Không truyền user-data khi tạo VM | Bình thường nếu không truyền `--user-data` lúc `server create` |
| Timeout | nova-api port 8775 không listen | `ss -lntp \| grep 8775` và kiểm tra `enabled_apis` trong `nova.conf` |
