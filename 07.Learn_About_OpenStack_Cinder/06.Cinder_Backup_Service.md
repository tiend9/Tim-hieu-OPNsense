## 1. Tổng quan về cinder-backup

`cinder-backup` là service của OpenStack Cinder dùng để **sao lưu dữ liệu volume ra một backup backend riêng**. Backup có thể được restore về volume mới hoặc restore đè vào volume gốc nếu đủ điều kiện.

Các chức năng chính:

- Tạo full backup của volume.
- Tạo incremental backup dựa trên backup trước đó.
- Backup từ snapshot.
- Backup volume đang `in-use` bằng `--force`.
- Restore backup về volume mới hoặc volume có sẵn.
- Delete backup.
- Export/import backup metadata để khôi phục sau thảm họa database.
- Report capability/trạng thái service cho Cinder.

### 1.1. Vì sao cần cinder-backup?

Snapshot thường nằm cùng backend với volume gốc. Nếu backend chính bị mất dữ liệu hoặc bị lỗi nghiêm trọng, snapshot cũng có thể mất theo. `cinder-backup` giúp đưa dữ liệu sang nơi lưu trữ khác:

- Swift/Object Storage.
- Ceph pool khác hoặc Ceph cluster khác.
- S3 hoặc S3-compatible object storage.
- NFS/POSIX filesystem.
- Google Cloud Storage.

### 1.2. cinder-backup không thay thế gì?

`cinder-backup` không thay thế:

- Backup database Cinder.
- Replication/snapshot native của storage backend.
- Disaster Recovery toàn cloud.
- Application-consistent backup bên trong guest.

Backup Cinder chủ yếu là **block-level backup**. Nếu volume đang gắn vào VM và dùng `--force`, backup thường chỉ đảm bảo **crash consistency**, không đảm bảo application consistency nếu ứng dụng chưa flush dữ liệu.

## 2. Vị trí của Backup Service trong kiến trúc Cinder

Kiến trúc đơn giản:

```text
User / CLI / Horizon / SDK
        |
        v
+----------------+
|   cinder-api   |
+----------------+
        |
        | RPC qua RabbitMQ / oslo.messaging
        v
+----------------+
| cinder-backup  |
| BackupManager  |
+----------------+
        |
        | đọc dữ liệu volume qua cinder-volume / attach nội bộ
        v
+----------------+          +----------------------+
| cinder-volume  | <------> | Primary storage      |
| volume driver  |          | Ceph/LVM/NFS/Array   |
+----------------+          +----------------------+
        |
        | ghi dữ liệu backup
        v
+----------------------+
| Backup backend       |
| Swift/Ceph/S3/NFS... |
+----------------------+
```

Các service liên quan:

| Service | Vai trò |
| ------- | ------- |
| `cinder-api` | Nhận API request backup/restore/delete, validate policy/quota, ghi DB, gọi RPC. |
| `cinder-backup` | Chạy backup driver, đọc dữ liệu volume và ghi sang backup backend. |
| `cinder-volume` | Quản lý volume gốc, hỗ trợ attach/internal copy/snapshot tùy driver và luồng. |
| `cinder-scheduler` | Có thể tham gia chọn backup host trong một số luồng hoặc khi cần backup service phù hợp. |
| Database | Lưu metadata backup, trạng thái, parent backup, container, service host. |
| RabbitMQ | Truyền RPC giữa API, backup, volume, scheduler. |
| Keystone | Xác thực user/service token. |
| Swift/S3/Ceph/NFS/GCS | Nơi lưu dữ liệu backup thật. |

## 3. Backup khác Snapshot như thế nào?

| Tiêu chí | Snapshot | Backup |
| -------- | -------- | ------ |
| Nơi lưu | Thường cùng backend với volume gốc. | Có thể ở backend riêng: Swift, Ceph backup pool, S3, NFS... |
| Mục tiêu | Rollback nhanh, clone nhanh, thao tác ngắn hạn. | Bảo vệ dữ liệu dài hạn, khôi phục sau sự cố backend chính. |
| Phụ thuộc volume gốc | Thường phụ thuộc backend/volume gốc. | Có thể restore khi volume gốc không còn, nếu metadata còn. |
| Hiệu năng | Nhanh hơn, native backend. | Chậm hơn vì phải copy dữ liệu. |
| Dung lượng | Có thể dùng copy-on-write. | Lưu object/chunk hoặc RBD object riêng. |
| DR | Không đủ nếu storage backend chết hoàn toàn. | Tốt hơn nếu backup backend độc lập. |

Kết luận:

- Dùng snapshot cho rollback ngắn hạn.
- Dùng backup cho bảo vệ dữ liệu lâu hơn và khôi phục sau sự cố.
- Với workload quan trọng, nên dùng cả snapshot, backup backend độc lập, và backup database Cinder.

## 4. Luồng xử lý khi tạo Backup

Ví dụ:

```bash
openstack volume backup create --name backup-db-001 db-volume
```

Luồng tổng quát:

```text
1. User gửi request tới cinder-api
2. cinder-api xác thực Keystone token
3. cinder-api kiểm tra policy và quota backup
4. cinder-api kiểm tra volume có trạng thái hợp lệ
5. cinder-api tạo record backup trong DB, trạng thái creating
6. cinder-api chọn cinder-backup host phù hợp
7. cinder-api gửi RPC create_backup tới cinder-backup
8. cinder-backup chuẩn bị đọc dữ liệu volume
9. cinder-backup gọi backup driver
10. backup driver chia dữ liệu thành chunk/object
11. backup driver ghi dữ liệu sang Swift/Ceph/S3/NFS/GCS
12. cinder-backup cập nhật DB: available hoặc error
```

### 4.1. Backup volume `available`

Đây là trường hợp an toàn nhất:

```bash
openstack volume backup create --name backup-vol-01 vol-01
```

Volume không gắn vào VM, dữ liệu ít thay đổi, backup dễ nhất quán hơn.

### 4.2. Backup volume `in-use`

Phải dùng `--force`:

```bash
openstack volume backup create --force --name backup-live-vol vol-01
```

Lưu ý:

- Backup `in-use` thường là crash-consistent.
- Nên phối hợp freeze filesystem/application trong VM nếu cần application consistency.
- Với database, nên dùng cơ chế backup của DB hoặc flush/freeze trước khi backup.

### 4.3. Backup từ snapshot

OpenStackClient hỗ trợ backup từ snapshot:

```bash
openstack volume backup create --snapshot snap-01 --name backup-from-snap vol-01
```

Cách này hữu ích khi muốn cố định một điểm thời gian trước khi backup.

### 4.4. Backup theo Availability Zone

OpenStackClient bản mới hỗ trợ:

```bash
openstack volume backup create --availability-zone az-backup-1 --name backup-az vol-01
```

Tùy triển khai, Cinder sẽ chọn backup service trong AZ phù hợp nếu có.

## 5. Luồng Restore Backup

Restore về volume mới:

```bash
openstack volume backup restore <backup-id>
```

Hoặc restore vào volume có sẵn:

```bash
openstack volume backup restore <backup-id> <volume-id>
```

Luồng tổng quát:

```text
1. User gửi restore request
2. cinder-api kiểm tra backup metadata và policy
3. Nếu restore ra volume mới, Cinder tạo volume mới đủ size
4. cinder-api gửi RPC restore_backup tới cinder-backup
5. cinder-backup đọc object/chunk từ backup backend
6. cinder-backup ghi dữ liệu về target volume
7. cinder-volume/driver hoàn tất ghi dữ liệu
8. Backup trở về available, target volume trở về available hoặc error
```

### 5.1. Restore về volume mới

Đây là phương án được khuyến nghị vì ít rủi ro với dữ liệu gốc:

```bash
openstack volume backup restore backup-db-001
```

Cinder tạo volume mới dựa trên size backup. Sau đó bạn có thể attach volume mới vào VM để kiểm tra.

### 5.2. Restore đè vào volume gốc hoặc volume có sẵn

```bash
openstack volume backup restore backup-db-001 vol-restore-target
```

Điều kiện:

- Volume đích phải tồn tại.
- Volume đích phải đủ lớn.
- Volume đích phải ở trạng thái hợp lệ, thường là `available`.
- Restore đè sẽ ghi dữ liệu backup vào volume đích, cần cực kỳ cẩn thận.

### 5.3. Restore incremental backup

Khi restore incremental backup, Cinder cần chuỗi backup cha:

```text
full backup -> incremental 1 -> incremental 2 -> backup cần restore
```

Nếu mất metadata hoặc object của backup cha, restore incremental có thể fail.

## 6. Thành phần nội bộ của cinder-backup

Các module/class chính:

| Module/Class | Vai trò |
| ------------ | ------- |
| `cinder.backup.api.API` | API nội bộ xử lý create/delete/restore/export/import backup. |
| `cinder.backup.manager.BackupManager` | Manager chạy trong `cinder-backup`, nhận RPC và điều phối driver. |
| `cinder.backup.rpcapi.BackupAPI` | RPC client để gọi backup service. |
| `cinder.backup.driver.BackupDriver` | Base class cho backup driver. |
| `cinder.interface.backup_driver.BackupDriver` | Interface tối thiểu mà backup driver phải hỗ trợ. |
| `cinder.backup.chunkeddriver.ChunkedBackupDriver` | Base driver cho các backend lưu theo chunk/object. |
| `cinder.objects.backup.Backup` | Object model lưu metadata backup trong DB. |

Theo API docs mới nhất, `BackupManager` quản lý các thao tác:

- `create_backup`
- `delete_backup`
- `restore_backup`
- `export_record`
- `import_record`
- `reset_status`
- `publish_service_capabilities`
- `check_support_to_force_delete`

RPC API của BackupManager trong docs latest là `2.4`. Điều này quan trọng khi rolling upgrade vì các service Cinder dùng RPC version pin để tương thích trong giai đoạn nâng cấp.

## 7. Backup Driver và nơi lưu dữ liệu

`backup_driver` quyết định dữ liệu backup được ghi đi đâu.

Các driver phổ biến trong Cinder 28.x:

| Driver | Class | Nơi lưu | Ghi chú |
| ------ | ----- | ------- | ------ |
| Swift | `cinder.backup.drivers.swift.SwiftBackupDriver` | OpenStack Swift/Object Storage | Driver mặc định trong sample config. |
| Ceph | `cinder.backup.drivers.ceph.CephBackupDriver` | Ceph RBD pool | Tối ưu khi volume gốc là Ceph RBD. |
| S3 | `cinder.backup.drivers.s3.S3BackupDriver` | AWS S3 hoặc S3-compatible | Phù hợp MinIO, Ceph RGW, object storage ngoài. |
| NFS | `cinder.backup.drivers.nfs.NFSBackupDriver` | NFS share | Dễ triển khai lab/on-prem, cần mount ổn định. |
| POSIX | `cinder.backup.drivers.posix.PosixBackupDriver` | Filesystem local/shared | Chỉ nên dùng lab hoặc môi trường nhỏ. |
| GCS | `cinder.backup.drivers.google.GoogleBackupDriver` | Google Cloud Storage | Phù hợp hybrid/public cloud. |

### 7.1. Chọn driver nào?

Khuyến nghị thực tế:

- Dùng **Swift** nếu cloud đã có OpenStack Swift ổn định.
- Dùng **CephBackupDriver** nếu primary storage là Ceph RBD và muốn hiệu năng tốt.
- Dùng **S3BackupDriver** nếu tổ chức đã có S3-compatible storage như Ceph RGW/MinIO.
- Dùng **NFS** cho lab, môi trường nhỏ, hoặc nơi có NAS enterprise đáng tin cậy.
- Tránh POSIX local nếu không có replication/backup ngoài node, vì mất node là mất backup.

### 7.2. Một deployment chỉ dùng một backup_driver?

Mỗi process `cinder-backup` chạy với một `backup_driver` trong file cấu hình của nó. Có thể chạy nhiều `cinder-backup` host với cấu hình khác nhau, nhưng cần thiết kế rõ cách Cinder chọn backup host và cách vận hành restore/delete. Môi trường production thường giữ một loại backup backend chính để giảm phức tạp.

## 8. Full Backup, Incremental Backup và Metadata

### 8.1. Full backup

Mặc định, Cinder tạo full backup:

```bash
openstack volume backup create --name full-001 vol-01
```

Full backup copy toàn bộ dữ liệu cần thiết của volume vào backup backend.

### 8.2. Incremental backup

Tạo incremental backup:

```bash
openstack volume backup create --incremental --name inc-001 vol-01
```

Điều kiện:

- Volume phải có ít nhất một backup trước đó.
- Backup driver phải hỗ trợ incremental theo cách của nó.
- Metadata backup cha phải còn trong DB.

Nếu không có backup cha, incremental backup sẽ fail.

### 8.3. Quan hệ parent-child

Incremental backup dựa trên backup có timestamp mới nhất của cùng volume. Một backup có dependent backups thường không thể xóa bình thường cho đến khi các backup phụ thuộc được xử lý.

Kiểm tra:

```bash
openstack volume backup show <backup-id>
```

Các field quan trọng:

- `is_incremental`
- `has_dependent_backups`
- `volume_id`
- `parent_id` nếu client/API hiển thị

### 8.4. Backup metadata

Cinder lưu metadata backup trong database. Metadata này quan trọng không kém dữ liệu object vì restore cần biết:

- Backup nằm ở driver nào.
- Container/bucket/pool nào.
- Object/chunk naming.
- Parent backup.
- Volume size.
- Encryption/key metadata nếu volume mã hóa.

Nếu database Cinder mất mà không có backup DB hoặc không export backup metadata, dữ liệu trong Swift/S3/Ceph có thể vẫn còn nhưng rất khó restore qua Cinder.

## 9. Cấu hình chung trong cinder.conf

Các option backup quan trọng trong `[DEFAULT]`:

```ini
[DEFAULT]
# API và manager
backup_api_class = cinder.backup.api.API
backup_manager = cinder.backup.manager.BackupManager

# Driver mặc định trong sample config
backup_driver = cinder.backup.drivers.swift.SwiftBackupDriver

# Compression: none/off/no, zlib/gzip, bz2/bzip2, zstd
backup_compression_algorithm = zlib

# Mới trong Cinder 28.0.0:
# Cho phép backup driver tự tạo container/bucket nếu backend hỗ trợ
backup_create_containers = true

# Metadata version dùng khi backup metadata volume
backup_metadata_version = 2

# Gửi progress notification định kỳ
backup_timer_interval = 120
backup_object_number_per_notification = 10

# Kiểm tra driver đã init thành công chưa
backup_driver_init_check_interval = 60
backup_driver_stats_polling_interval = 60

# Xử lý pending backup delete khi service start
backup_service_inithost_offload = true

# Thread/process/concurrency
backup_native_threads_pool_size = 60
backup_workers = 4
backup_max_operations = 15

# Khi backup volume in-use, ưu tiên snapshot tạm nếu driver hỗ trợ
backup_use_temp_snapshot = false

# Backup service dùng cùng backend/host logic
backup_use_same_host = false

# Service identity
host = backup01
storage_availability_zone = nova
```

### 9.1. `backup_create_containers`

Đây là option mới đáng chú ý trong Cinder 28.0.0:

```ini
backup_create_containers = true
```

Ý nghĩa:

- `true`: driver được phép tự tạo container/bucket/directory nếu backend hỗ trợ.
- `false`: operator phải tạo sẵn container/bucket/directory trước khi chạy backup.

Production có yêu cầu kiểm soát chặt naming, policy, encryption hoặc lifecycle có thể đặt:

```ini
backup_create_containers = false
```

Khi đó phải chuẩn bị sẵn container/bucket trên Swift/S3/NFS/Ceph tùy driver, nếu không backup sẽ fail.

### 9.2. `backup_workers`

```ini
backup_workers = 4
```

Trong Cinder 28.0.0 sample config, `backup_workers` có giới hạn tối đa 4. Tăng số này giúp xử lý backup đồng thời tốt hơn nhưng cũng tăng:

- CPU dùng cho compression.
- RAM.
- I/O đọc từ primary storage.
- Network tới backup backend.
- I/O ghi trên backup backend.

Không nên tăng nếu chưa đo bottleneck.

### 9.3. `backup_max_operations`

```ini
backup_max_operations = 15
```

Giới hạn số thao tác nặng bộ nhớ chạy đồng thời: backup và restore. `0` nghĩa là không giới hạn, không khuyến nghị cho production nếu volume lớn.

### 9.4. `backup_use_temp_snapshot`

```ini
backup_use_temp_snapshot = false
```

Nếu đặt `true`, Cinder sẽ tạo snapshot tạm để backup không gián đoạn khi driver hỗ trợ. Nếu `false`, Cinder có thể clone temporary volume để backup. Tùy backend, snapshot tạm có thể nhanh hơn hoặc ít I/O hơn.

## 10. Cấu hình Swift Backup Driver

Swift là driver mặc định trong sample config.

### 10.1. Cấu hình cơ bản

```ini
[DEFAULT]
backup_driver = cinder.backup.drivers.swift.SwiftBackupDriver

# Nếu để trống, Cinder có thể lấy Swift endpoint từ Keystone catalog
backup_swift_url = http://controller:8080/v1/AUTH_
backup_swift_container = volumebackups

# Swift auth mode
backup_swift_auth = per_user
backup_swift_auth_version = 3
backup_swift_auth_url = http://controller:5000/v3
```

### 10.2. `per_user` và `single_user`

```ini
backup_swift_auth = per_user
```

| Mode | Ý nghĩa | Khi dùng |
| ---- | ------- | -------- |
| `per_user` | Dùng thông tin user/project để ghi backup. | Phù hợp khi Swift ACL/quota theo project. |
| `single_user` | Dùng một service account chung. | Dễ vận hành hơn, thường dùng production private cloud. |

Ví dụ `single_user`:

```ini
[DEFAULT]
backup_swift_auth = single_user
backup_swift_auth_version = 3
backup_swift_auth_url = http://controller:5000/v3
backup_swift_user = cinder-backup
backup_swift_key = CINDER_BACKUP_SWIFT_PASS
backup_swift_project = service
backup_swift_user_domain = Default
backup_swift_project_domain = Default
backup_swift_container = volumebackups
```

### 10.3. Swift object size và incremental block size

```ini
backup_swift_object_size = 52428800
backup_swift_block_size = 32768
```

Ý nghĩa:

- `backup_swift_object_size`: kích thước object lưu trong Swift, mặc định khoảng 50 MB.
- `backup_swift_block_size`: block size dùng để track thay đổi cho incremental backup.
- `backup_swift_object_size` phải là bội số của `backup_swift_block_size`.

### 10.4. Retry, TLS và region

```ini
backup_swift_retry_attempts = 3
backup_swift_retry_backoff = 2
backup_swift_ca_cert_file = /etc/ssl/certs/ca-bundle.crt
backup_swift_auth_insecure = false

# Mới trong Cinder 28.0.0, hữu ích khi Keystone có nhiều region
backup_swift_region_name = RegionOne
```

Trong multi-region deployment, nên cấu hình `backup_swift_region_name` để Cinder dùng đúng Swift endpoint theo region. Nếu không, Cinder có thể chọn nhầm endpoint từ service catalog.

### 10.5. Service token cho Swift

```ini
backup_swift_service_auth = true

[service_user]
send_service_user_token = true
auth_type = password
auth_url = http://controller:5000/v3
project_domain_name = Default
user_domain_name = Default

```

Service token giúp các tác vụ dài như backup/restore không bị ảnh hưởng khi user token hết hạn giữa chừng. Cấu hình service token là khuyến nghị bảo mật quan trọng trong Cinder hiện đại.

## 11. Cấu hình Ceph Backup Driver

Ceph Backup Driver phù hợp khi:

- Primary volume backend là Ceph RBD.
- Muốn backup sang pool Ceph khác.
- Muốn tận dụng differential/incremental backup của RBD.
- Muốn backup giữa Ceph pool hoặc Ceph cluster khác.

### 11.1. Cấu hình cơ bản

```ini
[DEFAULT]
backup_driver = cinder.backup.drivers.ceph.CephBackupDriver
backup_ceph_conf = /etc/ceph/ceph.conf
backup_ceph_user = cinder-backup
backup_ceph_pool = backups
backup_ceph_chunk_size = 134217728
restore_discard_excess_bytes = true
```

### 11.2. Chuẩn bị Ceph pool

```bash
ceph osd pool create backups 128
ceph osd pool application enable backups rbd
rbd pool init backups
```

Tạo user:

```bash
ceph auth get-or-create client.cinder-backup \
  mon 'profile rbd' \
  osd 'profile rbd pool=backups, profile rbd-read-only pool=volumes' \
  mgr 'profile rbd pool=backups' \
  -o /etc/ceph/ceph.client.cinder-backup.keyring
```

Điều chỉnh quyền theo kiến trúc thực tế:

- Nếu backup cần đọc volume pool `volumes`, user cần quyền đọc trên pool đó.
- Nếu backup ghi vào pool `backups`, user cần quyền ghi trên pool `backups`.
- Nếu volume và backup ở cluster khác nhau, cần file conf/keyring phù hợp.

### 11.3. Incremental với Ceph RBD

Ceph Backup Driver có thể phát hiện source volume là RBD và cố gắng dùng differential backup. Nếu differential fail, driver fallback về full copy.

Lưu ý:

- Backup Ceph incremental có thể giữ snapshot trên source volume storage.
- Snapshot trên primary storage có thể tiêu tốn dung lượng đắt hơn backup storage.
- Cinder 28.x có `backup_ceph_max_snapshots` để giới hạn số snapshot gần nhất giữ lại.

```ini
backup_ceph_max_snapshots = 10
```

Ý nghĩa:

- `0`: giữ không giới hạn snapshot.
- `>0`: chỉ giữ số snapshot gần nhất trên source storage.

Trade-off:

- Giảm dung lượng snapshot trên primary storage.
- Nhưng nếu user xóa các backup còn snapshot chung, incremental tiếp theo có thể thành full backup.

### 11.4. RBD mirroring cho backup image

```ini
backup_ceph_image_journals = false
```

Nếu `true`, driver áp dụng feature `JOURNALING` và `EXCLUSIVE_LOCK` cho backup RBD objects để hỗ trợ mirroring. Chỉ bật khi thật sự cần RBD mirroring cho backup pool.

## 12. Cấu hình S3 Backup Driver

S3 driver dùng cho AWS S3 hoặc S3-compatible object storage như Ceph RGW, MinIO, Cloudian.

### 12.1. Cấu hình cơ bản

```ini
[DEFAULT]
backup_driver = cinder.backup.drivers.s3.S3BackupDriver
backup_s3_endpoint_url = https://s3.example.com
backup_s3_store_access_key = ACCESS_KEY
backup_s3_store_secret_key = SECRET_KEY
backup_s3_store_bucket = volumebackups
backup_s3_object_size = 52428800
backup_s3_block_size = 32768
backup_s3_verify_ssl = true
backup_s3_ca_cert_file = /etc/ssl/certs/ca-bundle.crt
```

### 12.2. Retry và connection pool

```ini
backup_s3_timeout = 60
backup_s3_max_pool_connections = 10
backup_s3_retry_max_attempts = 4
backup_s3_retry_mode = standard
```

Với object storage qua WAN hoặc endpoint không ổn định, tăng retry có thể giúp giảm lỗi tạm thời. Tuy nhiên retry quá nhiều làm tác vụ backup treo lâu hơn.

### 12.3. Proxy và TLS

```ini
backup_s3_http_proxy = http://proxy.example.com:8080
backup_s3_https_proxy = http://proxy.example.com:8080
backup_s3_verify_ssl = true
backup_s3_ca_cert_file = /etc/cinder/certs/object-ca.pem
```

Không nên đặt `backup_s3_verify_ssl = false` trên production trừ khi đang tạm debug.

### 12.4. Server-side encryption

```ini
backup_s3_sse_customer_algorithm = AES256
backup_s3_sse_customer_key = <base64-or-provider-specific-key>
```

Hai option này phải được đặt cùng lúc nếu muốn dùng SSE-C. Cần có quy trình bảo vệ key riêng; mất key là không restore được dữ liệu.

## 13. Cấu hình NFS/POSIX Backup Driver

### 13.1. NFS Backup Driver

```ini
[DEFAULT]
backup_driver = cinder.backup.drivers.nfs.NFSBackupDriver
backup_share = 192.168.10.20:/exports/cinder-backup
backup_mount_point_base = /var/lib/cinder/backup_mount
backup_mount_options = vers=4.1,sec=sys
backup_mount_attempts = 3
backup_container = volumebackups
backup_file_size = 1999994880
backup_sha_block_size_bytes = 32768
backup_enable_progress_timer = true
```

Chuẩn bị NFS:

```bash
mkdir -p /exports/cinder-backup
chown cinder:cinder /exports/cinder-backup
```

Kiểm tra mount từ node chạy backup:

```bash
showmount -e 192.168.10.20
mount -t nfs -o vers=4.1 192.168.10.20:/exports/cinder-backup /mnt
touch /mnt/test-from-cinder-backup
umount /mnt
```

### 13.2. POSIX Backup Driver

```ini
[DEFAULT]
backup_driver = cinder.backup.drivers.posix.PosixBackupDriver
backup_posix_path = /var/lib/cinder/backup
backup_container = volumebackups
backup_file_size = 1999994880
backup_sha_block_size_bytes = 32768
```

POSIX driver dễ dùng cho lab, nhưng production cần đảm bảo path là shared filesystem có redundancy. Nếu path chỉ là local disk của backup node, mất node/disk là mất backup.

GCS phù hợp khi:

## 17. Export/Import Backup Metadata

Backup Cinder phụ thuộc vào metadata trong database. Nếu mất DB, dữ liệu backup trong object store chưa chắc restore được. Có hai cách bảo vệ:

1. Backup toàn bộ database Cinder định kỳ.
2. Export metadata của các backup quan trọng.

### 17.1. Export metadata

Chạy với admin:

```bash
cinder backup-export <backup-id>
```

Output là metadata đã encode. Lưu output này vào nơi an toàn, tách khỏi Cinder DB.

### 17.2. Import metadata

Chạy với admin:

```bash
cinder backup-import <metadata>
```

Sau khi import thành công, có thể restore backup như bình thường:

```bash
openstack volume backup restore <backup-id>
```

### 17.3. Khi nào cần export/import?

- Di chuyển backup sang Cinder deployment khác.
- Khôi phục sau thảm họa DB.
- Chỉ muốn bảo vệ một số backup quan trọng thay vì cả DB.
- Di chuyển giữa region/cloud có cùng backup backend hoặc object data đã được copy.

### 17.4. Volume mã hóa

Nếu volume được mã hóa, metadata backup cần giữ thông tin liên quan tới key UUID. Phải đảm bảo key manager như Barbican cũng được backup/restore đúng, nếu không volume restore có thể không đọc được.

## 19. HA, Scaling và Performance

### 19.1. Chạy nhiều cinder-backup

Có thể chạy nhiều `cinder-backup` service để tăng khả năng xử lý:

```text
backup01: cinder-backup
backup02: cinder-backup
backup03: cinder-backup
```

Điều kiện:

- Cùng `backup_driver` và cùng backend nếu muốn restore/delete linh hoạt.
- Cấu hình Keystone/MQ/DB đồng nhất.
- Backend backup chịu được concurrency.
- Log tập trung để debug.

### 19.2. `backup_use_same_host`

```ini
backup_use_same_host = false
```

Option này ảnh hưởng cách Cinder chọn backup service host. Nếu có nhiều backup service dùng cùng backend hoặc cần locality, cần hiểu rõ trước khi bật. Mặc định `false` phù hợp đa số môi trường.

### 19.3. Backup host thay đổi

Nếu di chuyển backup node hoặc đổi hostname, backup records cũ có thể trỏ tới host cũ. Cinder có command quản trị:

```bash
cinder-manage backup list
cinder-manage backup update_backup_host --currenthost <old-host> --newhost <new-host>
```

Dùng khi đổi backup node và cần restore/delete backup cũ.

### 19.4. Giới hạn concurrency

Các option cần tune cùng nhau:

```ini
backup_workers = 4
backup_native_threads_pool_size = 60
backup_max_operations = 15
backup_compression_algorithm = zlib
```

Tác động:

- Compression dùng CPU.
- Backup/restore volume lớn dùng RAM và I/O.
- Object storage có thể rate limit.
- Primary storage có thể bị ảnh hưởng bởi backup đọc dữ liệu lớn.

### 19.5. Rate-limit volume copy bandwidth

Cinder có cơ chế giới hạn băng thông copy volume trong một số luồng bằng cấu hình liên quan tới volume copy. Nếu backup làm ảnh hưởng workload production, nên xem xét rate limit, schedule backup theo giờ thấp điểm, hoặc tách network backup riêng.

## 21. Các lỗi thường gặp

### 21.1. Không thấy cinder-backup service

Triệu chứng:

```bash
openstack volume service list
```

Không có `cinder-backup` hoặc state là `down`.

Kiểm tra:

```bash
systemctl status cinder-backup
journalctl -u cinder-backup -n 200
grep -E "ERROR|CRITICAL|Traceback" /var/log/cinder/cinder-backup.log
```

Nguyên nhân:

- Service chưa cài/chưa start.
- Sai `transport_url`.
- Sai DB connection.
- Backup driver init fail.
- Thiếu Python dependency của driver như boto3, google-api-python-client, rados/rbd.
- Credential backend sai.

### 21.2. Backup stuck ở `creating`

Nguyên nhân:

- Backup service chết giữa chừng.
- MQ mất kết nối.
- Object backend chậm hoặc treo.
- Volume lớn, backup vẫn đang chạy thật.
- Driver không update progress.

Kiểm tra:

```bash
openstack volume backup show <backup-id>
grep "<backup-id>" /var/log/cinder/cinder-backup.log
openstack volume service list
```

Không reset state vội nếu backend vẫn đang ghi dữ liệu.

### 21.3. Backup chuyển `error`

Kiểm tra log:

```bash
grep "<backup-id>" /var/log/cinder/cinder-backup.log | tail -100
grep -E "BackupDriverException|Traceback|ERROR" /var/log/cinder/cinder-backup.log
```

Nguyên nhân thường gặp:

- Swift/S3 bucket/container không tồn tại và `backup_create_containers = false`.
- Không có quyền ghi object.
- TLS/CA sai.
- Hết quota object storage.
- Ceph keyring sai quyền.
- NFS mount fail.
- Volume source bị detach/delete hoặc storage lỗi.

### 21.4. Swift backup fail

Log có thể có:

```text
Unauthorized
Container not found
Connection refused
SSLError
```

Kiểm tra:

```bash
openstack catalog show object-store
openstack container list
grep -E "backup_swift|swift_catalog_info|keystone_catalog_info" /etc/cinder/cinder.conf
```

Với multi-region, kiểm tra:

```ini
backup_swift_region_name = RegionOne
```

### 21.5. Ceph backup fail

Kiểm tra:

```bash
ceph -s
rbd -p backups ls --id cinder-backup
ceph auth get client.cinder-backup
ls -l /etc/ceph/
grep -E "backup_ceph|backup_driver" /etc/cinder/cinder.conf
```

Nguyên nhân:

- Pool `backups` chưa tạo hoặc chưa `rbd pool init`.
- Keyring thiếu quyền.
- `backup_ceph_user` không khớp file keyring.
- Ceph conf không có monitor đúng.
- Pool đầy hoặc gần full.

### 21.6. S3 backup fail

Kiểm tra:

```bash
grep -E "backup_s3|backup_driver" /etc/cinder/cinder.conf
curl -I https://s3.example.com
```

Nguyên nhân:

- Endpoint URL sai.
- Access key/secret key sai.
- Bucket chưa tồn tại.
- TLS CA sai.
- Proxy sai.
- S3-compatible backend không hỗ trợ option yêu cầu.

### 21.7. Không xóa được incremental backup

Thông báo thường liên quan tới dependent backups.

Kiểm tra:

```bash
openstack volume backup show <backup-id>
openstack volume backup list --long
```

Nếu `has_dependent_backups = True`, backup này là parent của backup khác. Cần xóa các backup con trước, hoặc dùng quy trình force/admin phù hợp sau khi hiểu rủi ro.

### 21.8. Restore fail

Nguyên nhân:

- Volume đích nhỏ hơn backup.
- Backup metadata thiếu hoặc không khớp backend.
- Backup object bị xóa/hỏng.
- Encryption key không còn trong Barbican.
- Driver hiện tại khác driver đã tạo backup.
- Backup service host cũ không còn và metadata host chưa được update.

Kiểm tra:

```bash
openstack volume backup show <backup-id>
openstack volume show <target-volume-id>
cinder-manage backup list
grep "<backup-id>" /var/log/cinder/cinder-backup.log
```

### 21.9. Token hết hạn trong backup dài

Backup/restore volume lớn có thể chạy lâu. Nếu dùng backend cần Keystone/Swift auth, token hết hạn có thể gây lỗi.

Khuyến nghị:

```ini
[service_user]
send_service_user_token = true
```

Với Swift:

```ini
backup_swift_service_auth = true
```

## 22. Best Practices cho Production

### 22.1. Tách backup backend khỏi primary storage

Không nên lưu backup cùng failure domain với volume gốc. Nếu dùng Ceph:

- Tốt: volume pool và backup pool khác nhau, replication/EC policy phù hợp.
- Tốt hơn: backup sang Ceph cluster khác hoặc object storage độc lập.
- Không tốt: backup cùng pool với volume production.

### 22.2. Backup Cinder database

Cinder docs nhấn mạnh backup phụ thuộc metadata trong DB. Cần backup:

- Cinder database.
- Keystone/Barbican nếu volume mã hóa.
- `cinder.conf` và keyring/credentials.
- Export metadata cho backup quan trọng.

### 22.3. Kiểm thử restore định kỳ

Backup không được kiểm thử restore thì chưa đáng tin.

Checklist test:

```bash
openstack volume backup create --name test-restore-backup test-volume
openstack volume backup restore test-restore-backup
openstack volume list
openstack server add volume test-vm <restored-volume>
```

Kiểm tra dữ liệu trong VM sau restore.

### 22.4. Dùng service token

Service token giúp tác vụ dài ổn định hơn và tránh một số rủi ro token/user session.

### 22.5. Giới hạn concurrency

Không để backup chạy không giới hạn:

```ini
backup_workers = 4
backup_max_operations = 15
```

Lên lịch backup theo batch, tránh giờ cao điểm.

### 22.6. Theo dõi capacity backup backend

Monitor:

- Dung lượng Swift/S3 bucket.
- Ceph pool `backups`.
- NFS filesystem usage.
- Object count.
- Tốc độ tăng backup.
- Số backup status `error`.
- Thời gian backup/restore trung bình.

### 22.7. Bảo mật credential

File cần bảo vệ:

```text
/etc/cinder/cinder.conf
/etc/ceph/ceph.client.cinder-backup.keyring
/etc/cinder/certs/*
```

Quyền file:

```bash
chown root:cinder /etc/cinder/cinder.conf
chmod 640 /etc/cinder/cinder.conf
```

Không commit access key/secret/keyring vào repo.

### 22.8. Chuẩn hóa naming

Ví dụ:

```text
<project>-<app>-<volume>-daily-YYYYMMDD
<project>-<app>-<volume>-weekly-YYYYWW
```

Metadata:

```bash
openstack volume backup create \
  --property retention=daily-14 \
  --property app=mysql \
  --property env=prod \
  --name prod-mysql-data-daily-20260507 \
  mysql-data
```

```bash
ceph osd pool create backups 128
ceph osd pool application enable backups rbd

ceph auth get-or-create client.cinder-backup \
  mon 'profile rbd' \
  osd 'profile rbd pool=backups, profile rbd-read-only pool=volumes' \
```

## 24. Những điểm mới trong Cinder 28.0.0 / OpenStack 2026.1

### 24.1. Baseline phiên bản

Tại ngày 2026-05-07:

- OpenStack mới nhất là **2026.1 Gazpacho**.
- Cinder stable tương ứng là **28.0.0**.
- Cinder `latest` là nhánh phát triển sau 28.0.0, nên production nên lấy 2026.1/28.0.0 làm baseline.

### 24.2. Option mới `backup_create_containers`

Cinder 28.0.0 thêm:

```ini
backup_create_containers = true
```

Option này kiểm soát việc backup driver có được tự tạo container/bucket/directory hay không. Khi đặt `false`, operator phải tạo sẵn container cho backup service.

Đây là thay đổi quan trọng cho môi trường production có policy object storage chặt chẽ.

### 24.3. Multi-region Swift

Cinder 28.0.0 bổ sung:

```ini
backup_swift_region_name = RegionOne
```

Option này giúp chọn đúng Swift endpoint trong Keystone service catalog khi triển khai nhiều region.

Release notes cũng nhắc option:

```ini
[glance]
region_name = RegionOne
```

Option Glance không phải backup option trực tiếp, nhưng liên quan các workflow volume-image trong multi-region deployment.

### 24.4. `backup_workers` giới hạn tối đa 4 trong sample Cinder 28.0.0

Sample config 2026.1 ghi `backup_workers` có maximum value 4. Khi nâng cấp từ bản cũ, cần kiểm tra lại nếu từng đặt giá trị cao hơn.

### 24.5. Không có thay đổi core backup flow lớn

Release notes 28.0.0 không nêu thay đổi lớn về kiến trúc core của `cinder-backup`. Các luồng create/restore/delete, full/incremental backup, export/import metadata vẫn giữ nguyên về mặt vận hành.

## 25. Tóm tắt nhanh

| Nội dung | Ghi nhớ |
| -------- | ------- |
| Service | `cinder-backup` sao lưu volume sang backend riêng. |
| Driver mặc định | `cinder.backup.drivers.swift.SwiftBackupDriver`. |
| Backend phổ biến | Swift, Ceph, S3, NFS/POSIX, GCS. |
| Full backup | Mặc định khi không dùng `--incremental`. |
| Incremental backup | Cần backup cha và driver hỗ trợ. |
| Backup in-use | Dùng `--force`, thường chỉ crash-consistent. |
| Restore an toàn | Restore về volume mới trước, kiểm tra rồi mới thay thế production. |
| Metadata | Cần DB Cinder hoặc `cinder backup-export`. |
| Cinder 28.0.0 mới | `backup_create_containers`, `backup_swift_region_name`. |
| Debug chính | `cinder-backup.log`, backup ID, request ID, service list. |

Checklist nhanh:

```bash
openstack volume service list
openstack volume backup list --long
openstack volume backup show <backup-id>
grep "<backup-id>" /var/log/cinder/cinder-backup.log
```
