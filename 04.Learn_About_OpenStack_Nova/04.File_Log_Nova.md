# FILE LOG NOVA

> Tài liệu này cập nhật theo **OpenStack 2026.1 Gazpacho**. Trọng tâm là cách Nova ghi log, vị trí file log, cách bật debug, cách đọc log theo luồng tạo VM, và cách gom log tập trung.

## I. LOG NOVA DÙNG ĐỂ LÀM GÌ?

Nova có nhiều service khác nhau, mỗi service xử lý một phần trong vòng đời của VM. Khi tạo VM lỗi, console không mở được, scheduler báo `NoValidHost`, RabbitMQ mất kết nối hoặc Placement trả lỗi, log là nơi đầu tiên cần xem.

Các log Nova giúp trả lời các câu hỏi:

- Request của user đã tới `nova-api` chưa?
- Nova có xác thực Keystone thành công không?
- Scheduler có hỏi Placement không?
- Placement trả về candidate host hay báo thiếu tài nguyên?
- `nova-compute` có nhận build request không?
- Libvirt/QEMU có boot instance thành công không?
- Neutron, Glance, Cinder có trả lỗi cho Nova không?

Khi debug Nova, không nên chỉ xem một file log. Phải đọc theo luồng:

```text
nova-api
  -> nova-scheduler
  -> placement
  -> nova-conductor
  -> nova-compute
  -> libvirt / qemu / neutron / glance / cinder
```

## II. CÁC FILE LOG THƯỜNG GẶP

Tùy distro và cách deploy, log có thể nằm trong file `/var/log/nova/*.log` hoặc trong `systemd-journald`. Với lab cài bằng package Ubuntu/RHEL, thường gặp các file sau.

### 1. Trên controller node

| File log | Service | Dùng để xem gì |
|----------|---------|----------------|
| `/var/log/nova/nova-api.log` | `nova-api` | Request REST API, auth Keystone, policy, quota, lỗi gọi service khác |
| `/var/log/nova/nova-scheduler.log` | `nova-scheduler` | Chọn compute host, lỗi `NoValidHost`, filter/weigher, Placement candidate |
| `/var/log/nova/nova-conductor.log` | `nova-conductor` | Truy cập DB thay cho compute, build/migrate state, RPC nội bộ |
| `/var/log/nova/nova-novncproxy.log` | `nova-novncproxy` | Lỗi console noVNC, token console, kết nối proxy tới compute |
| `/var/log/placement/placement-api.log` | Placement | Inventory/allocation, API `/allocation_candidates`, lỗi auth Placement |

Nếu Placement chạy sau Apache hoặc uwsgi, log HTTP cũng có thể nằm ở:

```text
/var/log/apache2/placement_access.log
/var/log/apache2/placement_error.log
/var/log/httpd/placement_access.log
/var/log/httpd/placement_error.log
```

### 2. Trên compute node

| File log | Service | Dùng để xem gì |
|----------|---------|----------------|
| `/var/log/nova/nova-compute.log` | `nova-compute` | Build VM, spawn libvirt, attach network/volume, update resource provider |
| `/var/log/libvirt/libvirtd.log` | libvirt | Lỗi libvirt daemon |
| `/var/log/libvirt/qemu/<instance>.log` | QEMU process | Lỗi QEMU/KVM của từng instance |
| `/var/log/neutron/*.log` | Neutron agent | Port binding, Linux Bridge/OVS/OVN, security group |

Trong nhiều lỗi thực tế, `nova-compute.log` chỉ nói "build failed", còn nguyên nhân gốc nằm ở Neutron, libvirt hoặc QEMU log.

## III. CẤU HÌNH LOG TRONG `nova.conf`

Nova dùng thư viện `oslo.log`, nên các option log nằm trong group `[DEFAULT]` của `/etc/nova/nova.conf`.

Ví dụ cấu hình cơ bản:

```ini
[DEFAULT]
debug = false
log_dir = /var/log/nova
use_stderr = false
```

Ý nghĩa:

| Option | Ý nghĩa |
|--------|---------|
| `debug` | `true` thì ghi log mức DEBUG; mặc định là INFO |
| `log_file` | Ghi log vào một file cụ thể |
| `log_dir` | Thư mục chứa log nếu `log_file` là relative path |
| `use_stderr` | Ghi log ra stderr, hay gặp khi chạy service trong container/systemd |
| `use_journal` | Ghi log vào systemd journal |
| `use_syslog` | Gửi log vào syslog |
| `syslog_log_facility` | Facility syslog, ví dụ `LOG_LOCAL0` |
| `use_json` | Ghi log dạng JSON, hữu ích cho log pipeline hiện đại |
| `log_rotation_type` | Rotate log theo `interval`, `size` hoặc `none` |
| `max_logfile_size_mb` | Dung lượng tối đa nếu rotate theo size |
| `max_logfile_count` | Số file log rotated giữ lại |
| `log_config_append` | Dùng file cấu hình logging riêng của Python |

### 1. Bật debug tạm thời

Khi cần debug sâu:

```ini
[DEFAULT]
debug = true
```

Sau đó restart service cần debug:

```bash
systemctl restart nova-api nova-scheduler nova-conductor nova-novncproxy
systemctl restart nova-compute
```

Không nên bật `debug = true` lâu trong production vì log rất nhiều, có thể làm đầy disk và lộ thông tin nhạy cảm.

### 2. Dùng `log_config_append`

Option mới nên dùng là:

```ini
[DEFAULT]
log_config_append = /etc/nova/logging.conf
```

Không nên dùng option cũ:

```ini
log-config = /etc/nova/logging.conf
```

`log-config` là tên cũ đã bị deprecate. Khi dùng `log_config_append`, các option log khác như `log_dir`, `log_file`, `use_syslog`, `log_date_format` có thể bị bỏ qua vì toàn bộ logging được điều khiển bởi file logging riêng.

Ví dụ `/etc/nova/logging.conf` đơn giản:

```ini
[loggers]
keys = root, nova

[handlers]
keys = stderr

[formatters]
keys = context

[logger_root]
level = WARNING
handlers = stderr

[logger_nova]
level = INFO
handlers = stderr
qualname = nova

[handler_stderr]
class = StreamHandler
args = (sys.stderr,)
formatter = context

[formatter_context]
class = oslo_log.formatters.ContextFormatter
```

## IV. XEM LOG BẰNG FILE VÀ JOURNALD

### 1. Xem log file trực tiếp

Xem log mới nhất:

```bash
tail -f /var/log/nova/nova-api.log
tail -f /var/log/nova/nova-scheduler.log
tail -f /var/log/nova/nova-compute.log
```

Tìm lỗi:

```bash
grep -i "error\|traceback\|failed\|novalidhost" /var/log/nova/*.log
```

Tìm theo UUID instance:

```bash
grep -R "<instance-uuid>" /var/log/nova /var/log/neutron /var/log/libvirt
```

Tìm theo request ID:

```bash
grep -R "req-xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx" /var/log/nova
```

### 2. Xem log qua `journalctl`

Nếu service ghi log vào journald:

```bash
journalctl -u nova-api -n 100 --no-pager
journalctl -u nova-scheduler -n 100 --no-pager
journalctl -u nova-conductor -n 100 --no-pager
journalctl -u nova-novncproxy -n 100 --no-pager
journalctl -u nova-compute -n 100 --no-pager
```

Theo dõi realtime:

```bash
journalctl -u nova-compute -f
```

Xem từ một thời điểm:

```bash
journalctl -u nova-compute --since "2026-05-26 10:00:00"
```

## V. ĐỌC LOG THEO LUỒNG TẠO VM

Khi chạy lệnh tạo VM, thêm `--debug` để lấy request URL, response code và request ID:

```bash
openstack --debug server create \
  --flavor m1.small \
  --image cirros \
  --network provider \
  vm-test
```

Sau đó debug theo thứ tự sau.

### 1. `nova-api.log`

Kiểm tra request có tới Nova không:

```bash
grep -i "server create\|POST /servers\|req-" /var/log/nova/nova-api.log
```

Các lỗi hay gặp:

| Dấu hiệu | Nguyên nhân thường gặp |
|----------|------------------------|
| `401 Unauthorized` | Sai token, Keystone auth lỗi |
| `403 Forbidden` | Policy/RBAC không cho phép |
| `Quota exceeded` | Hết quota instance, core hoặc RAM |
| `Failed to connect to Placement` | Sai endpoint/auth Placement |
| `Failed to allocate network` | Nova gọi Neutron lỗi |

### 2. `nova-scheduler.log`

Nếu VM kẹt `BUILD` rồi chuyển `ERROR`, hoặc CLI báo `No valid host was found`, xem scheduler:

```bash
grep -i "novalidhost\|allocation_candidates\|selected host\|filter" /var/log/nova/nova-scheduler.log
```

Các nguyên nhân phổ biến:

- Compute service down hoặc disabled.
- Placement không thấy resource provider của compute.
- Flavor yêu cầu nhiều CPU/RAM/disk hơn cloud còn lại.
- Image/flavor extra specs yêu cầu trait không host nào có.
- Host aggregate hoặc availability zone không khớp.
- PCI/GPU/SR-IOV resource không đủ.

### 3. Placement log

Nếu scheduler không tìm được host, kiểm tra Placement:

```bash
grep -i "allocation_candidates\|resource provider\|inventory\|allocation" /var/log/placement/placement-api.log
```

Kiểm tra bằng CLI:

```bash
openstack resource provider list
openstack allocation candidate list \
  --resource VCPU=1 \
  --resource MEMORY_MB=512 \
  --resource DISK_GB=1
```

Các lệnh Placement yêu cầu plugin `osc-placement` trong OpenStackClient.

### 4. `nova-conductor.log`

`nova-conductor` thường ghi lỗi liên quan DB, object state, migration state hoặc RPC giữa controller và compute:

```bash
grep -i "traceback\|build\|migrate\|database\|rpc" /var/log/nova/nova-conductor.log
```

Nếu conductor lỗi, compute có thể không lấy được state hoặc không update được trạng thái instance.

### 5. `nova-compute.log`

Trên compute node được chọn:

```bash
grep -R "<instance-uuid>" /var/log/nova/nova-compute.log
```

Các lỗi hay gặp:

| Dấu hiệu | Kiểm tra thêm |
|----------|---------------|
| `libvirtError` | `/var/log/libvirt/libvirtd.log`, QEMU log |
| `PortBindingFailed` | Neutron agent, OVS/Linux Bridge/OVN |
| `ImageNotFound` | Glance image, endpoint Glance |
| `VolumeNotFound` hoặc attach lỗi | Cinder, iSCSI, os-brick |
| `No disk space left` | Disk compute, image cache, ephemeral storage |

## VI. LOG CONSOLE CỦA INSTANCE

Log Nova service khác với log boot bên trong VM. Khi muốn xem output console của VM:

```bash
openstack console log show <server>
```

Giới hạn số dòng:

```bash
openstack console log show --lines 100 <server>
```

Lệnh này hữu ích khi:

- VM boot lỗi.
- VM không nhận DHCP.
- SSH không vào được.
- Cloud-init lỗi.

Nếu dùng serial console tương tác, xem thêm tài liệu VNC/console ở file `06.Process_Managing_VNC.md`.

## VII. GOM LOG TẬP TRUNG BẰNG RSYSLOG

Trong lab nhỏ, mỗi node giữ log local vẫn đủ. Trong môi trường nhiều compute node, nên gom log về một log server để debug theo timeline.

Mô hình:

```text
controller ─┐
compute01  ├──> log-server
compute02  ┘
```

### 1. Cấu hình log server nhận log TCP

Trên log server, tạo file:

```bash
/etc/rsyslog.d/10-openstack-server.conf
```

Nội dung:

```conf
module(load="imtcp")
input(type="imtcp" port="10514")

template(
  name="OpenStackPerHost"
  type="string"
  string="/var/log/remote/%HOSTNAME%/%programname%.log"
)

if ($programname startswith "nova") then {
  action(type="omfile" dynaFile="OpenStackPerHost")
  stop
}
```

Restart rsyslog:

```bash
systemctl restart rsyslog
ss -lntp | grep 10514
```

### 2. Cấu hình node gửi log

Trên controller/compute, tạo file:

```bash
/etc/rsyslog.d/60-openstack-client.conf
```

Ví dụ gửi log tới log server:

```conf
*.* @@<log-server-ip>:10514
```

Restart:

```bash
systemctl restart rsyslog
```

Sau đó log server sẽ có dạng:

```text
/var/log/remote/controller/nova-api.log
/var/log/remote/controller/nova-scheduler.log
/var/log/remote/compute01/nova-compute.log
```

Trong production, thường dùng pipeline như rsyslog/Fluentd/Vector/Filebeat -> Elasticsearch/OpenSearch/Loki/Splunk.

## VIII. JSON LOG VÀ JOURNALD

Nếu log được đẩy vào hệ thống phân tích tập trung, có thể bật JSON log:

```ini
[DEFAULT]
use_json = true
```

Nếu chạy trong môi trường systemd và muốn dùng journal native:

```ini
[DEFAULT]
use_journal = true
```

Lưu ý:

- Không bật quá nhiều kiểu output cùng lúc nếu không cần.
- Nếu dùng `log_config_append`, các option như `use_json`, `use_journal`, `use_syslog` có thể không còn hiệu lực.
- Với container/Kolla/OpenStack-Ansible, log path có thể khác package truyền thống.

## IX. DEBUG NHANH THEO TRIỆU CHỨNG

| Triệu chứng | File/lệnh nên xem |
|-------------|-------------------|
| Tạo VM bị `NoValidHost` | `nova-scheduler.log`, Placement log, `openstack resource provider list` |
| VM stuck `BUILD` | `nova-api.log`, `nova-conductor.log`, `nova-compute.log` |
| VM chuyển `ERROR` ngay khi boot | `nova-compute.log`, libvirt/QEMU log |
| Console noVNC không mở | `nova-novncproxy.log`, `[vnc] novncproxy_base_url`, firewall port `6080` |
| VM không có IP | Neutron agent log, DHCP agent, port binding |
| Boot from volume lỗi | `nova-compute.log`, `cinder-volume.log`, iSCSI/os-brick |
| Migration lỗi | `nova-conductor.log`, `nova-compute.log` trên source/destination, libvirt log |
| Placement auth lỗi | `/var/log/placement/placement-api.log`, section `[placement]` trong `nova.conf` |

Checklist ngắn khi debug:

```bash
openstack compute service list
openstack hypervisor list
openstack server show <server>
openstack console log show --lines 100 <server>
openstack resource provider list
```

## X. TỔNG KẾT

Log Nova phải đọc theo luồng, không đọc rời từng file. Với lỗi tạo VM, bắt đầu từ `nova-api`, đi qua `nova-scheduler`, Placement, `nova-conductor`, rồi tới `nova-compute`. Với lỗi boot thật sự, phải xem thêm libvirt, QEMU, Neutron, Glance hoặc Cinder.

Các điểm cần nhớ:

- `debug = true` chỉ bật khi cần debug.
- `log_config_append` là option mới thay cho `log-config`.
- `request_id` và `instance_uuid` là chìa khóa để nối log giữa nhiều service.
- `NoValidHost` thường liên quan Placement, resource, aggregate, trait hoặc compute service.
- Log boot của VM xem bằng `openstack console log show`, không phải log service Nova.
