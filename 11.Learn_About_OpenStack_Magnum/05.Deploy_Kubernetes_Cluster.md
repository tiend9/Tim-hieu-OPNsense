# DEPLOY CỤM KUBERNETES VỚI MAGNUM

> **Phiên bản tham chiếu**: OpenStack **2026.1 Gazpacho** + Magnum **18.x**

## I. CÂU LỆNH TẠO CLUSTER TỪ CLUSTERTEMPLATE

Sau khi đã chuẩn bị xong bản thiết kế (ClusterTemplate), người dùng có thể bắt đầu tạo lập cụm Kubernetes Cluster vật lý. Lệnh khởi tạo của Magnum sẽ kích hoạt Heat chạy ngầm để xây dựng cơ sở hạ tầng.

### Cú pháp tạo cụm Kubernetes

Sử dụng lệnh `openstack coe cluster create` để khởi chạy cụm máy chủ:

```bash
source /etc/kolla/admin-openrc

# Tạo cluster mang tên "k8s-production-cluster":
openstack coe cluster create \
  --cluster-template k8s-prod-template \
  --master-count 1 \
  --node-count 2 \
  k8s-production-cluster
```

**Các tham số chính**:

- **`--cluster-template`**: Tên hoặc UUID của ClusterTemplate đã định nghĩa từ trước (ví dụ: `k8s-prod-template`).
- **`--master-count`**: Số lượng máy ảo làm Master Node.
  - *Lab/Test*: Đặt bằng `1`.
  - *Production HA*: Bắt buộc đặt bằng `3` để đảm bảo cơ chế High Availability cho Etcd và API Server.
- **`--node-count`**: Số lượng máy ảo làm Worker Node chạy ứng dụng ban đầu (ví dụ: `2`). Số lượng này có thể dễ dàng co giãn (scale-up/down) sau khi chạy.
- **`k8s-production-cluster`**: Tên định danh của cụm Kubernetes.

## II. THEO DÕI TIẾN TRÌNH TẠO CLUSTER

Quá trình khởi tạo cụm Kubernetes thường mất từ **5 đến 15 phút** tùy thuộc vào hiệu năng của ổ cứng lưu trữ và tốc độ mạng Internet (để tải về các Docker images của hệ thống K8s). Magnum sẽ gọi Heat xây dựng hạ tầng, khởi động CoreOS, cài đặt Kubelet và tạo lập mạng CNI.

### 1. Kiểm tra trạng thái danh sách cụm

```bash
# Kiểm tra danh sách các cluster đang chạy và trạng thái:
openstack coe cluster list
```

**Output mẫu trong quá trình cài đặt**:

```text
+--------------------------------------+------------------------+--------------------+--------------------+
| uuid                                 | name                   | keypair            | status             |
+--------------------------------------+------------------------+--------------------+--------------------+
| d9c8b7a6-1234-abcd-efgh-0123456789ab | k8s-production-cluster | magnum-ssh-key     | CREATE_IN_PROGRESS |
+--------------------------------------+------------------------+--------------------+--------------------+
```

### 2. Xem chi tiết tiến trình khởi tạo

Để biết tiến độ cụ thể và cấu hình mạng đã hoàn thành đến đâu, chạy lệnh:

```bash
openstack coe cluster show k8s-production-cluster
```

**Các trạng thái vòng đời của Cluster**:

- **`CREATE_IN_PROGRESS`**: Magnum đang kết hợp với Heat để dựng VM, thiết lập certificate và cài đặt Kubernetes.
- **`CREATE_COMPLETE`**: Cụm Kubernetes đã cài đặt thành công, các node đã gia nhập cụm và API Server sẵn sàng tiếp nhận kết nối.
- **`CREATE_FAILED`**: Đã xảy ra lỗi hệ thống trong quá trình cài đặt hạ tầng hoặc cấu hình phần mềm trên node.

## III. XEM LOG HEAT STACK KHI GẶP LỖI (CREATE_FAILED)

Khi trạng thái cluster chuyển sang `CREATE_FAILED`, Magnum API thường chỉ hiển thị thông báo lỗi chung chung. Vì Magnum gọi Heat để tạo hạ tầng, ta bắt buộc phải truy cập trực tiếp dịch vụ Heat để xem lịch sử sự kiện (Events) và phát hiện tài nguyên lỗi cụ thể.

```text
  [Magnum Cluster: CREATE_FAILED]
               │
               ▼ (Tìm kiếm Stack tương ứng trong Heat)
  [Heat Stack: k8s-production-cluster-xxxx]
               │
               ▼ (Kiểm tra sự kiện lỗi cụ thể)
  [Lỗi chi tiết: Quota Exceeded / Octavia LB Timeout / Glance Image missing metadata]
```

### Quy trình Troubleshooting chi tiết

```bash
# 1. Liệt kê danh sách các Stack đang chạy trong Heat:
openstack stack list

# Tìm stack có tên tương tự dạng: "k8s-production-cluster-lx425tgshdf"

# 2. Liệt kê toàn bộ các sự kiện của Stack để tìm điểm lỗi (FAILED):
openstack stack event list k8s-production-cluster-lx425tgshdf

# 3. Lọc trực tiếp tài nguyên bị lỗi khởi tạo:
openstack stack resource list k8s-production-cluster-lx425tgshdf --filter status=FAILED
```

**Các nguyên nhân lỗi phổ biến nhất**:

- **`QuotaExceeded`**: Tài khoản Tenant bị hết hạn mức (Quota) về số lượng vCPUs, RAM, Security Groups, hoặc số lượng IP Floating trong Neutron.
- **`Octavia LB Provisioning Timeout`**: Dịch vụ Octavia không thể tạo Load Balancer cho Master API (thường do lỗi kết nối mạng quản trị amphora hoặc thiếu tài nguyên Compute chạy VM Amphora).
- **`Glance Image Metadata error`**: Image CoreOS quên không cấu hình thuộc tính `os_distro=fedora-coreos`, dẫn đến việc các driver phần mềm không thể kích hoạt trên node.

## IV. LẤY KUBECONFIG VÀ KẾT NỐI VÀO CỤM

Khi trạng thái cụm K8s đã chuyển sang **`CREATE_COMPLETE`**, ta cần lấy file cấu hình xác thực `kubeconfig` từ Magnum để dùng công cụ `kubectl` quản trị cụm.

Magnum cung cấp cơ chế tự động ký chứng chỉ TLS Client và đóng gói file cấu hình thông qua câu lệnh CLI:

### 1. Tạo thư mục lưu trữ cấu hình bảo mật

```bash
# Tạo thư mục lưu trữ chứng chỉ trên máy quản trị:
mkdir -p ~/k8s-production-config
```

### 2. Tải file cấu hình và chứng chỉ xác thực

```bash
# Lấy file config từ Magnum lưu vào thư mục vừa tạo:
openstack coe cluster config k8s-production-cluster --dir ~/k8s-production-config
```

Lệnh này sẽ tự động tải về thư mục chỉ định các file:

- `config`: File cấu hình Kubernetes Context (chứa token, API Endpoint IP và trỏ đường dẫn chứng chỉ).
- `ca.pem`, `cert.pem`, `key.pem`: Các chứng chỉ TLS Client giúp xác thực bảo mật lớp mã hóa API.

### 3. Thiết lập biến môi trường để sử dụng

```bash
# Khai báo biến KUBECONFIG chỉ tới file config vừa tải:
export KUBECONFIG=~/k8s-production-config/config

# (Tùy chọn) Lưu vĩnh viễn vào profile của shell:
echo "export KUBECONFIG=~/k8s-production-config/config" >> ~/.bashrc
```

## V. KIỂM TRA CÁC NODE ĐÃ READY CHƯA

Sau khi cấu hình xong biến môi trường `KUBECONFIG`, ta có thể sử dụng các lệnh tiêu chuẩn của Kubernetes để kiểm tra trạng thái hoạt động thực tế bên trong cụm.

### 1. Kiểm tra danh sách Node

```bash
# Kiểm tra danh sách các Node Master và Worker:
kubectl get nodes -o wide
```

**Output mong đợi**:

```text
NAME                                         STATUS   ROLES                  AGE   VERSION   INTERNAL-IP      EXTERNAL-IP
k8s-production-cluster-master-0              Ready    control-plane,master   12m   v1.27.3   192.168.200.15   10.10.10.120
k8s-production-cluster-node-0                Ready    <none>                 10m   v1.27.3   192.168.200.32   None
k8s-production-cluster-node-1                Ready    <none>                 10m   v1.27.3   192.168.200.41   None
```

### 2. Kiểm tra trạng thái hoạt động của Core Pods

```bash
# Đảm bảo toàn bộ các Pod quản trị hệ thống đều ở trạng thái Running:
kubectl get pods -n kube-system
```

**Kiểm tra các thành phần cốt lõi**:

- **CNI Pods (Calico/Flannel)**: Phải ở trạng thái `Running` để thiết lập mạng giữa các Pod.
- **CoreDNS**: Chịu trách nhiệm phân giải DNS nội bộ cụm.
- **Kube-Proxy**: Điều phối Service Port routing.
- **OpenStack Cloud Controller Manager (CCM)**: Pod tích hợp giúp Kubernetes tương tác trực tiếp với các API Nova, Neutron và Cinder của OpenStack.
