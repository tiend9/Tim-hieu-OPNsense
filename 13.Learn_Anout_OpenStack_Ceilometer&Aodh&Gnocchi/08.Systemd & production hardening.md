# SYSTEMD & PRODUCTION HARDENING CHO TELEMETRY, GNOCCHI & AODH

> **Phiên bản tham chiếu**: OpenStack **2026.1 Gazpacho**

## I. TELEMETRY VÀ CEILOMETER — QUẢN LÝ SYSTEMD VÀ THIẾT LẬP LOGGING TRONG PRODUCTION

Để đưa hệ thống giám sát vào vận hành thực tế ở quy mô lớn, việc kiểm soát tài nguyên tiến trình và tối ưu hóa hệ thống ghi log của Ceilometer là vô cùng quan trọng.

### 1. Quản lý các dịch vụ bằng Systemd

Các tiến trình Ceilometer được cấu trúc hóa dưới dạng các Systemd Unit chuẩn, cho phép tự động khởi động lại khi lỗi và giới hạn tài nguyên hệ thống (CPU/RAM).

#### a. Systemd Unit cho Notification Agent (`/etc/systemd/system/ceilometer-agent-notification.service`)

```ini
[Unit]
Description=OpenStack Ceilometer Notification Agent
After=syslog.target network.target

[Service]
Type=simple
User=ceilometer
ExecStart=/openstack/venvs/ceilometer/bin/ceilometer-agent-notification --config-file=/etc/ceilometer/ceilometer.conf
Restart=on-failure
RestartSec=10
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target
```

#### b. Systemd Unit cho Polling Agent (`/etc/systemd/system/ceilometer-polling.service`)

```ini
[Unit]
Description=OpenStack Ceilometer Polling Agent
After=syslog.target network.target

[Service]
Type=simple
User=ceilometer
# Chạy với quyền namespaces để cào metric qua libvirt:
ExecStart=/openstack/venvs/ceilometer/bin/ceilometer-polling --config-file=/etc/ceilometer/ceilometer.conf
Restart=on-failure
RestartSec=10

[Install]
WantedBy=multi-user.target
```

### 2. Thiết lập Logging qua Oslo.log và cơ chế Log Rotation

Mặc định, Ceilometer sử dụng thư viện `oslo.log` để quản lý nhật ký hệ thống. Trên môi trường production, log cần được ghi ra tệp tin chuyên biệt và tự động giải phóng bộ nhớ tránh đầy ổ đĩa.

- **Cấu hình trong `/etc/ceilometer/ceilometer.conf`**:

  ```ini
  [DEFAULT]
  # Kích hoạt ghi log vào thư mục chuyên dụng:
  log_dir = /var/log/ceilometer
  log_file = ceilometer.log
  use_stderr = False
  debug = False
  ```

- **Thiết lập Log Rotation (`/etc/logrotate.d/ceilometer`)**:

  ```text
  /var/log/ceilometer/*.log {
      daily
      rotate 7
      compress
      missingok
      notifempty
      sharedscripts
      postrotate
          systemctl reload ceilometer-agent-notification >/dev/null 2>&1 || true
      endscript
  }
  ```

## II. GNOCCHI — QUẢN LÝ SYSTEMD VÀ TỐI ƯU HÓA HIỆU NĂNG (TUNING)

Gnocchi là dịch vụ chịu tải ghi đĩa lớn nhất trong cụm Telemetry. Việc tinh chỉnh luồng xử lý bất đồng bộ đóng vai trò quyết định đến tính ổn định của hệ thống.

### 1. Quản lý dịch vụ bằng Systemd

Các file unit systemd quản trị hai cấu phần API và bộ nạp số liệu nền:

#### a. Systemd Unit cho Metricd Daemon (`/etc/systemd/system/gnocch-metricd.service`)

```ini
[Unit]
Description=Gnocchi Metric Processing Daemon
After=syslog.target network.target

[Service]
Type=simple
User=gnocchi
ExecStart=/openstack/venvs/gnocchi/bin/gnocchi-metricd --config-file=/etc/gnocchi/gnocchi.conf
Restart=always
RestartSec=5
# Đảm bảo metricd có đủ quyền truy cập file descriptors cho hàng nghìn file time-series:
LimitNOFILE=131072

[Install]
WantedBy=multi-user.target
```

### 2. Tối ưu hóa hiệu năng (Tuning) trong Production

Cấu hình tinh chỉnh hiệu năng trong `/etc/gnocchi/gnocchi.conf`:

```ini
[metricd]
# 1. Tăng số lượng worker xử lý bất đồng bộ (khuyến nghị: 1 worker cho mỗi CPU core khả dụng):
workers = 8

# 2. Khoảng thời gian giãn cách quét Incoming Storage để xử lý dữ liệu thô (tính bằng giây):
processing_delay = 5

# 3. Kích thước batch nạp dữ liệu tối đa cho mỗi luồng xử lý:
metric_processing_delay = 10
```

- **`workers`**: Nếu số lượng worker quá thấp, Gnocchi sẽ bị nghẽn (delay) khi ghi dữ liệu chuỗi thời gian vào Ceph.
- **`processing_delay`**: Tần suất dọn dẹp và xử lý dữ liệu đệm. Giảm thông số này giúp đẩy nhanh tốc độ hiển thị biểu đồ của người dùng gần với thời gian thực hơn.

## III. AODH — QUẢN LÝ SYSTEMD VÀ THIẾT LẬP TÙY CHỈNH THỜI GIAN (TUNING)

Aodh cần chạy ổn định các trình đánh giá để kịp thời phát hiện và phản hồi các sự cố hạ tầng.

### 1. Quản lý các dịch vụ bằng `Systemd`

Aodh triển khai các daemon dưới dạng Systemd độc lập để dễ dàng scale-out độc lập khi tải của luồng Notifier tăng cao.

#### Systemd Unit cho Evaluator Daemon (`/etc/systemd/system/aodh-evaluator.service`)

```ini
[Unit]
Description=OpenStack Aodh Alarm Evaluation Daemon
After=syslog.target network.target

[Service]
Type=simple
User=aodh
ExecStart=/openstack/venvs/aodh/bin/aodh-evaluator --config-file=/etc/aodh/aodh.conf
Restart=on-failure
RestartSec=10

[Install]
WantedBy=multi-user.target
```

### 2. Tối ưu hóa Logging và chu kỳ quét cảnh báo (Tuning)

Cấu hình tinh chỉnh hoạt động của Aodh trong `/etc/aodh/aodh.conf`:

```ini
[DEFAULT]
log_dir = /var/log/aodh
use_stderr = False
debug = False

[alarming]
# Chu kỳ đánh giá định kỳ các alarm threshold (tính bằng giây):
evaluation_interval = 60

# Số lượng luồng (workers) đồng thời để đánh giá các alarm:
evaluation_workers = 4
```

- **`evaluation_interval`**: Quy định thời gian giãn cách giữa các chu kỳ quét kiểm tra. Trong production lớn, đặt chu kỳ quá ngắn (ví dụ < 30 giây) sẽ gây áp lực truy vấn REST API cực lớn lên Gnocchi API, có thể làm tê liệt Gnocchi API Server. Cấu hình khuyến nghị an toàn là **`60`** hoặc **`120`** giây.

- **Log Rotation (`/etc/logrotate.d/aodh`)**: Thiết lập tương tự để quay vòng log định kỳ hàng ngày, giữ lại tối đa 7 ngày lưu trữ để tiết kiệm tài nguyên ổ cứng.
