**Note1**: Ta tạo biến môi trường để làm gì ?

Ta tạo biến môi trường dùng để lưu các biến mà request có thể dùng lại, thay vì bạn phải gõ đi gõ lại.

Ví dụ dễ hiểu:

- Bạn có API ở nhiều môi trường:

```text
Local: http://localhost:3000
Dev: https://dev-api.example.com
Production: https://api.example.com
```

- Thay vì mỗi request phải viết URL đầy đủ như:

```text
https://dev-api.example.    com/users
```

- Bạn tạo biến environment:

```text
baseUrl = https://dev-api.    example.com
```

- Rồi trong request dùng:

```text
{{baseUrl}}/users
```

=> Khi muốn chuyển từ **Dev** sang **Production**, bạn chỉ cần đổi **environment** hoặc đổi giá trị **baseUrl**, không cần **sửa từng request**.

**Environment** thường dùng để lưu:

```text
baseUrl — domain API
token — access token sau khi login
userId, orderId — ID dùng cho request tiếp theo
apiKey — khóa API
thông tin cấu hình theo từng môi trường: dev, staging, prod
```

Tiếp theo ta tạo phần **test Script**

**Note3**: Trong Postman, phần Scripts có 2 phần chính:

- Pre-request
- Post-response

Nhiều người vẫn quen gọi là **Tests** hoặc **Post-request**, nhưng trong giao diện mới thường là **Post-response**.

Nói đơn giản:

- **Pre-request** chạy trước khi gửi request.
- **Post-response** chạy sau khi nhận response từ API.

1. **Pre-request** dùng để làm gì?

**Pre-request** dùng để chuẩn bị dữ liệu trước khi gọi API.

Ví dụ thường gặp:

- Tạo token hoặc lấy token trước khi gọi API chính
- Tạo timestamp, chữ ký bảo mật, random data
- Set biến vào environment
- Tự động thêm header
- Bỏ qua request trong một số điều kiện

2. **Post-response** dùng để làm gì?

**Post-response** chạy sau khi API trả kết quả.

Nó thường dùng để:

- Kiểm tra status code
- Kiểm tra response có đúng dữ liệu không
- Kiểm tra response body có field cần thiết không
- Lưu token, userId, orderId từ response vào environment
- Điều khiển request tiếp theo khi chạy collection

Vào tab `Tests`, dán script sau vào phần `post-res` để tự động parse và lưu token vào environment:

```javascript
// Lấy token từ response header X-Subject-Token
const token = pm.response.headers.get("X-Subject-Token");
pm.environment.set("token", token);

// Parse project_id từ body
const body = pm.response.json();
const projectId = body.token.project.id;
pm.environment.set("project_id", projectId);

console.log("Token saved:", token);
console.log("Project ID:", projectId);
```

**Note4**: Tại sao lấy token Fernet ở Keystone không phải phương thức `GET` mà lại là `POST`?

*Bản chất của vấn đề*:

- `GET` theo chuẩn HTTP là "lấy tài nguyên đã tồn tại" — không có body, không có side effect.

- `POST` là "tạo ra tài nguyên mới" — có body, có side effect.
Khi bạn gọi `/v3/auth/tokens`, bạn không phải đang đọc một token có sẵn — bạn đang yêu cầu Keystone tạo ra một token mới dựa trên credentials bạn cung cấp. Đây là hành động tạo mới (create), nên dùng `POST` là đúng chuẩn `REST`.(**Credentials** ta cung cấp ở đây chính là `admin_password` mà bạn phải lấy ở **Controller**)

- Lợi ích lấy Token Fernet để làm 1 cái **Credenticals thứ hai** để request các service khác nhanh hơn (do không lưu trong DB như `UUID`) do nó giúp tách biệt dữ liệu response trả về **header** với **metadata** (Phần body) để xử lí.

### 3. Tương tác với Network Services

*Neutron* là Network Service quản lý networks, subnets, routers, security groups, floating IPs. Port: `9696`.

**Lưu ý**: `Header X-Auth-Token`: `{{token}}` là **BẮT BUỘC** cho tất cả **Neutron API**.

#### 3.1 List Networks

Ta setup request `GET {{neutron_url}}/v2.0/networks` và `X_Auth_Token`

#### 3.2 Create Network

Ta setup request `POST {{neutron_url}}/v2.0/networks` và `X_Auth_Token`

Và thêm phần Boby với Format là `RAW`:

```Json
{
  "network": {

Và thêm phần Boby với Format là `RAW`:

    "network_id": "<network_id>",

    "dns_nameservers": ["8.8.8.8", "8.8.4.4"]
  }
}
```

**Note**: Lấy `network_id` bằng request `GET {{neutron_url}}/v2.0/networks` ở trên hoặc trong Controller.

### 8. SETUP COLLECTION VÀ AUTO-TOKEN

**Note**: Giải thích một số khái niệm cơ bản trong Postman:

- **Environment (Môi trường) là gì?**
  Environment trong Postman là một tập hợp các biến (variables) dưới dạng key-value. Nó cho phép bạn lưu trữ các thông số thay đổi theo từng môi trường làm việc (ví dụ: Dev, Test, Prod) như địa chỉ IP, URL của API, username, password. Nhờ đó, bạn có thể chạy cùng một request trên nhiều môi trường khác nhau chỉ bằng cách chuyển đổi Environment mà không cần sửa URL hay body của request.

- **Collection là gì?**
  Collection là một thư mục dùng để nhóm và tổ chức các API request có liên quan với nhau. Bạn có thể lưu các request thành từng thư mục con, gán script chạy tự động cho cả collection, xuất/nhập (export/import) để chia sẻ cho team, hoặc chạy toàn bộ các request trong collection tuần tự bằng tính năng Collection Runner.

- **Auto-Token (Tự động lấy Token) là gì?**
  Trong OpenStack, để gọi bất kỳ API nào (Nova, Neutron, Cinder...), bạn đều cần gắn header `X-Auth-Token`. Thay vì phải copy/paste token thủ công mỗi khi token hết hạn (thường là 1 tiếng), ta có thể sử dụng tính năng **Tests** (hoặc **Pre-request Script**) của Postman kết hợp với biến Environment để tự động trích xuất và lưu Token vào biến sau khi gửi request xác thực tới Keystone. Các request tiếp theo chỉ việc gọi lại biến `{{token}}` mà không cần làm gì thêm.

Phần tương tác với **Collection** và **Auto-Token** ta sẽ đọc tài liệu ở [đây](https://github.com/tiend9/Tim-hieu-OPNsense/blob/main/15.Deployment_OPS/04.Working_with_API_OPS/01.OpenStack_Postman_API_Guide.pdf) đã hướng dẫn chi tiết.
