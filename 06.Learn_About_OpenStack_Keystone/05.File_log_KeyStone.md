# TÌM HIỂU FILE LOG CỦA KEYSTONE

**Log file** là một thành phần không thể thiếu trong quá trình vận hành, giám sát và khắc phục sự cố (troubleshooting) đối với **OpenStack Keystone**. Bài viết này sẽ đi sâu vào các loại file log, cách cấu hình, cách đọc hiểu và phân tích log để debug.

## 1. Tổng quan về Hệ thống Log của Keystone

Keystone (Identity Service) là trung tâm xác thực và phân quyền của toàn bộ hệ thống OpenStack. Do đó, log của Keystone chứa các thông tin cực kỳ quan trọng về:

- Các request xác thực (Authentication requests).
- Việc cấp phát và xác thực Token.
- Các thao tác tạo, sửa, xóa User, Project, Role, Service, Endpoint,...
- Tình trạng kết nối giữa Keystone và các backend (Database MySQL/MariaDB, Memcached, LDAP).

Theo mặc định trong hầu hết các bản phân phối Linux (Ubuntu/Debian, CentOS/RHEL), log của Keystone được lưu tại thư mục:

```bash
/var/log/keystone/
```

## 2. Các file Log chính của Keystone

Do Keystone hiện tại chủ yếu được triển khai dưới dạng một **WSGI application** chạy trên Web Server (như **Apache2** hoặc **uWSGI**), hệ thống log thường được chia thành 2 phần:

- Log của ứng dụng Keystone
- Log của Web Server.

### 2.1. File log của ứng dụng Keystone

- **`/var/log/keystone/keystone.log`**: Đây là file log chính và quan trọng nhất. Nó ghi lại toàn bộ hoạt động bên trong của ứng dụng Keystone, bao gồm:
  - các cảnh báo (`WARNING`)
  - lỗi (`ERROR`)
  - thông tin (`INFO`)
  - gỡ lỗi (`DEBUG`) nếu được bật.
  - Các lỗi kết nối database, lỗi logic, lỗi token hết hạn... đều nằm ở đây.

### 2.2. File log của Web Server (Apache/WSGI)

Vì **Web Server** đóng vai trò tiếp nhận request HTTP/HTTPS và chuyển cho **Keystone WSGI** xử lý, log của nó giúp theo dõi lượng traffic và các lỗi ở tầng HTTP:

- **`/var/log/apache2/keystone_access.log`** (hoặc `httpd` trên RHEL/CentOS): Ghi lại tất cả các request HTTP gửi đến Keystone (IP client, Method `GET`/`POST`/`DELETE`, `URI`, `HTTP Status Code` trả về).

- **`/var/log/apache2/keystone_error.log`**: Ghi lại các lỗi ở tầng Web Server (ví dụ: **Apache** không gọi được **script WSGI**, tiến trình **WSGI** bị crash).

## 3. Cấu hình Log trong Keystone

Việc ghi log của Keystone được cấu hình trong file cấu hình chính: **`/etc/keystone/keystone.conf`**.

Mở file và tìm đến section `[DEFAULT]` để thiết lập các tham số liên quan đến log:

```ini
[DEFAULT]

# Bật chế độ Debug. Nếu set là True, log sẽ ghi lại rất chi tiết mọi hoạt động (cả các câu query SQL, quá trình mã hóa token...).
# RẤT HỮU ÍCH khi debug nhưng KHÔNG NÊN bật trên Production vì sẽ làm tăng kích thước file log cực nhanh.
debug = False

# Đường dẫn thư mục chứa file log.
log_dir = /var/log/keystone

# Tên file log. Nếu được thiết lập cùng với log_dir, file sẽ lưu tại /var/log/keystone/keystone.log
log_file = keystone.log

# Bật/tắt việc sử dụng syslog (thường dùng để đẩy log tập trung).
use_syslog = False

# Định dạng chuẩn của một dòng log.
# logging_context_format_string = %(asctime)s.%(msecs)03d %(process)d %(levelname)s %(name)s [%(request_id)s %(user_identity)s] %(instance)s%(message)s
```

## 4. Cấu trúc của một dòng Log Keystone

Hiểu được cấu trúc một dòng log sẽ giúp bạn dễ dàng "đọc vị" được vấn đề bằng các công cụ như `awk` hay `grep`.

Một dòng log chuẩn của Keystone thường có dạng:

```bash
2023-10-25 14:32:01.123 15423 INFO keystone.auth.plugins.password [req-9a8b7c6d-1234-5678-abcd-1234567890ab - - - - -] Validating password for user: admin
```

**Phân tích các thành phần:**

1. `2023-10-25 14:32:01.123`: Timestamp (Thời gian xảy ra sự kiện).
2. `15423`: PID (Process ID của tiến trình xử lý request).
3. `INFO`: Log Level (Mức độ của log: `DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL`).
4. `keystone.auth.plugins.password`: Module của mã nguồn Python đang tạo ra dòng log này.
5. `[req-9a8b7c6d...]`: **Request ID**. Đây là thông tin cực kỳ quan trọng. Mỗi request gửi đến OpenStack sẽ được gắn 1 ID duy nhất. Bạn có thể dùng **Request ID** này để trace luồng đi của request qua nhiều file log của các dịch vụ khác nhau (Nova, Glance, Neutron...) để xem request bị lỗi ở bước nào.
6. `Validating password for user: admin`: Nội dung thông báo log.

## 5. Phân tích log tại `/var/log/keystone/` để Debug Lỗi

Khi có một dịch vụ khác báo lỗi không thể xác thực (VD: **Nova** báo lỗi HTTP `401 Unauthorized` khi gọi tới **Keystone**), bạn cần thực hiện các bước sau để debug:

### Bước 1: Giám sát log trực tiếp (Real-time monitoring)

Sử dụng lệnh `tail -f` để xem log mới nhất được sinh ra khi bạn thực hiện thao tác gây ra lỗi:

```bash
tail -f /var/log/keystone/keystone.log
```

### Bước 2: Bật chế độ Debug (Nếu log INFO không đủ thông tin)

Nếu log bình thường không chỉ ra rõ lỗi, hãy sửa `debug = True` trong `/etc/keystone/keystone.conf` và khởi động lại dịch vụ Apache:

```bash
# Ubuntu/Debian
systemctl restart apache2
# CentOS/RHEL
systemctl restart httpd
```

*Lưu ý: Nhớ tắt debug sau khi troubleshoot xong.*

### Bước 3: Lọc log theo Request ID hoặc Keyword

Giả sử bạn tìm thấy một lỗi có chứa `req-abcd1234`, hãy dùng `grep` để lấy toàn bộ ngữ cảnh của request đó:

```bash
grep "req-abcd1234" /var/log/keystone/keystone.log
```

Hoặc tìm kiếm các dòng lỗi:

```bash
grep "ERROR" /var/log/keystone/keystone.log
```

### Một số lỗi phổ biến và dấu hiệu nhận biết trong log

1. **Lỗi kết nối Cơ sở dữ liệu (Database Connection Error):**

   - **Log**: `OperationalError: (pymysql.err.OperationalError) (2003, "Can't connect to MySQL server on 'controller' (111)")`
   - **Nguyên nhân**: Dịch vụ MariaDB/MySQL bị sập, sai IP, sai port hoặc tường lửa chặn.

2. **Lỗi hết hạn / Sai thông tin xác thực (Invalid Credentials):**

   - **Log**: `WARNING keystone.common.wsgi [...] Authorization failed. The request you have made requires authentication.`
   - **Nguyên nhân**: User nhập sai mật khẩu, hoặc token đã hết hạn (expired).

3. **Lỗi kết nối Memcached:**
   - **Log**: `WARNING keystone.common.cache.backends.memcache_pool [...] Error talking to memcached`
   - **Nguyên nhân**: Tiến trình Memcached bị chết hoặc cấu hình sai địa chỉ Memcached trong `keystone.conf`. Điều này làm việc cấp và xác thực token bị chậm đi rất nhiều.

4. **Lỗi không tìm thấy Endpoint (EndpointNotFound):**

   - **Log**: `ERROR keystone.catalog.core [...] Endpoint not found.`
   - **Nguyên nhân**: Dịch vụ đang yêu cầu một API endpoint chưa được tạo trong Keystone Catalog.

## 6. Luân chuyển Log (Log Rotation)

Nếu Keystone phục vụ hàng ngàn request mỗi giây, file `keystone.log` sẽ phình to rất nhanh, gây cạn kiệt dung lượng ổ cứng (Lỗi `No space left on device`).
Giải pháp là sử dụng công cụ **Logrotate** của Linux.

File cấu hình logrotate cho Keystone thường nằm tại: **`/etc/logrotate.d/keystone`**. Cấu trúc mẫu:

```bash
/var/log/keystone/*.log {
    daily               # Cắt log hàng ngày
    missingok           # Bỏ qua nếu không tìm thấy file log, không báo lỗi
    rotate 7            # Giữ lại 7 file log cũ nhất (trong 7 ngày)
    compress            # Nén các file log cũ (thành .gz) để tiết kiệm dung lượng
    delaycompress
    notifempty          # Không cắt log nếu file rỗng
    create 640 keystone keystone # Quyền và owner của file log mới tạo
    postrotate
        systemctl reload apache2 > /dev/null 2>/dev/null || true
    endscript
}
```

Nhờ cơ chế này, hệ thống log của Keystone sẽ luôn được dọn dẹp gọn gàng và ổn định.

**Tổng kết:** Việc làm chủ file log của Keystone (biết xem ở đâu, cấu hình như thế nào, và cách grep thông tin) là kỹ năng "sống còn" đối với người quản trị OpenStack để đảm bảo hệ thống xác thực vận hành trơn tru
